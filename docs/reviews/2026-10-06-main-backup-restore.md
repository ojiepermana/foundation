## Summary

Perubahan ini menambah backup dan pemulihan database: role baca saja `foundation_backup` di `database/provision.ts`, `deploy/backup.yaml` dengan dua job sekali jalan, script `foundation-backup.sh` (create, retensi, check) dan `foundation-restore.sh` (sepuluh pemeriksaan sebelum `pg_restore`), `database/fingerprint.ts`, suite `backup.test.ts` (BKP-003 sampai BKP-007) dan `backup-static.test.ts` (BKP-001), bukti `.local/feature-14/restore.json` di langkah `test:database:real`, aturan `docs/rules/backup.md`, template dan catatan latihan restore. Reviewer tidak menemukan blocker maupun major. Reviewer menjalankan `bun run test:database:real` pada pohon sumber akhir dan hasilnya hijau: 85 test lulus dalam 117 detik, `restore.json` berstatus `passed` dengan kedua belas guard lulus, dan sesudahnya tidak ada container, network, atau folder `foundation-backup-*` yang tertinggal. Temuan yang tersisa ada dua minor (DSN dengan password tampil di argumen proses, dan jalur sinyal belum punya test runtime) serta beberapa nit pada script, runbook, dan dokumen pelacak.

## Minor

### 🟡 DSN dengan password tampil di argumen `pg_dump`, `psql`, dan `pg_restore`, `deploy/backup/foundation-backup.sh:307`

**Problem**: Kedua script memberi alat PostgreSQL seluruh connection string sebagai `--dbname="$FOUNDATION_BACKUP_DATABASE_URL"` (backup baris 307) atau `--dbname="$FOUNDATION_ADMIN_DATABASE_URL"` (`deploy/backup/foundation-restore.sh:118` untuk `psql` dan `:196` untuk `pg_restore`), sehingga password ikut di argumen proses. Reviewer membuktikannya di scratchpad: container backup dengan image, user, dan flag yang sama dijalankan terhadap listener palsu yang menggantung, lalu `docker top <container> -o pid,args` mencetak `pg_dump --dbname=postgres://foundation_backup:<password uji>@postgres:5432/foundation --role=pg_read_all_data ...` dan baris `timeout` dengan DSN yang sama. Pada host Linux proses container tampil di tabel proses host, dan `/proc/<pid>/cmdline` dapat dibaca setiap pengguna lokal kecuali host memakai `hidepid`. Bentuk ini ditetapkan spec (baris *Perintah pg_dump* dan *Perintah restore*) dan malah diwajibkan BKP-001 (`environmentProblems` hanya menerima DSN sebagai `--dbname="$NAME"`), jadi ini keputusan desain yang belum dicatat sebagai risiko. Rationale tidak menyebutnya, `docs/rules/backup.md` bagian *Batas* hanya menyebut akses Docker setara root, dan `docs/rules/deployment.md:67` justru meminta operator tidak menaruh nilai rahasia di argumen perintah.

**Why it matters**: Password `foundation_backup` (setingkat admin untuk kerahasiaan menurut spec, karena membaca seluruh data dan `pg_authid`) terbaca pengguna host mana pun selama `pg_dump` berjalan, sampai 3.600 detik setiap hari. Password `foundation_admin` (superuser) terbaca selama restore, yaitu saat insiden. Pada host yang hanya dipakai satu operator dampaknya kecil, tetapi spec sendiri memperlakukan kedua credential ini sebagai yang paling sensitif, dan semua jalur lain di repository membawa DSN lewat environment.

**Suggested fix**: Putuskan lewat `/architect` salah satu dari dua jalan. Pertama, script menulis file credential di `/tmp` (tmpfs, mode 0600) untuk `PGPASSFILE` atau `PGSERVICEFILE`, dan `--dbname` hanya memuat host, port, user, dan database; ubah baris *Perintah pg_dump*, *Perintah restore*, dan langkah 6 *Urutan restore* di spec, konstanta `PG_DUMP`, `PG_RESTORE`, dan `PSQL` di BKP-001, lalu tambahkan kontrol bahwa DSN tidak muncul di argumen. Kedua, bila pemilik menerima risikonya, catat di bagian *Security model* spec dan bagian *Batas* `docs/rules/backup.md` bahwa DSN terlihat di tabel proses host selama job berjalan, dengan `hidepid=2` pada `/proc` sebagai mitigasi host.

### 🟡 Handler TERM dan INT hanya dijaga pemeriksaan statis dan probe manual, `tests/integration/database/backup.test.ts:1180`

**Problem**: `on_signal`, `background`, `wait`, dan `remove_run_files` adalah bash yang paling halus di kedua script (script berjalan sebagai PID 1, alat dijalankan di background, trap dipasang tiga kali). Kategori `interrupted` hanya dibuktikan BKP-001, yang membaca teks fungsi, dan probe manual dengan `pg_dump` palsu di `verify.md` baris 75. Spec AC-3 beralasan bahwa keadaan itu "tidak dapat dipicu komponen nyata tanpa mengubah konstanta script", padahal dapat dipicu: `docker kill --signal TERM <nama run>` pada run Compose yang diberi nama eksplisit `foundation-backup-run-<hex>-<n>` saat `pg_dump` sungguhan menunggu lock 30 detik (kasus BKP-006 di baris 1180), atau saat koneksi menggantung. Reviewer membuktikan perilakunya sekarang benar dengan `pg_dump` sungguhan yang menggantung saat connect: TERM memberi exit 143, sedangkan INT dan `docker stop` (image memakai `STOPSIGNAL SIGINT`) memberi exit 130, masing masing dengan tepat satu baris `Backup failed: interrupted` dan folder backup kosong.

**Why it matters**: Refactor script yang mempertahankan teks fungsi tetapi merusak perilaku (misalnya `wait` dipindah, atau proses anak tidak lagi dihentikan) lulus seluruh test. Akibatnya `docker stop` atau penjadwal yang dihentikan dapat meninggalkan `.partial` dan container yang menunggu sampai `stop_grace_period` habis, tanpa ada test yang gagal. Ini jalur penanganan galat yang tidak punya bukti runtime, jadi minor, bukan nit.

**Suggested fix**: Tambahkan satu test BKP-006 yang memegang lock `ACCESS EXCLUSIVE` seperti kasus lock timeout, memulai run backup di background dengan nama eksplisit, lalu mengirim `docker kill --signal TERM`, `docker kill --signal INT`, dan `docker stop` ke nama itu (satu run per sinyal). Periksa exit 143 atau 130, tepat satu baris `Backup failed: interrupted`, dan folder sama persis dengan sebelum run. Karena nama container sudah didaftarkan di `signal-cleanup.ts`, GATE-009 tidak perlu berubah. Perbarui kalimat AC-3 dan baris *Perubahan GATE-009* di spec lewat `/architect`, karena `interrupted` tidak lagi hanya statis.

## Nits

- ⚪ `deploy/backup/foundation-backup.sh:351`, `sync` tanpa argumen menyiram seluruh filesystem host, bukan hanya `/backup`. Pada host database yang sibuk itu menahan semua tulis sampai selesai. Spec menulis "diikuti `sync`", jadi ubah hanya bila pemilik setuju: `sync -f "$BACKUP_DIR"` (GNU coreutils) cukup untuk durabilitas folder ini.
- ⚪ `deploy/backup/foundation-restore.sh:121`, pemeriksaan pra restore lewat `psql` memakai kategori cadangan `pg_restore`, sehingga galat `psql` yang tidak dikenal tercetak `Restore failed: pg_restore` padahal `pg_restore` belum berjalan. Ini sesuai tabel *Pesan script*, tetapi menyesatkan operator. Pakai `psql` sebagai cadangan di `query()` dan tambahkan ke tabel pesan, atau catat di `docs/rules/backup.md`.
- ⚪ `deploy/backup/foundation-backup.sh:115` dan `deploy/backup/foundation-restore.sh:89`, fungsi `category()` sama persis di kedua script dan hanya dijaga test BKP-001 (`functionBody` sama). Tidak masalah selama kedua script dipasang terpisah, tetapi satu komentar yang menunjuk ke test itu membuat penyunting tahu mengapa kedua salinan harus diubah bersama.
- ⚪ `docs/rules/backup.md:195`, bullet *Pemulihan* menyuruh "biarkan project lama berhenti", tetapi perintahnya hanya `stop edge`; backend dan PostgreSQL project lama tetap berjalan, dan tabel *Prosedur insiden* baris pertama meminta edge dan backend dihentikan. Tulis perintah `stop` untuk semua service project lama (tanpa `down --volumes`), atau sebut service mana yang sengaja dibiarkan.
- ⚪ `docs/rules/backup.md:148`, `:156`, dan `:171`, runbook meminta `FOUNDATION_ADMIN_DATABASE_URL` dan `FOUNDATION_BACKUP_DATABASE_URL` diisi "di shell", tetapi tidak meminta menghapusnya sesudahnya, berbeda dari `docs/rules/deployment.md:72` untuk provisioning. Compose memberi nilai shell prioritas atas `--env-file` (test sendiri bergantung pada hal itu untuk `FOUNDATION_DATA_NETWORK`), sehingga `FOUNDATION_BACKUP_DATABASE_URL` yang tertinggal menimpa DSN di `.env.backup` pada backup berikutnya (gagal tertutup dengan `Backup failed: connection`, tetapi membingungkan), dan DSN superuser tetap ada di environment shell. Tambahkan satu kalimat penutup runbook: hapus kedua variable dari shell.
- ⚪ `docs/specs/0013-backup-pemulihan-data/verify.md`, 14 kotak masih `[ ]` (baris 64, 85, 92, 102, 119, 132, 145, 146, 154, 172, 178, 187, 212, dan 213). Beberapa memuat angka usang: baris 119 menulis 70 test (run reviewer 85), baris 178 menulis 12 test BKP-001 (baris 199 dan run reviewer 15), dan baris 64 serta 102 menggambarkan keadaan sementara (`status` `failed`, guard `not_run`) yang tidak berlaku lagi. Centang yang sudah dijalankan (kontrol negatif tercatat pada catatannya) atau tandai tergantikan.
- ⚪ `AGENTS.md`, bagian *Sumber aturan* belum menunjuk `docs/rules/backup.md`. Spec menetapkan ini sebagai tindak lanjut `/sync`, jadi sampai itu jalan agent yang mengubah `deploy/backup*`, `database/fingerprint.ts`, atau role backup tidak diberi tahu untuk membaca aturan itu.
- ⚪ `docs/scope/scope.md:366`, kotak induk "Bangun" masih `[ ]` padahal kelima sub butirnya `[x]`. Centang bersama butir `/document`, seperti fitur sebelumnya.

## Strengths

- Bukti berlapis dan tahan salah baca. Setiap kasus gagal diperiksa dengan tiga sisi: stderr harus tepat satu baris kategori, stdout kosong, dan keadaan folder (nama, jenis, ukuran, mode, mtime) atau target (fingerprint dengan digest) tidak berubah. Pemindaian secret punya kontrol positif (sentinel data harus ada di teks dump) dan memindai berkas `restore.json` sebelum ditulis.
- Struktur script memaksa penyaringan keluaran. Stderr dialihkan ke file di `/tmp`, hanya `report()` menulis ke fd 3, dan test statis menghitung bahwa `>&3` muncul tepat sekali. Pemetaan kategori mengikuti urutan tabel spec dan dikunci dengan mutasi.
- Keputusan yang lahir dari probe tercatat dan masing masing punya test: `sha256sum --check` yang menerima baris yang menamai file lain (`checksum_wrong_file`), `pg_dump` yang menjadikan lock wait `statement_timeout`, tabel ber RLS yang terbaca 0 baris tanpa galat (fingerprint memakai `row_security = off` dan gagal jelas), dan stempel nama yang ditolak GNU `date`.
- Perubahan `provision.ts` aman terhadap regresi. Daftar grantee dibaca lewat satu subquery sehingga pemeriksaan `Unknown privilege drift` tidak mati diam diam saat role backup tidak ada (diuji pada test terakhir BKP-002), report tanpa variable sama persis dengan sebelumnya, dan 13 test DATA lama berjalan tanpa diubah. Reviewer juga membuktikan `docker compose run -e NAME` dengan variable yang tidak ada di shell membuat variable itu tidak ada di container (bukan kosong), sehingga perintah provisioning di `docs/rules/deployment.md` tetap aman bagi operator yang belum memakai role backup.
- Batas bukti dinyatakan jujur di kode, dokumen, dan catatan latihan: `restore.json` memuat kalimat `boundary`, catatan latihan menyebut Docker Desktop macOS tidak membuktikan syarat owner folder dan RTO sampai edge belum terukur, dan tidak ada perintah yang mengunggah backup atau mendorong image (BKP-001 menolak alat jaringan dan penyalinan di kedua script).
- Pembersihan sinyal suite baru ikut dijaga GATE-009 (daftar `checked`, `REAL_SUITES`, heuristik `docker network create` dan `docker compose ... run --rm`, dan test `interruptedSuite` dengan Docker palsu), dan run reviewer tidak meninggalkan sisa apa pun.

## Major

### 🟠 RPM repo dipasang sebelum keasliannya diperiksa, `infrastructure/postgres/Dockerfile:25`

**Problem**: `rpm -i --nosignature /tmp/pgdg-repo.rpm` memasang payload dan dapat menjalankan scriptlet paket sebagai root sebelum fingerprint key diperiksa pada baris 32 dan signature RPM diperiksa pada baris 37. Pemeriksaan berikutnya memakai filesystem dan alat yang sudah dapat diubah oleh paket tersebut. Perilaku `--nosignature` dan eksekusi scriptlet pada instalasi ditegaskan dalam [manual RPM](https://rpm.org/docs/4.20.x/man/rpm.8).

**Why it matters**: Bila artefak pada endpoint distribusi diganti tanpa key penandatangan PGDG, scriptlet dari RPM pengganti tetap dapat berjalan sebelum build menolaknya. Scriptlet juga dapat mengubah alat pemeriksa atau isi image; kegagalan signature sesudah instalasi tidak membatalkan eksekusi yang sudah terjadi. HTTPS melindungi pengiriman, tetapi urutan ini menghilangkan perlindungan signature terhadap kompromi artefak distribusi yang hendak diberikan AC-1 dan security model spec 0002. Ini temuan urutan kepercayaan dari kode, bukan klaim bahwa paket PGDG yang sekarang digunakan telah disusupi.

**Suggested fix**: Dapatkan public key secara terpisah atau ekstrak hanya key ke lokasi sementara tanpa memasang RPM, cocokkan fingerprint dengan konstanta tepercaya, lalu impor key tersebut. Wajibkan signature RPM yang valid dari key yang diizinkan sebelum menjalankan instalasi atau menggunakan konfigurasi repo dari payload. Tambahkan pembuktian INFRA-002 bahwa RPM dengan signature tidak valid atau tanpa signature ditolak sebelum scriptlet maupun payload bisa memengaruhi image.

### 🟠 Perintah update development dapat mempertahankan paket PostgreSQL lama, `docs/rules/infrastructure.md:69`

**Problem**: Prosedur untuk mengambil patch keamanan hanya menjalankan `docker compose ... build --pull postgres`. Jika digest base Oracle Linux belum berubah, Dockerfile dan build args tetap sama, sehingga langkah `RUN` yang memasang paket PGDG pada `infrastructure/postgres/Dockerfile:17` dapat diambil seluruhnya dari cache. Rilis patch PGDG di server repo tidak mengubah cache key itu. [Aturan cache Docker](https://docs.docker.com/build/cache/invalidation/#run-instructions) menjelaskan bahwa instalasi paket melalui `RUN` tidak otomatis dijalankan ulang; [opsi Compose build](https://docs.docker.com/reference/cli/docker/compose/build/) membedakan `--pull` dari `--no-cache`.

**Why it matters**: Pengembang yang sudah mempunyai image dapat mengikuti perintah pembaruan yang didokumentasikan, mendapat exit 0, lalu tetap menjalankan patch PostgreSQL lama. Pembaruan PostgreSQL tidak selalu bertepatan dengan perubahan base Oracle Linux. Ini membuat prosedur pemeliharaan keamanan dan klaim dev memakai paket 18 terbaru tidak dapat diandalkan, meskipun suite dengan versi terkunci lulus.

**Suggested fix**: Jadikan perintah update eksplisit membatalkan cache instalasi, misalnya `docker compose --env-file .env.infrastructure build --pull --no-cache postgres`, kemudian buat ulang service sebagaimana sudah didokumentasikan. Selaraskan README, rules, serta langkah spec/verify yang memuat perintah update itu. Buktikan perintah update menjalankan ulang langkah instalasi ketika base tetap sama, lalu catat versi paket yang benar-benar terpasang; jangan menganggap exit 0 build sebagai bukti paket diperbarui.

## Major

### 🟠 Allowlist bundle masih menerima key lain dengan short ID yang sama, `infrastructure/postgres/verify-pgdg-repo-rpm.sh:29`

**Problem**: Fingerprint penuh pada baris 18 sampai 22 hanya memeriksa paket public key pertama. Sesudah import seluruh file ke database sementara, baris 29 hanya membaca `%{VERSION}` setiap `gpg-pubkey`, yaitu delapan digit terakhir fingerprint, lalu menjalankan `sort -u`. Dua sertifikat berbeda dengan short ID PGDG yang sama menjadi satu nilai dan lolos pemeriksaan baris 30. Baris 35 kemudian mengimpor keduanya ke trust store global. Tidak ada pemeriksaan fingerprint lengkap bagi sertifikat tambahan.

**Why it matters**: Pihak yang dapat mengganti file key dapat mempertahankan sertifikat PGDG asli sebagai key pertama dan menambahkan key miliknya dengan short ID yang sama. Repo RPM asli tetap lolos, sementara signer tambahan mendapat kepercayaan untuk instalasi paket berikutnya. Pencarian short ID 32 bit tidak memerlukan pemalsuan fingerprint SHA1 penuh atau private key PGDG. Panduan primer GnuPG menjelaskan bahwa key dengan ID 32 bit tertentu dapat dibuat dengan usaha rendah, sehingga short ID tidak layak menjadi batas kepercayaan ini. Lihat [An Advanced Introduction to GnuPG, bagian 10.6.1, halaman 115](https://www.gnupg.org/ftp/people/neal/an-advanced-introduction-to-gnupg/an-advanced-introduction-to-gnupg.pdf#page=115).

**Evidence and limits**: Dalam container sementara dari base yang dipin, reviewer mengimpor key PGDG arm64 asli dan menjalankan `rpm -q gpg-pubkey --qf '%{VERSION} %{RELEASE}\n'`. Identitas yang dipakai kandidat memang hanya `b9738825`, bukan fingerprint lengkap. Jalur penerimaan dua key dengan nilai ini terlihat langsung pada `sort -u` dan perbandingan string. Implementasi upstream RPM 4.19 memakai `pgpKeyID_t` untuk pencarian keyring, sehingga dua key dengan short ID sama dan long ID berbeda tidak otomatis dianggap identik oleh keyring ([rpmkeyring.c](https://github.com/rpm-software-management/rpm/blob/rpm-4.19.x/rpmio/rpmkeyring.c)). Reviewer tidak membuat collision khusus fingerprint PGDG dan tidak mengklaim eksploitasi kandidat ini telah direproduksi sampai pemasangan payload. Ini adalah cacat pemilihan identitas pada kode, dengan prasyarat collision short ID, bukan kegagalan test bundle acak yang sudah lulus.

**Suggested fix**: Validasi fingerprint lengkap setiap sertifikat yang benar benar akan diimpor. Anda dapat menolak sertifikat tambahan melalui parser sertifikat, atau mengimpor ke keyring terisolasi lalu mengekspor hanya sertifikat dengan fingerprint lengkap yang telah dipin untuk import global. Jangan memutuskan kepercayaan berdasarkan `%{VERSION}` atau menghapus jumlah key melalui `sort -u`. Bila tetap memakai database sementara RPM, baca dan periksa kembali bahan public key dari setiap record, termasuk jumlah record, sebelum mengimpor bahan yang sudah dibatasi. Pertahankan fixture bundle yang ada dan cakup perilaku identitas key penuh agar short ID tidak kembali menjadi otorisasi.

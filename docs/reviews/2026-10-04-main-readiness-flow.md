## Summary

Perubahan ini menambah `GET /api/readiness` khusus development (satu pemeriksaan aktif per instance, batas 5.000 ms, urutan 404, 400, 503, 429, dan `Cache-Control: no-store`), kontrak OpenAPI dan SDK hasil generate, adapter `ReadinessApi`, halaman `/kesiapan`, serta tooling uji nyata (READY-008 dan READY-009) dengan penjaga container. Reviewer tidak menemukan blocker maupun major. Perilaku sesuai spec 0006 pada semua jalur yang reviewer jalankan sendiri, termasuk PostgreSQL 18 nyata (lock, pause, stop dan start) dan browser nyata. Dari 20 mutasi kecil yang reviewer coba di scratchpad, 16 tertangkap test dan 4 selamat. Temuan yang tersisa: jalur HTTP 200 dan 429 hanya terbukti oleh suite Docker di luar `test:ci`, laporan bukti dan `verify.md` tertinggal dari suite saat ini, dan tujuh file uji belum punya gerbang tipe.

## Minor

### 🟡 Jalur HTTP 200 dan 429 hanya terbukti oleh suite Docker di luar `test:ci`, `apps/backend/src/features/development/readiness.routes.ts:55`

**Problem**: Pemetaan jawaban di baris 55 sampai 58 (200 diteruskan apa adanya, `status(429, ...)`, `status(503, ...)`), validasi response Elysia atas `ReadinessAvailable`, dan header `no-store` pada 200 dan 429 tidak dijalankan oleh test mana pun yang ikut `test:ci`. READY-001 hanya mencapai 503 (tanpa pool dan pool tripwire) serta 400 dan 404, READY-002 menguji factory dan bukan route, sedangkan READY-004 dan READY-005 memakai respons tiruan di sisi frontend. Reviewer menyalin `apps/backend/src` dan `tests/integration/backend/readiness.test.ts` ke scratchpad di luar repository, lalu membuat dua mutasi: `busy` dipetakan ke `status(503, ...)`, dan `appliedMigrations` dikirim sebagai string. Pada keduanya seluruh 23 test `tests/integration/backend/readiness.test.ts` tetap lulus. Mutasi yang sama pada READY-008 (Docker) gagal pada 2 test untuk yang pertama dan 8 test untuk yang kedua.

**Why it matters**: AC-2 menjanjikan bentuk 200 yang tepat dan AC-4 menjanjikan 429 serta `no-store` pada 200 dan 429. Spec memang menaruh bukti database nyata di luar `test:ci` sampai fitur 11 (Consequences, bagian Negative), sehingga gate default tetap hijau ketika kontrak 200 atau 429 rusak. Kerusakan itu baru ketahuan ketika seseorang menjalankan `test:database:real` secara manual, dan jalur CI dengan Docker belum ada.

**Suggested fix**: Tambah satu test tanpa Docker di `tests/integration/backend/readiness.test.ts` yang memberi `createApp('development', { database })` sebuah pool tiruan yang hanya menyediakan `begin(callback)` dengan transaksi tiruan (fungsi tagged template yang mengembalikan satu baris `applied`). Periksa 200 dengan tiga key tepat dan `no-store`, 429 untuk request kedua selagi yang pertama tertahan, dan 503 sesudah tiruan menolak. Beri nama test itu sebagai test route, bukan bukti database, karena READY-008 tetap satu satunya bukti untuk role dan PostgreSQL.

### 🟡 Laporan menyatakan kontrol mutasi sudah tercatat di `verify.md`, tetapi kotaknya masih terbuka, `docs/testing/0009-readiness-flow.md:43`

**Problem**: Baris 43 laporan menyatakan kontrol mutasi langkah 1 sampai 4 (impor spinner yang lebih dalam, binding `aria-disabled` yang dihapus, dua mutasi `isDevMode()`, probe kebocoran credential, empat mutasi source READY-010) "tercatat di verify.md dan dijalankan pada sesi milestone masing masing". Scope sudah mencentang `Verifikasi`.

**Why it matters**: Bukti bahwa test sungguh gagal ketika kodenya dirusak adalah klaim yang bisa diperiksa, dan kini klaim itu tidak punya catatan hasil. Reviewer mengulang sebagian kontrol itu sendiri di scratchpad dan hasilnya baik (lihat bagian Test coverage), tetapi dua kontrol yang butuh build production atau Docker (`isDevMode()` dan probe kebocoran) tidak reviewer ulang, sehingga untuk keduanya klaim laporan belum terbukti oleh dokumen mana pun.

**Suggested fix**: Jalankan langkah yang tersisa, atau jalankan ulang dan catat hasilnya (perintah, hasil, file dikembalikan byte demi byte) lalu centang kotaknya. Kotak baris 213 sebaiknya diubah menjadi catatan bahwa `0009` dipakai fitur ini. Kotak VoiceOver tetap manual: centang bila sudah dijalankan, atau ubah menjadi catatan batas bukti (laporan sudah menyebutnya di bagian Batas bukti). Sampai itu selesai, ubah kalimat di baris 43 menjadi "direncanakan di verify.md" atau sebut kontrol mana yang sudah dijalankan.

### 🟡 Tujuh file uji yang menjalankan penjaga container belum punya gerbang tipe, `tsconfig.contract.json:11`

**Problem**: `typecheck:contract` memeriksa `scripts/test-readiness-real.ts`, `scripts/lib/readiness-container.ts`, dan test di `tests/integration/contract/`, tetapi tidak memeriksa `tests/integration/backend/readiness.test.ts`, `tests/integration/database/readiness.test.ts`, empat file `tests/e2e/readiness/` (`layout.ts` dan tiga spec), serta `playwright.real.config.ts` dan `playwright.config.ts`. Tipe file itu hanya diperiksa lewat dua perintah `tsc` ad hoc di `verify.md` (baris 111 dan 162), dan sebagian file itu berubah sesudahnya (06.03). Reviewer menjalankan kedua perintah itu pada isi saat ini dan keduanya exit 0, jadi tidak ada kesalahan tipe hari ini.

Kesalahan tipe pada pemanggil penjaga, misalnya argumen pemilik yang salah atau hasil `JSON.parse` yang tidak diperiksa, tidak akan gagal di gate mana pun. Review fitur 8 sudah mencatat celah serupa untuk `scripts/`, dan celah itu ditutup untuk file lama tetapi tidak untuk file baru ini.

**Suggested fix**: Tambahkan kedua file `bun:test` ke `files` di `tsconfig.contract.json` (opsi `types: ["bun"]` sudah sesuai).

## Minor

### 🟡 Cabang kegagalan sekunder dan environment `bun audit` pada `check:security` tidak dibedakan test, `tests/orchestration/security-scan.ts:249`

**Problem**: Tiga keputusan di orkestrasi pemindai tidak dikunci test mana pun. Baris 249 membatasi environment `bun audit` ke `PATH` dan `HOME`. Baris 280 dan 346 menaikkan `otherProblems` ketika `exceptions.json` ditolak atau container pemindai tidak dapat dihapus, dan `scripts/lib/security-policy.ts:532` membuat `security.json` berstatus `failed` bila `otherProblems` bukan 0. Reviewer menyalin repository ke scratchpad di luar repository dan membuat empat mutasi: environment `bun audit` diganti seluruh environment proses, baris 280 dihapus, baris 346 dihapus, dan `options.otherProblems === 0 &&` dihapus. Pada keempatnya seluruh 14 test `security-policy.test.ts` tetap lulus. Test GATE-007 yang memanggil `runSecurityScan` hanya mencapai jalur sinyal dan jalur checkout dangkal (di sana `bun audit` berhenti pada `bun_version_mismatch`), sehingga jalur `bun audit` yang benar benar berjalan tidak pernah dilalui dalam test.

**Why it matters**: AC-5 menyebut environment minimum tanpa `.env` dan kebijakan gagal yang tertulis. Fungsi pemetaan murni sudah diuji, tetapi pemasangannya tidak. Regresi diam diam pada baris 249 akan meneruskan variable environment proses gate (termasuk token bila suatu hari ada) ke proses yang berbicara dengan registry npm. Regresi pada baris 280, 346, atau 532 membuat file pengecualian yang rusak atau container pemindai yang tidak terhapus tetap lulus hijau, padahal kode dan komentarnya menjanjikan sebaliknya.

**Suggested fix**: Pisahkan pembentuk environment `bun audit` menjadi fungsi murni yang diekspor, seperti `containerArguments`, lalu uji bahwa variable di luar `PATH` dan `HOME` tidak ikut. Tambahkan test untuk `securityReport` dengan `otherProblems` lebih dari 0 yang harus berstatus `failed` walau ketiga pemindai `passed`. Untuk baris 280 dan 346, satu test `runSecurityScan` pada fixture dengan `exceptions.json` rusak dan `docker` palsu yang menolak `rm -f` cukup untuk mengunci keduanya.

### 🟡 Pencatatan `leftoverPorts` pada tier nyata tidak punya test otomatis, `scripts/lib/gate.ts:742`

**Problem**: AC-4 meminta gate mencatat listener yang masih tersisa pada port 8888 dan 8889 sesudah langkah tier nyata dihentikan karena batas waktu atau sinyal. Satu satunya bukti adalah langkah manual di `verify.md` (fixture dengan listener di 8888). Di salinan scratchpad, reviewer mengganti hasil `leftoverListeners` (baris 742, fungsi di baris 696) dengan `[]` dan seluruh 50 test `tier.test.ts` serta `report.test.ts` tetap lulus. Test hanya mengunci konstanta `LEFTOVER_PORTS` (`tier.test.ts:409`) dan nilai `leftoverPorts` kosong pada tier nyata yang berhasil.

**Why it matters**: Fungsi ini punya percabangan (hanya setelah langkah dihentikan, `listeners` yang melempar, PID unik dan terurut) dan satu satunya petunjuk bagi pengembang bahwa server tertinggal sesudah timeout atau sinyal. Bila rusak diam diam, manifest menyatakan bersih padahal port 8888 masih terpakai, dan run berikutnya gagal dengan alasan yang membingungkan.

**Suggested fix**: Jadikan daftar port yang diperiksa dapat disuntik lewat `RunTierOptions` (bawaannya tetap `LEFTOVER_PORTS`), sehingga test memakai port efemeral yang dibuka fixture tanpa menyentuh 8888 milik pengembang. Test itu menjalankan langkah yang timeout dengan listener di luar grup, lalu memeriksa PID di `leftoverPorts`, dan kasus langkah yang selesai sendiri tetap kosong.

### 🟡 Validator manifest lebih longgar daripada pembaca laporan, `scripts/lib/gate-report.ts:226`

**Problem**: `validManifest` memeriksa kandidat, langkah, dan bukti, tetapi tidak memeriksa `inputs`, `outputs`, maupun isi `environment`. Reviewer menyalin repository beserta bundle hasil run ke scratchpad lalu menghapus `inputs` dari manifest tier cepat yang selebihnya valid. `bun run test:report` berhenti dengan satu baris `Laporan gate tidak dapat disusun`, tanpa `report.json`, `report.md`, maupun ringkasan job, karena `checksumTable` (baris 756) membaca `values[path]` dari nilai `undefined`. Dengan `environment` berupa objek kosong, laporan tetap ditulis tetapi tabel tier memuat teks `undefined undefined, Bun undefined`. Mengembalikan `inputs` membuat laporan normal lagi.

**Why it matters**: Spec menyediakan kode `manifest_invalid` untuk manifest yang tidak dapat dipakai, dan laporan seharusnya menjadi `incomplete` dengan alasan itu. Artefak dari versi runner lain atau yang terpotong akan membuat job `report` gagal tanpa laporan, sehingga penyebabnya tidak terlihat di ringkasan job.

**Suggested fix**: Tambahkan pemeriksaan bentuk di `validManifest`: `inputs` berupa objek dengan nilai teks atau `null`, `outputs` berupa objek dengan nilai teks, serta `environment.os`, `arch`, dan `bun` berupa teks dan `node` teks atau `null`. Tambahkan satu kasus pada GATE-006 untuk manifest yang kehilangan `inputs` dan harus memberi `manifest_invalid`.

### 🟡 Tiga suite nyata yang diubah fitur ini belum punya gerbang tipe, `tsconfig.tooling.json:8`

**Problem**: `tsconfig.tooling.json` kini memeriksa seluruh file baru fitur ini, tetapi tiga dari empat suite nyata yang mendapat kode pembersihan sinyal tidak masuk tsconfig mana pun: `tests/integration/infrastructure/postgres.test.ts`, `tests/integration/database/provision.test.ts`, dan `tests/integration/database/migration.test.ts`. Hanya `tests/integration/database/readiness.test.ts` ada di `tsconfig.contract.json`. Bun membuang tipe tanpa memeriksanya. Reviewer menjalankan `tsc --noEmit` ad hoc pada ketiga file dengan opsi yang sama seperti `tsconfig.tooling.json` dan hasilnya exit 0, jadi tidak ada kesalahan tipe hari ini.

**Why it matters**: Kode baru di ketiga file itu memanggil `docker rm -f` dan `docker compose down` dari callback sinkron (argumen, tipe kembalian `string[]`, `Bun.spawnSync`). Kesalahan tipe pada pemanggil ini tidak gagal di gate mana pun, sementara pola yang sama sudah dicatat sebagai celah pada review fitur 10 dan 8.

**Suggested fix**: Tambahkan ketiga file itu ke `files` di `tsconfig.tooling.json` (opsi `types: ["bun"]` sudah sesuai) pada commit yang sama dengan perubahannya.

### 🟡 Tiga aturan kecil spec lolos dari mutasi, `scripts/lib/security-policy.ts:58`

**Problem**: Tiga cabang yang spec tuliskan tidak dibedakan test, dibuktikan dengan mutasi pada salinan scratchpad. (1) `security-policy.ts:58`, digest pada pin diubah dari tepat 64 heksadesimal menjadi 1 sampai 64: test pin tetap lulus karena tidak ada kasus digest pendek. (2) `security-policy.ts:250`, gitleaks dengan exit code selain 0 atau 2 dan array temuan tidak kosong diperlakukan sebagai temuan, bukan `not_run`: test pemetaan hanya mencoba exit 1 dengan keluaran kosong, jadi lolos. (3) `gate-report.ts:555`, field identitas PostgreSQL berupa string kosong diterima: spec meminta string tidak kosong, tetapi test hanya mencoba field yang hilang.

**Why it matters**: Ketiganya memperlonggar aturan yang spec tulis eksplisit (pin harus digest lengkap, kombinasi exit dan JSON lain harus `not_run`, identitas tidak boleh tampil sebagian). Dampak langsungnya kecil karena `docker pull` menolak digest pendek dan keduanya tetap menggagalkan tier, tetapi ketiganya adalah garis yang test GATE-006 dan GATE-007 seharusnya jaga.

**Suggested fix**: Tambahkan satu kasus per butir: pin dengan digest 63 karakter, `evaluateGitleaks({ code: 1, stdout: <array tidak kosong> })` yang harus `not_run` dengan `invalid_output`, dan `image.json` dengan satu field berupa string kosong yang harus membuat `postgres` bernilai `null`.

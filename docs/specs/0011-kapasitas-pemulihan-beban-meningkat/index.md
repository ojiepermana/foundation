# 0011. Kapasitas dan pemulihan saat beban meningkat

**Date**: 2026-10-04
**Status**: Accepted

## Summary

Anda mendapat pengujian kapasitas k6 yang dapat diulang untuk dua alur nyata yang ada sekarang, `GET /api/status` dan `GET /api/readiness`, dengan model beban, durasi, data, batas resource, dan target yang ditetapkan spec ini dari pengukuran awal di mesin ini ditambah margin. Setiap profil berjalan di environment Docker terisolasi (PostgreSQL 18, backend, dan k6 masing masing dalam container dengan batas CPU dan memory tetap), mencatat beban aktual, iterasi yang tidak sempat dimulai (dropped iterations), resource, dan pool database, lalu gagal bila satu threshold atau pengamatan tidak terpenuhi. Smoke berjalan pada setiap push sebagai langkah terakhir tier nyata gate CI; load, stress, spike, outage database, dan soak menjadi tier kapasitas terpisah yang dijalankan manual, lokal maupun lewat workflow GitHub. Angka ini berlaku untuk satu instance backend development dengan satu CPU, bukan perkiraan kapasitas produk, dan batas bukti itu tertulis di setiap hasil.

## Requirements

**User stories**:

- Sebagai pemilik proyek, Anda dapat menjalankan satu perintah per profil dan mendapat bukti apakah backend memenuhi target pada beban normal, di atas normal, lonjakan, durasi panjang, dan saat database berhenti lalu berjalan lagi.
- Sebagai pengembang, setiap push menjalankan smoke k6, sehingga script beban yang rusak atau perilaku dasar yang berubah langsung terlihat di gate.
- Sebagai pemilik release, Anda dapat membaca beban aktual, dropped iterations, resource, pool, dan batas environment pada laporan yang terikat ke commit yang sama, tanpa target yang dilonggarkan diam diam.

**Acceptance criteria**:

- **AC-1**: Model beban dan profil ditetapkan satu kali di modul murni `tests/performance/helpers/plan.ts` (tanpa impor apa pun) sesuai tabel *Model beban*, *Rencana fase*, dan *Thresholds*, lalu dipakai keenam profil `tests/performance/profiles/smoke.ts`, `load.ts`, `stress.ts`, `spike.ts`, `outage.ts`, dan `soak.ts` lewat `export const options = optionsFor('<profil>')`. Modelnya open model (laju kedatangan tetap): setiap iterasi tepat satu request, sehingga laju iterasi sama dengan request per detik, dan journey `status` serta `readiness` berjalan sebagai scenario terpisah. Beban normal N adalah 1.000 iterasi per detik untuk `status` dan 50 untuk `readiness`; beban lebih O adalah 4.000 dan 1.000. Setiap scenario menyiapkan seluruh VU nya sebelum T0, dengan `preAllocatedVUs` sama dengan `maxVUs` menurut paragraf *Alokasi VU*, sehingga k6 tidak pernah membuat VU baru selama fase berjalan. Setiap profil mengekspor tepat `options`, `setup`, `handleSummary`, `status`, dan `readiness`; scenario `status_*` memakai `exec` `status` dan scenario `readiness_*` memakai `exec` `readiness`. Script k6 hanya mengimpor modul bawaan `k6`, `k6/http`, `k6/metrics`, dan `k6/execution` serta file relatif `.ts` di `tests/performance/`, tanpa modul remote; `plan.ts` dan `expectations.ts` tidak mengimpor apa pun dan tidak memakai `__ENV`, `process`, atau `Bun`; kode tingkat modul tidak membaca `__ENV`, dan variable run hanya dibaca serta divalidasi di dalam `setup()` menurut paragraf *Bentuk profil dan variable run*, sehingga `k6 inspect` berjalan tanpa `--env`. PERF-001 memeriksa aturan impor ini dengan parser TypeScript. Langkah smoke menjalankan `k6 inspect --execution-requirements` atas keenam profil, dan scenario serta thresholds hasil inspect wajib cocok dengan `optionsFor(<profil>)` menurut baris *Pemeriksaan inspect*; selisih membuat smoke gagal dengan alasan `inspect_mismatch`.
- **AC-2**: Setiap run profil membuat environment sendiri menurut tabel *Topologi environment test* dan menghapusnya pada setiap jalur keluar: network Docker baru; PostgreSQL 18 dari `foundation-postgres:18-pinned` (dibangun dari `infrastructure/postgres/pins.json` bila belum ada atau label base nya berbeda), diprovision dan dimigrasi dengan `database/provision.ts` dan `database/migrate.ts` memakai credential acak; backend komposisi development dari `apps/backend/src/index.ts` di container `oven/bun:1.4.2-slim`; dan k6 dari `grafana/k6:2.3.0` yang berbagi network namespace backend. Image k6 dan Bun dipin tag beserta digest indeks di `tests/performance/images.json`, ditarik dengan digest sebelum dipakai, lalu dijalankan dengan `--pull never`; tag Bun wajib `<engines.bun>-slim`, sehingga versi Bun di container sama dengan `engines.bun`. Batas resource dan flag keamanan setiap container mengikuti tabel itu. Backend hanya mendengar di `127.0.0.1` di dalam namespace nya dan tidak dipublikasikan ke host; PostgreSQL hanya dipublikasikan ke port loopback acak untuk orkestrasi. Tidak ada file `.env`, credential production, atau PostgreSQL Compose bersama yang dipakai atau di mount; sebelum membuat apa pun, run gagal dengan alasan `env_file_present` bila ada file yang namanya diawali `.env` di bawah `apps/backend`, `libs`, atau `node_modules`. Sebelum membuat apa pun, run juga gagal dengan alasan `environment_too_small` bila mesin container melihat kurang dari 4 CPU atau kurang dari 4 GiB memory, dan dengan alasan `environment_busy` bila ada container lain berlabel `foundation.test` yang sedang berjalan; pemeriksaan `environment_busy` diulang sesudah k6 keluar. Bila UID host 0, folder keluaran k6 diserahkan ke 65534:65534 sebelum container k6 dibuat.
- **AC-3**: Setiap respons diperiksa menurut tabel *Klasifikasi respons*: status HTTP yang diizinkan per endpoint dan fase, body JSON dengan himpunan key yang tepat, `Cache-Control: no-store` pada readiness, `appliedMigrations` sama dengan jumlah file `database/migrations/*.sql`, serta `checkedAt` yang lulus `Date.parse` dan berakhiran `Z`. 429 `{"status":"busy"}` adalah penolakan yang diharapkan untuk readiness pada setiap fase, sedangkan 503 hanya diharapkan pada fase `stopping`, `outage`, dan `recovering` profil outage. `status` selalu wajib 200. Status lain, body yang tidak sesuai, atau kegagalan transport (status 0 atau timeout request 10 detik) menggagalkan check dan menambah counter `unexpected_responses`.
- **AC-4**: Thresholds setiap profil mengikuti tabel *Thresholds* dan dideklarasikan pada `options.thresholds`: `unexpected_responses` `count==0` dan `dropped_iterations` `count==0` (keduanya `abortOnFail` dengan `delayAbortEval` `5s`), `checks` `rate==1`, `iterations{scenario:<nama>}` untuk setiap scenario laju tetap minimal 99,9 persen dari rencana, tetapi tidak pernah lebih dari rencana dikurangi jumlah VU scenario itu (paragraf *Ambang beban aktual*), serta target latency dan ketersediaan readiness per fase. Threshold yang gagal membuat k6 keluar 99, orkestrasi keluar 1 dengan alasan `k6_thresholds_failed`, dan langkah gate gagal. Nilai target tidak dibaca dari environment, argumen, atau file lain, sehingga hanya dapat diubah lewat spec ini dan `plan.ts`.
- **AC-5**: `result.json` setiap profil mencatat, dari ringkasan `handleSummary`, laju rencana, jumlah iterasi rencana dan aktual, serta laju aktual setiap scenario (iterasi aktual dibagi detik rencana scenario dari `plan.ts`, bukan laju Counter k6 yang dibagi durasi seluruh test), total `iterations`, `http_reqs`, `dropped_iterations`, dan `vus_max`, serta latency dan jumlah per endpoint, fase, dan hasil dari submetrik yang dimunculkan kelompok Pencatatan pada tabel *Thresholds*; submetrik yang tidak ada di ringkasan dicatat dengan jumlah 0 dan statistik `null` menurut baris *Isi result.json*. `http_reqs.count` wajib sama dengan `iterations.count` (alasan `iteration_request_mismatch`), dan waktu mulai scenario dari `setup_data.startedAt` paling lambat 2.000 ms sesudah T0 (alasan `phase_start_late`). Generator ikut diamati: rata rata CPU container k6 pada setiap fase terukur paling banyak 80 persen dari batas CPU nya dan memory puncaknya paling banyak 80 persen dari batas memory nya; bila tidak, profil gagal dengan alasan `generator_saturated`, karena beban yang tidak dapat dibangkitkan tidak pernah dianggap terbukti.
- **AC-6**: Selama profil berjalan, orkestrasi mengambil sampel `docker stats` untuk container backend, PostgreSQL, dan k6, serta `pg_stat_activity` setiap 1.000 ms lewat koneksi admin, menulis `observation.json`, dan menilai setiap check pada tabel *Pengamatan resource*: backend tetap berjalan tanpa restart dan tanpa OOM; stderr backend kosong dan stdout hanya baris tetap; memory puncak backend paling banyak 128 MiB; rata rata CPU backend pada fase `steady` load dan soak paling banyak 50 persen dari satu CPU; pertumbuhan memory soak paling banyak 16 MiB; sesi `foundation_backend` tidak pernah lebih dari 5 (batas pool spec 0004) dan sesi `foundation_backend` yang tidak idle tidak pernah lebih dari 1 (satu pemeriksaan aktif spec 0006); cakupan sampel cukup; dan selisih jam container dengan host paling banyak 1.000 ms, diukur sebelum T0 dan lagi sesudah k6 keluar. Check yang gagal membuat profil gagal dengan alasan `observation_failed` beserta nama check nya, kecuali `generator_cpu` dan `generator_memory` yang memakai alasan `generator_saturated`.
- **AC-7**: Profil outage pada beban N menghentikan container PostgreSQL dengan `docker stop --time 10` pada T0 + 90 detik dan menjalankannya lagi dengan `docker start` pada T0 + 150 detik, masing masing hanya sesudah penjaga container lulus. Fase setiap request ditentukan dari waktu mulai request (jam k6) lewat `requestPhase`, dan batas fase berjarak dari kedua perintah menurut baris outage *Rencana fase*: `stopping` dimulai 2 detik sebelum stop terjadwal, `outage` berlangsung dari T0 + 101 sampai T0 + 145 detik, dan `recovering` dimulai 5 detik sebelum start terjadwal, sehingga keterlambatan perintah yang diizinkan, selisih jam yang diizinkan, dan `connectionTimeout` pool 3 detik tidak pernah membuat request di tepi fase dinilai pada fase yang salah. `status` tetap 200 dan memenuhi target latency normal pada setiap fase selain `warmup`. Readiness yang dimulai pada fase `outage` hanya menjawab 503 atau 429, setiap 503 pada fase `stopping`, `outage`, dan `recovering` tiba dalam kurang dari 5.500 ms dari sisi k6 (batas 5.000 ms spec 0006 ditambah margin transport), dan sedikitnya satu 503 terjadi pada fase `outage`. Mulai T0 + 160 detik (10 detik sesudah start), readiness kembali memenuhi target normal tanpa restart backend, dan pool kembali membuka sesi `foundation_backend`. Waktu pemulihan aktual (`readiness_recovery_ms`: jawaban 200 readiness pertama yang diterima pada atau sesudah T0 + 150.000 menurut jam k6, apa pun waktu kirimnya, dikurangi T0 + 150.000) dicatat di `result.json`. Perintah stop atau start yang dikirim sebelum jadwal atau lebih dari 1.000 ms sesudahnya, stop yang selesai lebih dari 8.000 ms, atau start yang selesai lebih dari 5.000 ms sesudah dikirim menggagalkan profil dengan alasan `outage_control_late`.
- **AC-8**: Pada stress dan spike, fase `hold` dan `spike` (beban O) wajib memenuhi target beban lebih: latency `status` dan readiness yang berhasil sama dengan target normal, 429 cepat (p95 di bawah 10 ms), dan sedikitnya 20 persen pemeriksaan readiness berhasil. Fase `recover` (stress) dan `after` (spike) dimulai 10 detik sesudah beban kembali ke N dan wajib memenuhi target normal yang sama dengan load, sehingga pemulihan sesudah beban terbukti dalam batas 10 detik.
- **AC-9**: Smoke (`test:performance:smoke`) menjadi langkah terakhir tier nyata `test:ci:real` pada setiap push, dan unit modul murni (`test:performance:plan`) menjadi langkah tier cepat `test:ci`. Load, stress, spike, outage, dan soak menjadi langkah tier baru `capacity` (`test:ci:capacity` = `bun --no-env-file scripts/gate.ts capacity`) dengan urutan, batas waktu, dan bukti pada tabel *Tier kapasitas*. Tier kapasitas tidak termasuk gate per push: `TIER_NAMES` tetap `fast`, `real`, dan `security`, `test:report` tidak menuntut bundle kapasitas, dan skenario yang semua check nya merujuk script tier kapasitas hanya dihitung `test:report:capacity`; `test:scenarios` menolak skenario yang mencampur script tier kapasitas dengan script tier lain. `test:report` menambah bagian performance dari `result.json` smoke dan memperbarui `outOfScope` menurut baris *Laporan per push*; `test:report:capacity` menulis `.local/feature-12/report.json` dan `.local/feature-12/report.md` dengan pengikatan dan kandidat release menurut baris *Laporan kapasitas*. Workflow baru `.github/workflows/capacity.yml` hanya dipicu `workflow_dispatch` dan menjalankan tier kapasitas lalu laporannya; `check:workflow` menerapkan daftar izin baris *Workflow kapasitas*, menolak file workflow selain `application.yml` dan `capacity.yml`, dan actionlint yang dipin lulus atas kedua file. Nama tipe, kode alasan, jenis bukti, entri `outOfScope`, field laporan kapasitas, isi kolom *Test dan profil*, dan test gate lama yang diubah mengikuti tabel *Perubahan gate yang dinamai*; test lama hanya ditambah harapan baru atau diganti pada nilai yang diubah spec ini, dan tidak pernah dilonggarkan. Registry `tests/scenarios/performance.json` memuat PERF-001 sampai PERF-009 menurut *Critical test scenarios*.
- **AC-10**: `result.json` memuat blok `environment` dan daftar `limits` menurut baris *Isi result.json*: OS dan arsitektur host, model serta jumlah CPU host, memory host, versi server mesin container (key `containerEngine`) beserta jumlah CPU dan memory yang dilihatnya, jumlah container lain yang berjalan (tanpa nama), tanda CI, image beserta digest, image id dan versi server PostgreSQL, batas resource setiap container, ukuran pool, dan jumlah migration. Laporan per push dan laporan kapasitas menampilkan batas itu bersama hasil dengan label netral ("mesin container"), sehingga kode sumber `scripts/` tetap lolos pola INFRA-001. Nilai credential acak tidak muncul di output k6, backend, provision, migrate, dan orkestrasi, maupun di `summary.json`, `result.json`, dan `observation.json`, yang dibuktikan `artifact-scan.json` tanpa temuan; setiap baris yang dicetak orkestrasi melewati fungsi redaksi atas semua credential run, dan output mentah perintah tidak pernah dicetak. Dokumen pada baris *Dokumen yang diperbarui* menyebut profil, script, tier, pin, dan lokasi bukti baru.

## Decision

**Chosen option**: Opsi 1, k6 dari image yang dipin dengan seluruh komponen di dalam container berbatas resource, k6 berbagi network namespace backend, smoke di tier nyata per push, dan profil panjang di tier kapasitas manual yang memakai runner gate yang sama.

Spec ini tidak mengubah kode aplikasi, schema, migration, grant, atau variable environment aplikasi. Yang ditambahkan adalah script k6 di `tests/performance/`, orkestrasi di `tests/orchestration/performance-real.ts`, perluasan gate spec 0010 (satu langkah tier nyata, satu langkah tier cepat, tier `capacity`, dua jenis bukti, bagian laporan, dan laporan kapasitas), serta workflow manual `capacity.yml`. Pilihan kedua adalah backend sebagai proses host seperti `serve` dengan k6 container yang menjangkau host lewat `--network host` di Linux dan `host.docker.internal` di macOS; itu lebih dekat ke cara pengembang menjalankan backend, tetapi jalur yang diukur berbeda antara macOS dan Linux, backend tidak berbatas CPU, dan port host ikut dipakai (rationale, Opsi 2).

**Implementation skills**: Tidak ada skill komunitas yang membentuk keputusan ini; tidak ada skill k6 terpasang. Aturan proyek testing, keamanan, database, infrastruktur, dan workflow development tetap mengikat implementasi, dan perubahan gate mengikuti spec 0010.

**Model beban** (konstanta `LOADS` di `plan.ts`; satu iterasi sama dengan satu request):

| Beban | `status` (iterasi per detik) | `readiness` (iterasi per detik) | Request per detik | Dasar |
| --- | --- | --- | --- | --- |
| S0 smoke | 100 | 10 | 110 | sepersepuluh N, cukup untuk memvalidasi script dan perilaku dasar |
| N normal | 1.000 | 50 | 1.050 | status memakai sekitar 10 sampai 14 persen satu CPU pada baseline; readiness sekitar 5 persen throughput pemeriksaan terukur, sehingga 429 jarang terjadi |
| O beban lebih | 4.000 | 1.000 | 5.000 | 4 kali N untuk status dan 20 kali N untuk readiness, di atas throughput pemeriksaan sehingga penolakan 429 pasti terjadi; total tetap dalam anggaran generator k6 tiga CPU |

**Rencana fase** (konstanta `PROFILES`; nama scenario `<endpoint>_<fase>` dengan endpoint `status` atau `readiness`; scenario fase berikutnya memakai `startTime` sama dengan jumlah durasi fase sebelumnya):

| Profil | Fase berurutan (bentuk, durasi, beban) | Total | Tier |
| --- | --- | --- | --- |
| smoke | `warmup` tetap 10 s S0 · `steady` tetap 30 s S0 | 40 s | nyata, setiap push |
| load | `warmup` naik 60 s dari 0 ke N · `steady` tetap 600 s N | 660 s | kapasitas |
| stress | `warmup` naik 60 s dari 0 ke N · `ramp` naik 120 s dari N ke O · `hold` tetap 300 s O · `rampdown` turun 60 s dari O ke N · `settle` tetap 10 s N · `recover` tetap 180 s N | 730 s | kapasitas |
| spike | `warmup` naik 60 s dari 0 ke N · `before` tetap 120 s N · `rise` naik 5 s dari N ke O · `spike` tetap 60 s O · `fall` turun 5 s dari O ke N · `settle` tetap 10 s N · `after` tetap 180 s N | 440 s | kapasitas |
| outage | satu scenario tetap 220 s N per endpoint (`status_timeline`, `readiness_timeline`); fase dari waktu mulai request sejak T0 lewat `phaseAt`: `warmup` 0 sampai 30 s · `before` 30 sampai 88 s · `stopping` 88 sampai 101 s · `outage` 101 sampai 145 s · `recovering` 145 sampai 160 s · `after` 160 sampai 220 s; stop terjadwal pada 90 s dan start pada 150 s | 220 s | kapasitas |
| soak | `warmup` naik 60 s dari 0 ke N · `steady` tetap 3.600 s N | 3.660 s | kapasitas |

Setiap fase tetap memakai executor `constant-arrival-rate` dan setiap fase naik atau turun memakai `ramping-arrival-rate` dengan `startRate` sama dengan laju fase sebelumnya (0 untuk `warmup`) dan satu stage menuju laju target. Semua scenario memakai `timeUnit` `1s`, `gracefulStop` `6s` (di atas batas jawaban 5.000 ms readiness), serta `preAllocatedVUs` dan `maxVUs` yang bernilai sama menurut paragraf *Alokasi VU* di bawah. Setiap scenario `status_*` memakai `exec` `status` dan setiap scenario `readiness_*` memakai `exec` `readiness`. `options` juga berisi `setupTimeout` `60s`, `summaryTrendStats` `['avg', 'min', 'med', 'max', 'p(50)', 'p(95)', 'p(99)', 'count']`, dan `discardResponseBodies` `false`. Request memakai `timeout` `10s`.

**Alokasi VU** (diperbarui 2026-10-04 sesudah run pertama langkah 4; konstanta `VU_HEADROOM_MS` 100 dan fungsi `scenarioVUs(rate)` di `plan.ts`, yang menggantikan `preAllocatedVUs` dan `maxVUs` lama): setiap scenario mendapat `preAllocatedVUs` = `maxVUs` = `scenarioVUs(laju)` = max(10, ceil(laju × `VU_HEADROOM_MS` / 1.000)), dihitung dengan bilangan bulat, dengan laju = nilai terbesar dari laju awal dan laju target fase itu. VU (virtual user, pelaksana iterasi k6) disiapkan untuk 100 ms kedatangan sekaligus, dan k6 membuat semuanya sebelum `setup()`, jadi sebelum T0. Alasannya perilaku k6 2.3.0 yang terukur: executor laju kedatangan menjatuhkan iterasi begitu tidak ada VU yang sudah dibuat dan sedang bebas, walau `maxVUs` belum tercapai, lalu baru membuat VU tambahan satu per satu di latar belakang. VU di atas `preAllocatedVUs` karena itu tidak pernah mencegah iterasi pertama yang dijatuhkan, padahal satu iterasi yang dijatuhkan sudah menggagalkan run lewat `dropped_iterations` `count==0`; VU itu hanya menambah memory yang bergantung pada jeda yang tidak dapat diperkirakan. Dengan alokasi penuh, iterasi dijatuhkan hanya bila lebih dari laju × 0,1 iterasi satu scenario berjalan bersamaan, yaitu bila satu jeda (latency backend, jeda generator, atau jeda penjadwalan mesin container) menahan kedatangan sekitar 100 ms dikurangi waktu request biasa; scenario yang memakai batas bawah 10 VU mendapat ruang lebih panjang (readiness pada N 200 ms, smoke `status` 100 ms, smoke readiness 1 detik). Jumlah VU setiap scenario:

| Laju scenario | `status` | `readiness` |
| --- | --- | --- |
| S0 (100 dan 10 per detik) | 10 | 10 |
| N, termasuk `warmup` yang naik dari 0 ke N (1.000 dan 50 per detik) | 100 | 10 |

**Bentuk profil dan variable run**: setiap file profil berbentuk sama, yaitu impor relatif `optionsFor` dari `../helpers/plan.ts`, `setupRun` dan `writeSummary` dari `../helpers/lifecycle.ts`, serta kedua journey, lalu `export const options = optionsFor('<profil>')`, `export function setup() { return setupRun(); }`, `export function handleSummary(data) { return writeSummary(data); }`, serta `export function status(data)` dan `export function readiness(data)` yang memanggil journey dengan data setup. `setupRun()` di `lifecycle.ts` membaca `__ENV.FOUNDATION_PERF_T0` dan `__ENV.FOUNDATION_PERF_EXPECTED_MIGRATIONS`, memvalidasinya dengan `parseRunEnv` (T0 bilangan bulat positif dalam epoch ms, jumlah migration bilangan bulat 0 atau lebih), menunggu sampai T0, lalu mengembalikan `{ startedAt: Date.now(), t0, expectedMigrations }`; nilai yang tidak sah membuat `setup()` melempar galat, k6 keluar dengan exit code bukan 0 dan bukan 99 (diharapkan 107 untuk galat script, dibuktikan probe langkah 1), dan orkestrasi mencatat `k6_failed` dengan exit code itu. Journey membaca T0 dan jumlah migration hanya dari data setup, sehingga fase k6 dan jendela pengamatan orkestrasi memakai titik nol yang sama, dan `k6 inspect` yang hanya mengevaluasi kode tingkat modul tidak membutuhkan variable apa pun. `writeSummary(data)` mengembalikan tepat `{ '/out/summary.json': JSON.stringify(data), stdout: '<baris tetap>\n' }`.

Batas fase outage ditetapkan dari jarak terburuk yang diizinkan spec ini: selisih jam k6 dengan host paling banyak 1.000 ms (check `clock_offset`), stop dan start dikirim tidak lebih awal dari jadwal dan paling lambat 1.000 ms sesudahnya, stop selesai paling lama 8.000 ms sesudah dikirim, dan satu pemeriksaan readiness dapat menunggu koneksi pool paling lama 3.000 ms lalu berhasil bila database kembali sebelum batas itu. `stopping` dimulai 2.000 ms sebelum stop terjadwal (selisih jam 1.000 ditambah margin 1.000), sehingga request yang dimulai pada `before` selesai sebelum database disentuh. `outage` dimulai 11.000 ms sesudah stop terjadwal (keterlambatan 1.000, penyelesaian 8.000, selisih jam 1.000, margin 1.000), sehingga request yang dimulai pada `outage` selalu bertemu database yang sudah berhenti. `outage` berakhir 5.000 ms sebelum start terjadwal (selisih jam 1.000, `connectionTimeout` 3.000, margin 1.000), sehingga pemeriksaan yang dimulai pada `outage` tidak pernah dapat menjawab 200; pemeriksaan yang dimulai sebelum start dan selesai sesudahnya dinilai pada `recovering`, yang mengizinkan 200, 429, dan 503. `after` tetap dimulai 10.000 ms sesudah start terjadwal. Pada profil lain fase sama dengan bagian nama scenario sesudah garis bawah pertama.

Satuan latency adalah milidetik (`res.timings.duration`, yaitu waktu kirim, tunggu, dan terima). Fase `warmup`, `ramp`, `rampdown`, `rise`, `fall`, dan `settle` hanya diikat ambang umum dan klasifikasi respons, bukan target latency. Ekspresi Pencatatan dan `count>=0` beban aktual selalu lulus; gunanya hanya membuat submetrik muncul di ringkasan `handleSummary`, karena k6 hanya membuat submetrik yang dirujuk threshold. Probe langkah 1 Build plan membuktikan bahwa threshold atas submetrik tanpa sampel tidak menggagalkan run (trend kosong dibaca 0) dan bahwa `summaryTrendStats` menerima `count`; bila salah satunya tidak berlaku pada k6 2.3.0, implementasi berhenti dan kembali ke `/architect`.

**Ambang beban aktual** (diperbarui 2026-10-04 sesudah review, keputusan agent atas delegasi pemilik; rationale, *Ambang beban aktual 2026-10-04*): `iterationFloor(laju, detik)` di `plan.ts` adalah nilai terkecil dari floor(0,999 × laju × detik) dan laju × detik − `scenarioVUs(laju)`, dihitung dengan bilangan bulat dan tidak pernah di bawah 0. Alasannya perilaku k6 2.3.0 yang terukur pada run pertama tier kapasitas: executor laju tetap berhenti tepat di akhir durasinya, dan iterasi yang masih tertunda pada saat itu tidak dimulai dan tidak dihitung sebagai dropped iterations, sehingga jeda generator di akhir scenario mengurangi jumlah iterasi sebanyak kedatangan selama jeda itu (spike `status_settle` 9.986 dari 10.000 tanpa dropped iterations, sekitar 14 ms pada 1.000 per detik). VU scenario itu menyerap jeda yang sama di tengah scenario tanpa iterasi yang dijatuhkan (paragraf *Alokasi VU*), jadi akhir scenario mendapat ruang yang sama: jeda yang lebih panjang tetap gagal, di tengah scenario lewat `dropped_iterations` dan di akhir lewat ambang ini. Scenario panjang tetap memakai 99,9 persen karena 0,1 persen rencananya lebih besar dari jumlah VU nya. Ambang yang berubah: smoke `status_warmup` 990, `readiness_warmup` 90, `status_steady` 2.990, dan `readiness_steady` 290; `status_settle` 9.900 dan `readiness_settle` 490 pada stress dan spike; stress `readiness_recover` dan spike `readiness_after` 8.990; spike `readiness_before` 5.990, `status_spike` 239.600, dan `readiness_spike` 59.900. Ambang load, outage, soak, stress `hold`, stress `status_recover`, serta spike `status_before` dan `status_after` tidak berubah. `dropped_iterations` `count==0`, `http_reqs` sama dengan `iterations`, beban, dan target lain tidak berubah.

Setiap request membawa tag `endpoint` dan `phase`. `phase` dihitung satu kali sebelum request dikirim dengan `requestPhase(profile, exec.scenario.name, Date.now(), t0)`: pada profil selain outage hasilnya bagian nama scenario sesudah garis bawah pertama, pada outage `phaseAt(startedAtMs - t0)`. **Klasifikasi respons** (`classify`, satu satunya sumber keputusan check):

| Endpoint | Fase | Status diizinkan | Body dan header yang wajib |
| --- | --- | --- | --- |
| `status` | semua | 200 | JSON dengan tepat satu key, `{"status":"ok"}` |

Check k6 diberi nama tetap `<endpoint> response matches the expected outcome` dan lulus bila hasilnya bukan `rejected`. `metricUpdates` memetakan hasil ke metrik khusus: `rejected` menambah `unexpected_responses` 1 dengan tag `endpoint` dan `phase`; `available` menambah `readiness_available` `true` dan durasi ke `readiness_available_duration`; `busy` menambah `readiness_available` `false` dan durasi ke `readiness_busy_duration`; `unavailable` menambah `readiness_available` `false`, `readiness_unavailable` 1, dan durasi ke `readiness_unavailable_duration`, masing masing dengan tag `phase`; `ok` tidak menambah metrik khusus.

**Urutan orkestrasi** (`bun --no-env-file tests/orchestration/performance-real.ts <profil>`; fungsi murni diekspor, run hanya bila `import.meta.main`):

1. Validasi argumen profil (pemeriksaan sebelum run (1)) sebelum aksi lain apa pun. Sesudah lolos, pasang handler SIGINT, SIGTERM, dan SIGHUP yang membatalkan langkah berjalan dan menuju pembersihan, lalu hapus `.local/feature-12/<profil>/` dan buat lagi beserta subfolder `k6/` (diserahkan ke 65534:65534 bila UID host 0).
2. Pemeriksaan sebelum run (2) sampai (7). Pada smoke, jalankan k6 inspect untuk keenam profil dan bandingkan menurut baris *Pemeriksaan inspect*.
3. Buat folder `mkdtemp`, env file, network, dan container PostgreSQL; tunggu `SELECT 1` admin berhasil paling lama 30 detik; jalankan `database/provision.ts --apply` dan `database/migrate.ts --apply` di host dengan environment daftar izin seperti `tests/orchestration/readiness-real.ts`; hitung `database/migrations/*.sql`. Kegagalan pada langkah ini dicatat `setup_failed` dengan detail nama langkah dari kosakata baris *Kode alasan*.
4. Jalankan backend; poll setiap 250 ms paling lama 60 detik lewat `docker exec <backend> bun --no-env-file -e <script tetap>` sampai `/api/status` menjawab 200 dan `/api/readiness` menjawab 200 dengan jumlah migration yang diharapkan (selain itu `backend_not_ready`); ukur selisih jam pertama.
5. Tetapkan T0 = waktu host + `T0_DELAY_MS` (15.000 ms) lebih dulu, lalu `docker create` k6 dengan `--env FOUNDATION_PERF_T0=<T0>`, mulai aliran `docker stats --format '{{json .}}'` untuk ketiga container dan sampler `pg_stat_activity` (keduanya wajib sudah berjalan sebelum T0), lalu segera `docker start -a` k6 dengan batas waktu baris *Batas waktu perintah*. Waktu `docker create`, start aliran, dan start k6 diserap jeda 15 detik itu; `setup()` k6 menunggu sampai T0, dan check `phase_start_late` menangkap keterlambatan di atas 2.000 ms. Pada outage, kirim stop dan start sesuai jadwal di samping k6, masing masing tidak lebih awal dari jadwal menurut jam host.
6. Sesudah k6 keluar: hentikan aliran dan sampler, ulangi pemeriksaan `environment_busy`, ukur selisih jam kedua, baca keadaan backend dengan `docker container inspect --format '{{json .State.Running}} {{json .RestartCount}} {{json .State.OOMKilled}}'` (tidak pernah tanpa `--format`, karena `Config.Env` memuat `DATABASE_URL`), hentikan backend dengan `docker stop --time 5`, baca `docker logs` (stdout dan stderr terpisah), lalu nilai ringkasan dan pengamatan.
7. Pembersihan pada setiap jalur keluar, berurutan dan masing masing lewat penjaga dengan batas baris *Batas waktu perintah*: pembatalan perintah yang sedang berjalan bila ada sinyal (paling lama 10 detik), penghentian aliran dan sampler (paling lama 5 detik), k6 (`docker stop --time 10` bila masih berjalan, lalu `docker rm -f`), backend, PostgreSQL, dan container inspect (`docker rm -f`; container inspect biasanya sudah hilang karena `--rm` dan dilewati sesudah inspect penjaga menjawab tidak ada), network (`docker network rm`), lalu folder `mkdtemp`. Total terburuk 10 + 5 + (10 + 15) + 4 × (10 + 15) + (10 + 15) = 165 detik, di bawah masa tenggang 180 detik tier nyata dan tier kapasitas. Resource yang gagal dihapus dicatat `cleanup_failed` dengan nama resource milik run itu.
8. Susun `observation.json` dan `result.json` di memori, pindai output perintah yang ditangkap, `summary.json`, dan kedua teks itu untuk nilai credential sebelum redaksi, lalu ganti setiap nilai credential run dengan `[redacted]` sebelum kedua teks itu ditulis (diperbarui 2026-10-04 sesudah review: pemindaian sesudah redaksi tidak pernah dapat menemukan credential pada kedua teks itu). Temuan apa pun membuat `status` `failed` dengan alasan `secret_in_output` (detail jumlah temuan). Tulis `observation.json`, `result.json`, lalu `artifact-scan.json`. Bila `summary.json` tidak ada atau tidak dapat dibaca (k6 gagal atau melewati batas waktu), `actual`, `latency`, `readiness`, dan `thresholds` bernilai `null` dan alasan memuat `summary_missing` di samping `k6_failed` atau `k6_timeout`.
9. Exit 0 hanya bila `result.json` berstatus `passed`, pemindaian tanpa temuan, dan pembersihan lengkap; 1 untuk kegagalan lain; 2 untuk argumen profil yang tidak dikenal; 130, 143, atau 129 untuk SIGINT, SIGTERM, atau SIGHUP.

Konsol orkestrasi hanya mencetak baris tetap, kode alasan, nama resource milik run, dan nilai terukur; output mentah Docker, backend, provision, migrate, dan k6 tidak pernah dicetak, dan setiap baris yang dicetak melewati fungsi `redacted()` atas semua credential run, seperti `readiness-real.ts`. Seluruh langkah dijalankan fungsi `runProfile(profile, deps)` yang diekspor; `deps` berisi `root`, pemanggil perintah (`runProcessGroup` atau tiruan), `provision`, `migrate`, jam, `sleep`, dan `AbortSignal`, serta `chown` opsional untuk folder keluaran k6 pada UID host 0 (bawaan `chown` dari `node:fs`). Fungsi `main({ root, argv })` yang juga diekspor memvalidasi argumen, memasang handler sinyal, menyambungkan `deps` nyata, menjalankan `runProfile`, dan mengembalikan exit code; bagian `import.meta.main` hanya memanggil `main` dengan root checkout, seperti `runSecurityScan({ root })` pada `security-scan.ts`. Dengan begitu PERF-009 dapat menghentikan run pada setiap keadaan tanpa Docker dan tanpa menyentuh `.local/feature-12/` milik checkout.

**Pemeriksaan inspect** (smoke): untuk setiap profil, keluaran JSON `k6 inspect --execution-requirements` wajib memuat setiap scenario `optionsFor(<profil>)` dengan nama yang sama dan setiap field yang dideklarasikan `optionsFor` (`executor`, `exec`, `rate` atau `startRate`, `stages`, `duration`, `startTime`, `timeUnit`, `preAllocatedVUs`, `maxVUs`, `gracefulStop`) bernilai sama setelah dinormalisasi, tanpa scenario tambahan; himpunan key `thresholds` dan daftar ekspresi setiap key wajib sama persis setelah dinormalisasi. Field yang diisi default oleh k6 tidak dinilai. Normalisasi (fungsi murni `normalizeInspect` di `performance-real.ts`): durasi berbentuk string durasi Go (satu atau lebih pasangan angka desimal dan satuan `h`, `m`, `s`, `ms`, `us`, `µs`, atau `ns`, misalnya `1m0s` atau `1.5s`) atau string pendek `optionsFor` (`10s`) dikonversi ke milidetik bilangan bulat; `startTime` yang tidak ada atau `null` bernilai 0; setiap butir threshold, baik string ekspresi maupun objek `{ threshold, abortOnFail, delayAbortEval }`, menjadi `{ expression, abortOnFail, delayAbortEvalMs }` dengan `abortOnFail` `false` dan `delayAbortEvalMs` 0 bila tidak ada; key lain dengan nama berbeda untuk nilai yang sama ditolak sebagai `inspect_mismatch`, bukan ditebak. Bentuk ini dibuktikan terhadap keluaran `k6 inspect` nyata keenam profil yang ditangkap pada langkah 1 Build plan dan disimpan sebagai fixture PERF-001; bila keluaran nyata tidak memuat scenario atau thresholds, implementasi berhenti dan kembali ke `/architect`.

| Check | Profil | Aturan lulus |
| --- | --- | --- |

| `backend_memory_peak` | semua | memory backend maksimum paling banyak 128 MiB |
| `backend_cpu_mean` | load, soak | rata rata CPU backend pada fase `steady` paling banyak 50 (persen satu CPU) |
| `backend_memory_growth` | soak | rata rata memory pada 600 detik terakhir `steady` dikurangi rata rata detik ke 300 sampai 900 `steady` paling banyak 16 MiB |
| `pool_sessions` | semua | setiap sampel `pg_stat_activity` yang berhasil mencatat paling banyak 5 sesi `foundation_backend` |
| `pool_non_idle` | semua | setiap sampel yang berhasil mencatat paling banyak 1 sesi `foundation_backend` dengan `state` terisi dan bukan `idle` (sesi yang masih tersambung tanpa `state` tidak dihitung) |

Check `generator_cpu` dan `generator_memory` yang gagal dicatat `generator_saturated` dengan nama check sebagai detail; check lain yang gagal dicatat `observation_failed` dengan nama check sebagai detail.

Aliran `docker stats` berjalan lewat `runProcessGroup` dengan `onOutput`: setiap potongan output diberi waktu host saat potongan itu tiba (`receivedAtMs`), potongan dipecah per baris dengan sisa baris yang belum lengkap disimpan untuk potongan berikutnya, dan setiap baris lengkap memakai waktu potongan tempat baris itu selesai. Karakter kontrol terminal dibuang, `CPUPerc` dibaca sebagai persen satu CPU, dan bagian pertama `MemUsage` dikonversi ke MiB dari satuan B, KiB, MiB, atau GiB; nilai yang bukan angka (misalnya `--` untuk container yang berhenti) dicatat `null`. Paling banyak 4 sampel per container per detik disimpan; baris tambahan pada detik yang sama dibuang, sehingga ukuran `observation.json` terbatas. Aliran yang berhenti sebelum k6 selesai dijalankan ulang menurut baris *Batas waktu perintah*, dan celahnya dinilai check `observation_coverage`. Sampler `pg_stat_activity` mengambil satu sampel setiap 1.000 ms tanpa tumpang tindih (sampel berikutnya menunggu sampel sebelumnya selesai), memakai satu instance `Bun.SQL` admin dengan `max` 1 dan `connectionTimeout` 1 detik, dan membatasi setiap sampel 2.000 ms; sesudah sampel yang gagal atau melewati batas, instance itu ditutup dan instance baru dibuat untuk sampel berikutnya, sehingga koneksi lama yang putus karena PostgreSQL dihentikan tidak terbawa ke fase `after`. Query tetapnya `SELECT count(*) FILTER (WHERE usename = 'foundation_backend')::int AS sessions, count(*) FILTER (WHERE usename = 'foundation_backend' AND state <> 'idle')::int AS non_idle, count(*)::int AS total FROM pg_catalog.pg_stat_activity WHERE backend_type = 'client backend'`; sampel yang gagal dicatat `{ t, unavailable: true }`.

**Isi result.json** (`schema` 1; teks bebas dipotong 200 karakter):

| Field | Isi |
| --- | --- |
| `profile`, `status`, `reasons` | nama profil; `passed` atau `failed`; daftar `{ code, detail }` berurutan menurut kejadian, dengan `code` dan arti `detail` dari tabel *Kode alasan* di bawah |
| `startedAt`, `finishedAt`, `t0` | waktu ISO UTC dan T0 dalam epoch ms |
| `model` | beban (S0, N, atau O per fase), fase berurutan dengan bentuk, durasi, dan laju per endpoint, serta `iterationIsOneRequest: true` |
| `actual` | `scenarios`: per scenario `{ name, endpoint, phase, executor, startRate, endRate, seconds, plannedIterations, iterations, rate }`, dengan `startRate` dan `endRate` dari `plan.ts` (sama untuk scenario tetap), `seconds` durasi rencana, `plannedIterations` = laju × detik untuk scenario tetap atau (laju awal + laju akhir) / 2 × detik untuk scenario naik atau turun, `iterations` = `count` submetrik `iterations{scenario:<nama>}`, dan `rate` = `iterations` / `seconds`; serta `iterations`, `httpReqs`, `droppedIterations` (`count` metrik masing masing), `vusMax` (`value` metrik `vus_max`), dan `scenarioStartLateMs`. | `latency` | daftar `{ endpoint, phase, outcome, count, p50, p95, p99, max }` untuk setiap fase profil, dengan baris `status` `all` dari `http_req_duration{endpoint:status,phase:P}` (semua respons status; pada run yang lulus semuanya 200) serta baris `readiness` `available`, `busy`, dan `unavailable` dari `readiness_<hasil>_duration{phase:P}`; `count` dari statistik `count`, sisanya dari `p(50)`, `p(95)`, `p(99)`, dan `max`. Submetrik yang tidak ada atau dengan `count` 0 dicatat `count` 0 dan statistik `null`; `null` bila `summary.json` tidak ada |
| `readiness` | `{ phases, recoveryMs }`: `phases` daftar `{ phase, available, busy, unavailable, availableRatio }` dengan ketiga jumlah dari statistik `count` trend durasi hasil yang sama dan `availableRatio` = `available` / jumlah ketiganya (`null` bila jumlahnya 0); `recoveryMs` = `min` metrik `readiness_recovery_ms` untuk outage, `null` bila tidak ada sampel atau profil lain; seluruh `readiness` bernilai `null` bila `summary.json` tidak ada |
| `thresholds` | setiap `{ metric, expression, ok }` dari ringkasan, termasuk ekspresi Pencatatan; `null` bila `summary.json` tidak ada |
| `observation` | per container rata rata dan maksimum CPU serta memory, `memoryGrowthMiB` (soak) atau `null`, `restarts`, `oomKilled`, `stderrBytes`; untuk pool maksimum `sessions`, `nonIdle`, dan `total` serta jumlah sampel berhasil dan gagal; daftar check pengamatan `{ name, rule, actual, ok }` |
| `outage` | untuk outage `{ stopPlannedMs, stopIssuedMs, stopCompletedMs, startPlannedMs, startIssuedMs, startCompletedMs }` relatif T0; selain itu `null` |
| `environment` | `os`, `arch`, `cpuModel`, `cpuCount`, `memoryBytes` dari `node:os`; `containerEngine` `{ serverVersion, os, ncpu, memTotal }`; `otherContainersRunning` (jumlah saja); `ci` (benar bila variable `CI` ada); `images` `{ k6, bun, postgres: { image, imageId, baseImage, serverVersion } }`; `limits` per container sesuai tabel topologi; `pool` `{ max: 5, connectionTimeoutSeconds: 3 }`; `data` `{ appliedMigrations }`; `clockOffsetMs` `{ before, after }` (`after` bernilai `null` bila k6 tidak pernah berjalan) |
| `limits` | kalimat tetap baris *Batas bukti*, dengan jumlah migration terisi |

**Batas bukti** (ditulis apa adanya di `result.json` dan ditampilkan kedua laporan):

1. Alur yang diukur adalah diagnostik komposisi development, `GET /api/status` dan `GET /api/readiness`; komposisi production tidak memasang route apa pun dan belum ada endpoint bisnis.
2. Backend berjalan sebagai satu container dengan 1 CPU dan 512 MiB dari image Bun slim dengan source yang di mount, bukan image deployment fitur 13.
3. k6 dan backend berbagi network namespace loopback; tidak ada reverse proxy, TLS, atau latency jaringan nyata.
4. Data hanya riwayat migration (`<n>` baris); tidak ada tabel bisnis.
5. Mesin dipakai bersama (Docker Desktop di macOS bersama container lain, atau runner GitHub hosted); hasil hanya sebanding dengan run pada kelas environment yang sama.
6. Batas kapasitas (breakpoint) tidak dicari; hasil membuktikan beban yang disepakati, bukan titik jenuh.

**State transitions**:

- Run profil: `preparing` (pemeriksaan, image, environment) → `running` (fase berurutan) → `evaluating` → `passed` atau `failed`; pembersihan selalu berjalan sesudahnya. - Tier kapasitas: langkah berurutan dengan semantik spec 0010; langkah gagal membuat sisa langkah `not_run`.

**Key invariants**:

1. Target hanya ada di `plan.ts` dan tabel spec ini; tidak ada variable environment, argumen, atau file yang dapat mengubah laju, durasi, atau threshold. Dua variable run k6 hanya membawa T0 dan jumlah migration, dibaca hanya di `setupRun()`, dan tidak pernah dibaca kode tingkat modul.
2. Setiap run profil mempunyai network, PostgreSQL, backend, dan k6 sendiri; tidak ada yang dipakai bersama antarprofil, dengan `serve`, atau dengan PostgreSQL Compose.
3. Open model dengan satu request per iterasi; iterasi yang dijatuhkan menggagalkan run, dan generator yang jenuh tidak pernah menghasilkan lulus. Setiap scenario mempunyai `preAllocatedVUs` sama dengan `maxVUs`, sehingga seluruh VU dibuat sebelum T0 dan memory VU tidak bergantung pada jeda selama run.
4. Aksi Docker yang mengubah atau menghapus resource hanya berlaku pada nama yang dibuat run ini dan lolos penjaga container.
5. Backend memakai kode aplikasi apa adanya dalam komposisi development; fitur ini tidak mengubah kode di `apps/`, `libs/`, atau `database/`.
6. Credential acak tidak pernah dicetak; env file mode 0600 berada di folder `mkdtemp` yang dihapus pada setiap jalur keluar; output dan bukti dipindai.
7. Script k6 hanya mengimpor `k6`, `k6/http`, `k6/metrics`, `k6/execution`, dan file relatif `.ts` di `tests/performance/`; laporan pemakaian k6 dimatikan; modul `plan.ts` dan `expectations.ts` tanpa impor dan tanpa `__ENV`, `process`, atau `Bun`, sehingga dapat dipakai k6 dan Bun; PERF-001 memeriksa aturan ini dari source.

9. Fase setiap request ditentukan dari waktu mulai request, dan batas fase outage berjarak dari kedua perintah sejauh keterlambatan, selisih jam, dan `connectionTimeout` yang diizinkan.

**Security model**: Pelakunya pengembang lokal, job GitHub Actions per push (smoke), dan pengguna dengan hak tulis repository yang memicu `workflow_dispatch` (profil kapasitas); artifact repository publik dapat diunduh siapa pun. Seluruh beban hanya diarahkan ke backend milik run di `127.0.0.1` dalam namespace container nya; target lain tidak dapat dipilih karena URL dasar adalah konstanta. Backend memakai role `foundation_backend` dengan hak minimum spec 0004 lewat route yang tidak berubah, migration memakai role migrator, dan provisioning memakai admin container sementara; tidak ada credential production atau secret GitHub, dan workflow kapasitas hanya `contents: read` dengan checkout tanpa credential tersimpan. Container backend, k6, dan inspect berjalan read only, user non root, tanpa capability, `no-new-privileges`, dan dengan batas proses, memory, serta CPU; container PostgreSQL sama kecuali read only, karena `PGDATA` berada di lapisan tulis container, dan image nya berjalan sebagai `USER postgres`; backend tidak dipublikasikan, PostgreSQL hanya di loopback, dan mount backend dibatasi pada `apps/backend`, `libs`, `node_modules`, dan `package.json`, sehingga file `.env` tidak terlihat container. Image dipin digest indeks dan ditarik sebelum `--pull never`. k6 tidak memuat modul remote dan telemetri pemakaian k6 dimatikan. Jaringan keluar tidak diblokir: network run adalah bridge biasa (network internal akan memutus port loopback PostgreSQL yang dipakai orkestrasi), sehingga namespace backend yang dipakai bersama k6 tetap dapat menjangkau internet; tidak ada kode yang mengirim data run keluar, dan URL target adalah konstanta. Artifact hanya berisi bundle bukti dan laporan tanpa credential, dibuktikan `artifact-scan.json` dan pemeriksaan nilai sensitif gate. Batas yang dibuktikan adalah perilaku pembatasan concurrency readiness (429) dan batas waktu 5.000 ms pada beban yang disepakati; ini bukan bukti ketahanan terhadap banjir trafik jaringan, yang tetap membutuhkan kontrol edge sesuai aturan keamanan.

## Consequences

**Positive**:

- Foundation mendapat harness k6 yang dapat dipakai ulang oleh endpoint bisnis pertama: journey baru cukup ditambah ke `plan.ts`, `expectations.ts`, dan `journeys/`.
- Penolakan terkontrol (429) dan pemulihan sesudah beban serta sesudah database berhenti dibuktikan dengan angka, bukan hanya pada test fungsional READY-008.
- Topologi container dengan batas CPU dan memory sama di macOS dan Linux, sehingga hasil kedua environment lebih sebanding, dan run tidak memakai port 8888 atau 8889 di host.
- Beban aktual, dropped iterations, CPU dan memory backend, PostgreSQL, k6, serta sesi pool tercatat per profil dan ikut laporan yang terikat kandidat.
- Script beban yang rusak terdeteksi pada setiap push lewat smoke dan `k6 inspect`, walau profil panjang hanya dijalankan manual.

**Negative / tradeoffs**:

- Tier kapasitas membutuhkan sekitar 110 menit (soak 61 menit) dan mesin yang tidak menjalankan suite lain; di macOS run itu menahan Docker Desktop selama berjalan.
- Smoke menambah sekitar 2 sampai 3 menit pada job `real` per push, termasuk menarik dua image yang dipin bila belum ada di runner.
- Dua pin image baru dirawat manual, dan versi Bun di image wajib diperbarui bersama `engines.bun`.
- Target latency sekitar 4 sampai 7 kali nilai terukur lokal agar varians runner GitHub dan overhead k6 terserap; target itu menangkap regresi besar, bukan pergeseran kecil.
- Route status tidak jenuh pada beban O (baseline lebih dari 32.000 request per detik pada satu CPU), sehingga stress dan spike hampir tidak membebani CPU backend; pertentangan yang berarti hanya pada readiness.
- Biaya CPU k6 baru terukur di Mac ini (rata rata 38 sampai 44 persen satu CPU pada N, dan 81,7 persen rata rata serta 132,5 persen maksimum pada O di probe langkah 4), belum di runner GitHub; bila k6 tiga CPU tidak dapat membangkitkan beban O dalam batas 80 persen di runner, tier kapasitas gagal `generator_saturated` sampai pemilik memutuskan perubahan environment.
- Setiap profil membuat seluruh VU nya sebelum T0, walau yang aktif bersamaan biasanya hanya puluhan (gauge `vus` probe stress, diambil sekali per detik, paling tinggi 65 dari 2.500). Sebagian besar memory k6 karena itu dipakai VU yang menunggu, dan stress serta spike diperkirakan memakai sekitar dua pertiga dan setengah batas `generator_memory`.
- Jeda lebih dari sekitar 100 ms pada generator, mesin container, atau backend menggagalkan run lewat `dropped_iterations`, walau target latency masih terpenuhi. Ini disengaja (beban yang tidak dibangkitkan tidak dianggap terbukti), tetapi mesin atau runner yang berisik dapat gagal karena environment, bukan karena backend.
- Data ringkasan k6 tumbuh sekitar 200 sampai 330 byte per request selama run, sehingga soak satu jam diperkirakan memakai 56 sampai 81 persen batas `generator_memory`. Soak yang lebih panjang atau beban N yang lebih tinggi membutuhkan keputusan memory baru lewat `/architect`.
- Backend berjalan dalam container dengan `node_modules` host yang di mount, berbeda dari `serve` di host; ini hanya bekerja selama dependency backend murni JavaScript.
- Kode gate bertambah: tier keempat, dua jenis bukti, bagian laporan, laporan kapasitas, dan workflow kedua yang harus dijaga daftar izinnya; `runProcessGroup` yang dipakai bersama `api:check` dan runner tier mendapat opsi `onOutput`, yang wajib tidak mengubah perilaku pemanggil lama.
- Mesin container wajib melihat paling sedikit 4 CPU dan 4 GiB memory; Docker Desktop dengan alokasi lebih kecil gagal `environment_too_small` sampai alokasinya dinaikkan.
- Jendela `outage` yang dinilai ketat hanya 44 detik (101 sampai 145 detik) karena tepi fase diberi jarak dari perintah; request di sekitar stop dan start dinilai pada `stopping` dan `recovering` yang lebih longgar.
- Sampel `docker stats` sekitar satu sampai dua per detik dapat melewatkan lonjakan sangat singkat.
- Outage memakai `docker stop` (database berhenti bersih); database yang membeku (`docker pause`) tidak diukur pada beban dan tetap hanya dibuktikan fungsional oleh READY-008.
- Workflow kapasitas baru terbukti sesudah push dan pemicuan manual, karena `workflow_dispatch` tidak berjalan otomatis.

**Neutral**:

- Tidak ada perubahan kode aplikasi, schema, migration, grant, atau variable environment aplikasi.
- Gate per push tetap tiga tier; bukti smoke ikut bundle tier nyata.
- Laporan release tetap ditulis manual dan kini menyalin `report.md` per push serta `.local/feature-12/report.md` kapasitas untuk commit yang sama.
- Breakpoint dan k6 browser tidak dipakai: target tidak membutuhkan titik jenuh, dan frontend hanya aset statis yang alurnya dibuktikan Playwright.
- Mengembalikan perubahan cukup dengan revert commit, karena tidak ada data atau migration.

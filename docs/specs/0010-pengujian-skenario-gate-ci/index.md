# 0010. Pengujian skenario dan gate CI

**Date**: 2026-10-04
**Status**: Accepted

## Summary

Anda mendapat satu gate CI (gerbang pemeriksaan otomatis) yang menjalankan seluruh suite proyek pada setiap push dan pull request, termasuk PostgreSQL 18, backend, frontend, dan browser nyata. Setiap langkah CI adalah script root yang sama dengan yang Anda jalankan lokal, dan hasilnya dikumpulkan menjadi satu laporan per kandidat (commit beserta checksum artefaknya) yang membedakan lulus, gagal, dilewati, belum berjalan, dan test yang belum tersedia. Registry skenario divalidasi lebih ketat, setiap runner dibuktikan hanya menemukan suite miliknya, dan pemindai secret, dependency, serta workflow dipin dengan konfigurasi tetap dan kebijakan gagal yang tertulis, sehingga file di repository tidak dapat membungkamnya diam diam. Run GitHub Actions baru dapat dibuktikan setelah push; sebelum itu setiap langkah dibuktikan lokal dengan perintah yang sama.

## Requirements

**User stories**:

- Sebagai pengembang, Anda dapat menjalankan langkah CI yang sama secara lokal dan mendapat laporan dengan aturan yang sama seperti di CI.
- Sebagai pemilik release, Anda dapat membaca satu laporan yang mengikat setiap hasil test dan temuan pemindai pada commit dan artefak yang sama, tanpa menebak test mana yang belum berjalan.
- Sebagai penulis fitur, Anda mendapat penolakan yang jelas ketika registry merujuk test, kriteria, atau script yang tidak ada, atau ketika file test tidak dimiliki runner mana pun.

**Acceptance criteria**:

- **AC-1**: Setiap file test di repository dimiliki tepat satu runner menurut tabel pemilik di `scripts/lib/test-inventory.ts`: Vitest melalui Angular CLI (`test:frontend`) untuk `apps/frontend/src/**/*.spec.ts` dan `apps/frontend/src/**/*.test.ts`; Playwright dengan `playwright.config.ts` (`test:e2e`) untuk `tests/e2e/**/*.e2e.spec.ts` kecuali `*.real.e2e.spec.ts`; Playwright dengan `playwright.real.config.ts` (`test:readiness:real` dan `test:tooling:real`) untuk `tests/e2e/**/*.real.e2e.spec.ts`; serta `bun:test` untuk `tests/integration/<area>/**/*.test.ts` sesuai script area pada baris *Tabel pemilik runner*. Pola discovery adalah nama file yang cocok `^.+[._](test|spec)\.(js|jsx|ts|tsx|mjs|cjs|mts|cts)$`, yaitu gabungan pola bawaan Bun, Vitest, dan Playwright, sehingga file seperti `apps/frontend/tsconfig.spec.json` dan `tests/integration/infrastructure/compose.test.yml` bukan file test. File yang cocok pola discovery di luar tabel, termasuk di `tests/orchestration/`, `scripts/`, dan `apps/backend/`, membuat `check:test-discovery` gagal dengan path file itu. Menambah lokasi test baru, misalnya test unit backend `apps/backend/src/features/<fitur>/<service>.test.ts` menurut aturan testing, mensyaratkan satu baris pemilik di `scripts/lib/test-inventory.ts` dan langkah tier untuk script pemiliknya pada commit yang sama. Daftar file dari `playwright test --list --reporter=json` untuk setiap config dan dari `ng test --list-tests` wajib sama persis dengan himpunan pemiliknya, dibaca menurut baris *Format daftar runner*. Setelah run, setiap testsuite pada JUnit sebuah script hanya memuat file milik script itu, dan setiap file milik script muncul pada JUnit tersebut; selisih ke arah mana pun membuat gate `failed`.
- **AC-2**: `test:scenarios` memvalidasi seluruh `tests/scenarios/*.json` sebelum suite berjalan dan melaporkan semua pelanggaran sekaligus dengan path registry dan ID, tanpa isi file. Schema tetap: field yang tidak dikenal ditolak, skenario hanya memakai bentuk `checks`, `criteria` dan `checks` tidak boleh kosong, dan `critical` adalah boolean opsional. ID cocok `^[A-Z]+-\d{3}$` dan unik di seluruh registry. `source` adalah file reguler di `docs/specs/` atau `docs/rules/`, dan setiap kriteria didefinisikan sebagai butir daftar `**AC-n**:` pada source itu (bukan sekadar substring, sehingga `AC-1` tidak lolos karena `AC-10`). Setiap check mempunyai runner yang dikenal (`bun:test`, `vitest`, `playwright`, `command`), script yang ada di `package.json` dan menjadi langkah satu tier gate (check `command` juga boleh merujuk script tier itu sendiri), serta file reguler dengan path relatif di dalam repository tanpa `..` dan tanpa symlink. Untuk runner selain `command`, `testTag` wajib dan berupa ID terdaftar, file dimiliki runner script tersebut menurut AC-1, dan file memuat literal string yang diawali `<testTag>` diikuti spasi; literal dibaca dengan parser TypeScript yang sudah terpasang (`ts.createSourceFile`, node string literal, template tanpa substitusi, dan kepala template), sehingga tag yang hanya ada di komentar tidak dihitung. Untuk check `playwright`, `check:test-discovery` juga mewajibkan minimal satu test pada file itu menurut `playwright test --list` mempunyai judul lengkap (baris *Judul lengkap*) yang diawali `<testTag>` diikuti spasi. Pada check `command`, `testTag` opsional; bila ada harus ID terdaftar, tidak dicocokkan dengan isi file maupun JUnit, dan status check tetap berasal dari exit code. Skenario `critical` mempunyai minimal satu check `playwright` pada script tier. Seluruh 58 ID yang ada, termasuk TOOL-001 sampai TOOL-004, tetap ada dengan ID, kriteria, dan niat test yang sama; TOOL-003, TOOL-006, dan TOOL-008 yang masih memakai bentuk inline dipindah ke bentuk `checks` tanpa perubahan isi, dan test SDK-008 disesuaikan dengan runner tier menurut AC-3.
- **AC-3**: Workflow `.github/workflows/application.yml` berjalan pada setiap `push` dan `pull_request` dengan empat job pada `ubuntu-24.04`: `application` menjalankan `bun run test:ci` (tier cepat), `real` menjalankan `bun run test:ci:real` (tier nyata), `security` menjalankan `bun run test:ci:security` (tier keamanan), dan `report` menjalankan `bun run test:report` setelah ketiga job itu selesai, juga ketika salah satunya gagal, kecuali run dibatalkan. Langkah setiap tier mengikuti baris *Tabel tier*. Seluruh suite berjalan pada setiap push tanpa seleksi berdasarkan perubahan; skenario alur kritis APP-002, UI-001, READY-006, dan READY-009 ditandai `critical` dan dilaporkan pada bagian tersendiri. `check:workflow` menerapkan daftar izin pada baris *Aturan check:workflow* dan menolak setiap kunci, nilai, perintah, action, input, permission, trigger, atau path di luar daftar itu, termasuk rujukan `secrets.`, action yang tidak dipin SHA 40 heksadesimal, versi Node atau Bun yang berbeda dari `engines`, checkout job `security` tanpa `fetch-depth: 0`, dan script tier yang tidak dipanggil tepat satu kali pada job miliknya. Test SDK-008 di `tests/integration/contract/sdk.test.ts` disesuaikan pada perubahan yang sama: urutan `api:check` sebelum `build:frontend`, `test:frontend`, `test:integration`, dan `test:e2e` dibaca dari tabel tier `fast` yang diekspor `scripts/lib/gate.ts`, kunci `if` tingkat job hanya diizinkan pada job `report` dengan nilai `${{ !cancelled() }}`, sedangkan syarat `push` dan `pull_request` tanpa filter serta tepat satu langkah `bun run test:ci` tanpa `if` tetap. AC-8 spec 0009 tetap terpenuhi lewat tabel tier dan mendapat catatan amandemen yang merujuk spec ini.
- **AC-4**: `scripts/gate.ts <tier>` menjalankan langkah tier berurutan, setiap langkah sebagai `bun --no-env-file run <script>` dalam grup proses dengan environment daftar izin pada baris *Environment langkah* dan batas waktu tier, menghapus file bukti yang dideklarasikan sebelum langkah dimulai, berhenti pada langkah pertama yang tidak lulus dan mencatat sisanya `not_run` dengan alasan, lalu menulis bundle bukti beserta manifest tier. Langkah gagal bila exit code bukan 0, waktu habis, bukti wajib hilang atau tidak dapat dibaca menurut baris *Bukti per langkah* dan *Pembaca JUnit*, JUnit memuat failure atau error, `artifact-scan.json` memuat temuan, atau file bukti teks memuat nilai variable environment sensitif milik proses gate. Langkah dengan exit 0 tetapi memuat testcase dilewati dicatat `skipped` dan membuat tier gagal. Pada batas waktu atau sinyal, gate mengirim SIGTERM ke grup langkah dan menunggu masa tenggang tier sebelum SIGKILL; pada tier cepat dan tier nyata gate lalu mencatat listener yang masih tersisa pada port 8888 dan 8889. Setiap file `bun:test` tier nyata yang membuat container atau project Compose mendaftarkan resource itu, sebelum dibuat, pada modul `tests/orchestration/signal-cleanup.ts` menurut baris *Pembersihan sinyal suite nyata*, sehingga SIGINT, SIGTERM, atau SIGHUP ke `bun test` menghapus container, network, volume, dan folder sementara milik proses itu tanpa menyentuh resource run lain, lalu keluar 130, 143, atau 129; `tests/orchestration/database-real.ts` memberi grup `bun test` nya masa tenggang yang cukup untuk pembersihan itu. Tier nyata membangun image `foundation-postgres:18-pinned` dari `infrastructure/postgres/pins.json` lewat `test:infrastructure` pada job yang sama, lalu memakai PostgreSQL 18 terisolasi dengan credential acak, backend, frontend, dan Chromium nyata; Docker yang tidak tersedia membuat tier gagal, bukan lulus dengan skip. Workflow tidak memakai secret GitHub maupun credential production.
- **AC-5**: `check:security` menjalankan tiga pemindai yang dipin, melaporkan temuannya, dan menerapkan kebijakan tertulis; argumen, kanal laporan, batas waktu, dan pemetaan hasil mengikuti baris *Pemanggilan pemindai*, sedangkan field laporan dan aturan pengecualian mengikuti baris *Kebijakan pemindai*. (1) gitleaks dari image `ghcr.io/gitleaks/gitleaks` yang dipin tag dan digest indeks di `tests/security/scanners.json`, mode `git` dengan `--log-opts=--all` (seluruh riwayat yang dapat dijangkau dari semua ref checkout), `--redact`, konfigurasi tetap `tests/security/gitleaks.toml`, `.gitleaksignore` dan komentar `gitleaks:allow` diabaikan, tanpa jaringan, dan mount repository hanya baca; setiap temuan gagal kecuali fingerprint tercatat di `tests/security/exceptions.json` dengan alasan atau ditutup allowlist tunggal di `gitleaks.toml` (aturan `generic-api-key`, path `docs/testing/evidence/<NNNN>/*.json`, dan nilai berupa 64 heksadesimal kecil atau 40 heksadesimal besar, yaitu checksum SHA 256 dan fingerprint key PGP). Checkout dangkal (`git rev-parse --is-shallow-repository` bernilai `true`) membuat gitleaks `not_run`. (2) `bun audit` dari Bun yang dipin `engines.bun` (1.4.2), di folder sementara yang hanya berisi salinan `package.json` dan `bun.lock`, dengan environment minimum tanpa `.env`; advisory `high` atau `critical` gagal kecuali mempunyai pengecualian yang belum kedaluwarsa (paling lama 90 hari sejak dicatat), `moderate` dan `low` dilaporkan tanpa menggagalkan, severity lain gagal, pengecualian kedaluwarsa gagal, dan pengecualian tanpa temuan dilaporkan sebagai tidak terpakai. (3) actionlint dari image `rhysd/actionlint` yang dipin tag dan digest indeks, dengan `-config-file` ke file kosong `tests/security/actionlint.yaml` dan path workflow eksplisit, tanpa jaringan; setiap temuan gagal. Keberadaan `.gitleaks.toml`, `.gitleaksignore`, `.github/actionlint.yaml`, atau `.github/actionlint.yml` di checkout membuat `check:security` gagal dengan path file itu. Pemindai yang tidak dapat berjalan (image, jaringan registry npm, checkout dangkal, atau output yang tidak valid) dicatat `not_run` dan membuat tier gagal. `.local/feature-11/security.json` memuat nama, versi, image beserta digest, cakupan, jumlah temuan per kebijakan, dan daftar temuan dengan field yang dinamai baris *Kebijakan pemindai* saja, tanpa nilai secret, potongan baris, nama author, atau email. Pada kandidat fitur ini pemindai dependency tidak mempunyai temuan `high` atau `critical`: pin `postcss` 8.5.6 yang terkena empat advisory dinaikkan ke 8.5.28.
- **AC-6**: `test:report` menghitung status setiap check dari manifest tier dan JUnit di bundle. Testcase cocok untuk sebuah check bila path file testsuite, setelah dinormalisasi per runner, sama dengan file check dan judul lengkapnya (baris *Judul lengkap*) diawali `<testTag>` diikuti spasi; status dihitung hanya atas testcase cocok, sehingga kegagalan atau skip test lain di file yang sama tidak mengubah check itu. `passed`: script berjalan dan semua testcase cocok lulus, atau check `command` keluar 0 (check yang merujuk script tier memakai status tier). `failed`: ada testcase cocok yang gagal atau error, atau check `command` keluar bukan 0. `skipped`: testcase cocok ada tetapi sebagian atau semuanya dilewati, dengan alasan dari runner. `not_run`: script tidak berjalan pada run ini, dengan kode alasan seperti langkah sebelumnya gagal atau manifest tier tidak ada. `missing_test`: script berjalan tetapi tidak ada testcase cocok. Status skenario adalah status check terburuk dengan urutan `failed`, `missing_test`, `not_run`, `skipped`, lalu `passed`. `not_applicable` tidak dihasilkan generator dan hanya dipakai laporan release dengan alasan. Hanya `passed` yang dihitung lulus. Gate `passed` bila seluruh skenario `passed`, ketiga tier lulus, discovery sesuai, ketiga pemindai lulus, dan pengikatan sah; `failed` bila ada check, langkah tier, discovery, atau kebijakan pemindai yang gagal; selain itu `incomplete`. `test:report` keluar 0 hanya untuk gate `passed`.
- **AC-7**: Setiap manifest tier mencatat identitas kandidat (commit `HEAD`, `clean` yang benar hanya bila `git status --porcelain` kosong di awal dan di akhir tier, SHA 256 pohon sumber pada awal dan akhir tier, serta identitas run CI bila ada), versi Bun, Node (`null` bila perintah `node` tidak ada), OS, dan arsitektur, checksum input dan output pada baris *Value sourcing*, serta SHA 256 setiap file bukti. Environment tidak termasuk pengikatan. `test:report` menyatakan pengikatan sah hanya bila ketiga manifest dan checkout laporan mempunyai commit serta pohon sumber yang sama, pohon sumber tidak berubah selama tier, identitas run CI ketiga manifest dan job `report` sama pada `runId`, `runAttempt`, `sha`, `ref`, dan `event` (`job` dikecualikan) dengan `sha` sama dengan commit kandidat, atau ketiga manifest dan laporan sama sama tanpa identitas CI, dan setiap file bukti cocok dengan SHA 256 di manifest; selain itu gate `incomplete` dengan kode alasan per masalah pada baris *Kode alasan*. Laporan menandai kandidat release hanya bila gate `passed`, `clean` benar pada ketiga manifest, event `push` pada ref `refs/heads/main`, dan ketiga tier berasal dari run serta attempt CI yang sama; run lokal pada working tree yang belum masuk commit dapat lulus gate tetapi dinyatakan bukan kandidat release. Setiap syarat yang tidak terpenuhi dicatat sebagai alasan dengan kode lingkup *Kandidat release* pada baris *Kode alasan*, dalam bentuk dan urutan baris *Kandidat release*; tanda ini tidak mengubah status gate maupun exit code `test:report`. Laporan ditulis ke `.local/feature-11/report.json` dan `.local/feature-11/report.md` (bahasa Indonesia, isi dan kolom menurut baris *Isi laporan*, termasuk identitas PostgreSQL dari `image.json` tier nyata menurut baris *Identitas PostgreSQL*, tabel skenario mengikuti template laporan release) dan ditambahkan ke file `GITHUB_STEP_SUMMARY` bila variable itu ada.
- **AC-8**: Manifest, laporan, ringkasan job, dan `security.json` hanya memuat field terstruktur yang dinamai spec ini, tanpa nilai environment, credential, DSN, atau output langkah; output langkah hanya diteruskan ke konsol seperti sekarang. File bukti runner (JUnit beserta atribut `hostname`, `system-out`, dan pesan failure, screenshot, `image.json`, dan `artifact-scan.json`) diunggah apa adanya; sebelum disalin ke bundle, setiap file bukti teks diperiksa terhadap nilai variable environment sensitif milik proses gate menurut baris *Value sourcing*, dan temuan menggagalkan langkah dengan nama variable dan path saja. SIGINT, SIGTERM, dan SIGHUP (terminal yang tertutup) pada `scripts/gate.ts` atau `check:security` menghentikan grup proses yang sedang berjalan, mencatat langkah atau pemindai itu `failed` atau `not_run` dengan alasan sinyal dan sisanya `not_run`, menulis manifest atau `security.json`, lalu keluar 130, 143, atau 129; `check:security` juga menjalankan `docker rm -f` atas nama acak container pemindai pada setiap jalur keluar. Argumen container dibentuk fungsi murni yang diekspor `tests/orchestration/security-scan.ts` dengan flag pada baris *Pemanggilan pemindai*: `--rm`, nama acak berawalan `foundation-security-`, `--pull never`, `--network none`, `--read-only` dengan `/tmp` tmpfs, `--user` UID dan GID host (65534:65534 bila UID host 0), `--cap-drop ALL`, `--security-opt no-new-privileges`, `--pids-limit`, `--memory`, `--cpus`, serta mount repository dan konfigurasi hanya baca. Pemanggilan Docker hanya berada di `tests/orchestration/`, sehingga INFRA-001 tetap lulus. Artefak CI hanya memuat bundle bukti tier dan laporan, diunggah dengan `include-hidden-files: true`, `overwrite: true`, dan retensi 90 hari.
- **AC-9**: Setiap langkah `run` di workflow selain setup adalah `bun run <script>` yang dapat dijalankan lokal dengan perintah yang sama: `bun run test:ci`, `bun run test:ci:real` (memerlukan Docker), `bun run test:ci:security` (memerlukan Docker dan akses ke registry npm), lalu `bun run test:report` yang membaca bundle bukti lokal dengan aturan yang sama seperti di CI. Aturan testing, keamanan, dan infrastruktur, README, serta template laporan release menyebut tier, script, lokasi bukti, kebijakan pemindai, dan laporan baru menurut baris *Dokumen yang diperbarui*; kalimat bahwa suite nyata berjalan di luar `test:ci` sampai CI dengan Docker tersedia diperbarui, sedangkan kalimat yang diperiksa INFRA-001 tetap ada. Run GitHub Actions untuk commit fitur ini diperiksa setelah push oleh tahap pipeline berikutnya dan dicatat sebagai bukti terpisah, bukan disimpulkan dari run lokal.

## Decision

**Chosen option**: Perkuat tooling yang ada menjadi gate tiga tier yang dijalankan oleh satu runner tier Bun, dengan laporan yang menggabungkan bundle bukti setiap tier dan mengikatnya pada kandidat yang sama, ditambah tiga pemindai yang dipin.

`test:ci` tetap menjadi perintah tier cepat dan tetap tidak membutuhkan Docker, tetapi kini dijalankan `scripts/gate.ts` sehingga setiap langkah tercatat. Suite nyata yang selama ini berjalan di luar CI menjadi tier nyata pada job paralel, pemindai menjadi tier keamanan, dan job keempat menyusun laporan. Pilihan kedua adalah satu job berurutan yang memperpanjang rantai `&&` dan hanya mengunggah JUnit; itu lebih sederhana, tetapi tidak dapat mencatat langkah yang tidak berjalan, tidak mengikat bukti pada kandidat, dan memperlambat umpan balik tier cepat.

Tidak ada skill komunitas yang membentuk keputusan ini. Aturan proyek testing, keamanan, infrastruktur, workflow development, dan perintah development tetap mengikat implementasi.

## Feature design

**Data model sketch**: Tidak ada data persisten, migration, atau schema baru; pertanyaan schema menurut `AGENTS.md` tidak berlaku. Database test tetap container PostgreSQL 18 terisolasi milik suite yang ada (spec 0002, 0004, 0005, 0006, dan 0003) dengan credential acak per run. Fitur ini hanya menambah file data berikut.

| Entitas | Lokasi | Field utama | Relasi |
| --- | --- | --- | --- |
| Registry skenario | `tests/scenarios/<fitur>.json` | `source`, `scenarios` | 1:N skenario |
| Skenario | di dalam registry | `id`, `criteria` (tidak kosong), `critical` (opsional), `checks` (tidak kosong) | N:1 registry, 1:N check |
| Check | di dalam skenario | `runner`, `script`, `file`, `testTag` (wajib kecuali `command`, opsional pada `command`) | N:1 skenario, N:1 langkah tier lewat `script` |
| Pemilik runner | konstanta di `scripts/lib/test-inventory.ts` | `script`, `runner`, akar, pola file, config, JUnit | 1:N file test |
| Tier | konstanta di `scripts/lib/gate.ts` | `name`, `steps`, `stepTimeoutMs`, `stopGraceMs` | 1:N langkah |
| Langkah | di dalam tier | `script`, `evidence` (path, jenis, runner, wajib) | N:1 tier |
| Daftar pembersihan sinyal | memori proses `bun test`, modul `tests/orchestration/signal-cleanup.ts` | callback sinkron per resource beserta pelepasnya | 1:1 resource uji yang dibuat proses itu |
| Manifest tier | `.local/feature-11/evidence/<tier>/manifest.json` | `candidate`, `environment`, `inputs`, `outputs`, `steps`, `status` | 1:1 run tier, 1:N file bukti |
| Bundle bukti | `.local/feature-11/evidence/<tier>/<path repo>` | salinan file bukti pada path repo aslinya | N:1 manifest |
| Hasil pemindai | `.local/feature-11/security.json` | `scannedAt`, `workingTreeClean`, `scanners`, `status` | bukti langkah `check:security` |
| Laporan | `.local/feature-11/report.json` dan `report.md` | field pada baris *Isi laporan* | 1 per kandidat, membaca 3 manifest |
| Pin pemindai | `tests/security/scanners.json` | `gitleaks.image`, `actionlint.image` | dibaca `check:security` |
| Konfigurasi pemindai | `tests/security/gitleaks.toml`, `tests/security/actionlint.yaml` | `[extend]` dan satu `[[allowlists]]`; file kosong | dimount hanya baca ke container |
| Pengecualian | `tests/security/exceptions.json` | `secrets`, `dependencies` | N:1 temuan, awalnya kedua daftar kosong |

Baris komentar atau direktif di dalam `run` membuat perintah tidak cocok dan ditolak.

**Pemanggilan pemindai** (`tests/orchestration/security-scan.ts`): file ini mengekspor pembentuk argumen container sebagai fungsi murni dan hanya menjalankan pemindaian bila `import.meta.main`. Setiap image ditarik lebih dulu dengan `docker pull <repo>:<tag>@sha256:<digest>` dalam batas 300.000 ms per image, di luar batas pemindai; tarikan yang gagal membuat pemindai itu `not_run` dengan alasan `image_pull_failed`. Total waktu tetap dibatasi batas langkah tier keamanan. Container dijalankan dengan argumen tetap berurutan:

`docker run --rm --name foundation-security-<pemindai>-<12 heksadesimal acak> --pull never --network none --read-only --tmpfs /tmp:rw,nosuid,nodev,noexec,size=64m --user <uid>:<gid> --cap-drop ALL --security-opt no-new-privileges --pids-limit 256 --memory 1g --cpus 2 -e HOME=/tmp <env pemindai> -v <repo>:/repo:ro <mount konfigurasi> -w /repo <image> <argumen pemindai>`

| --- | --- | --- | --- | --- |
| gitleaks | `-e GIT_CONFIG_COUNT=1 -e GIT_CONFIG_KEY_0=safe.directory -e GIT_CONFIG_VALUE_0=/repo -e GIT_ATTR_SOURCE=4b825dc642cb6eb9a060e54bf8d69288fbee4904`; `-v <repo>/tests/security/gitleaks.toml:/config/gitleaks.toml:ro` | `git --config /config/gitleaks.toml --gitleaks-ignore-path /tmp --ignore-gitleaks-allow --log-opts=--all --redact --no-banner --exit-code 2 --report-format json --report-path - /repo` | 300.000 ms | stdout array JSON: exit 0 dengan array kosong berarti tanpa temuan, exit 2 dengan array tidak kosong berarti ada temuan, kombinasi lain atau JSON tidak valid berarti `not_run` dengan alasan `invalid_output` |

Batas waktu dan batas output adalah konstanta `SCAN_LIMITS` di `tests/orchestration/security-scan.ts`; hanya pemanggil `runSecurityScan` di test GATE-007 yang dapat memberi nilai lain, tidak lewat environment maupun argumen. Laporan pemindai hanya dibaca dari stdout yang ditangkap di memori dengan batas 50 MB dan tidak pernah ditulis mentah ke disk. UID dan GID berasal dari `process.getuid()` dan `process.getgid()`, diganti 65534:65534 bila UID host 0. Pada setiap jalur keluar, termasuk batas waktu, SIGINT, dan SIGTERM, `check:security` menjalankan `docker rm -f <nama>` dengan batas 60.000 ms untuk setiap container yang namanya sudah dibuat, mengikuti pola `tests/orchestration/readiness-container.ts`. Keberadaan `.gitleaks.toml`, `.gitleaksignore`, `.github/actionlint.yaml`, atau `.github/actionlint.yml` di checkout membuat `check:security` gagal dengan alasan `scanner_config_in_repo` dan path file itu.

**Kebijakan pemindai** (`scripts/lib/security-policy.ts` dan isi `security.json`):

- `security.json` memuat `schema`, `scannedAt` (UTC), `workingTreeClean`, `status`, dan `scanners` berisi tiga objek dengan field `name`, `version`, `image` (beserta digest, `null` untuk `bun audit`), `status` (`passed`, `failed`, atau `not_run`), `reason` (kode atau `null`), `coverage`, `counts` (jumlah temuan per `policy`), `findings`, dan `unusedExceptions`.
- Cakupan: gitleaks `{ head, commitsReachable, shallow }` dari `git rev-parse HEAD`, `git rev-list --all --count`, dan `git rev-parse --is-shallow-repository`; `bun audit` `{ packages }`, yaitu jumlah entri `packages` pada `bun.lock` yang dibaca `Bun.JSONC.parse`; actionlint `{ files }`, yaitu path workflow yang diperiksa.
- Field temuan: gitleaks `rule`, `file`, `line`, `commit`, `fingerprint`, `policy`; `bun audit` `advisory`, `package`, `severity`, `vulnerableVersions`, `installedVersions`, `policy`; actionlint `file`, `line`, `column`, `kind`, `message` (dipotong 200 karakter), `policy`. `policy` bernilai `failed`, `excepted`, atau `reported`. Field lain dari keluaran pemindai, termasuk `Secret`, `Match`, `Author`, `Email`, `Message`, `Link`, dan `Date`, dibuang.
- Fingerprint gitleaks berbentuk `<commit>:<file>:<rule>:<line>` seperti keluaran gitleaks, sehingga pengecualian secret hanya dapat dicatat setelah commit pembawanya ada; temuan pada commit baru membuat tier keamanan merah sampai secret dihapus atau pengecualian dicatat.
- Pengecualian: `recorded` tidak boleh setelah tanggal pemindaian; pengecualian dependency berlaku sampai dan termasuk tanggal `expires` (kedaluwarsa bila tanggal pemindaian UTC setelah `expires`, alasan `exception_expired`), dan `expires` paling lama 90 hari setelah `recorded` (selain itu `exception_too_long`). Pengecualian secret dan dependency tanpa temuan dicatat di `unusedExceptions` tanpa menggagalkan.
- Severity `high` dan `critical` gagal, `moderate` dan `low` dilaporkan, dan severity lain gagal dengan alasan `severity_unknown`. Versi terpasang diambil dari entri `bun.lock` yang memenuhi `vulnerable_versions` lewat `Bun.semver.satisfies`.
- Saat working tree tidak bersih, `workingTreeClean` bernilai `false` dan laporan menyatakan bahwa perubahan yang belum masuk commit tidak dipindai gitleaks.

**Kandidat release** (`releaseCandidate` di `report.json`, keputusan 69):

- Bentuknya `{ value, reasons }`. Setiap alasan berbentuk `{ code, tier }`, dengan `tier` berupa `fast`, `real`, `security`, atau `null` untuk syarat tingkat laporan, seperti masalah pengikatan; tidak ada `path` karena tidak ada file yang terlibat. `value` benar hanya bila `reasons` kosong.
- Semua syarat yang tidak terpenuhi dicatat, bukan hanya yang pertama, dalam urutan tetap berikut. Dalam satu kode, urutan tier adalah `fast`, `real`, `security`, lalu `null`.

| Urutan | Kode | `tier` | Dicatat bila |
| --- | --- | --- | --- |
| 1 | `gate_not_passed` | `null` | gate `failed` atau `incomplete` |
| 2 | `not_clean` | nama tier | manifest tier yang valid mempunyai `candidate.clean` bernilai `false` |
| 3 | `not_ci` | nama tier, atau `null` untuk job laporan | manifest tier yang valid dengan `candidate.ci` bernilai `null`; bertier `null` bila `candidate.ci` di `report.json` (identitas CI job laporan) bernilai `null` |

- Run atau attempt CI yang berbeda tidak mempunyai kode sendiri. Pengikatan mencatat `ci_identity_differs`, `ci_attempt_differs`, atau `ci_mixed`, gate menjadi `incomplete`, dan alasan kandidat release memuat `gate_not_passed`. Karena pengikatan yang sah menuntut `event` dan `ref` sama pada ketiga manifest dan job laporan, `event` serta `ref` hanya dinilai dari identitas CI job laporan. Tanpa identitas CI pada job laporan keduanya tidak dinilai, dan `not_ci` bertier `null` yang menjelaskannya.
- Contoh: run lokal yang lulus pada checkout bersih memberi `not_ci` untuk `fast`, `real`, `security`, dan `null`; pull request memberi `event_not_push` dan `ref_not_main`; push ke branch lain memberi hanya `ref_not_main`.
- `report.md` dan ringkasan job menulis `Kandidat release: ya`, atau `Kandidat release: bukan` diikuti setiap kode beserta nama tiernya bila tidak `null`, dalam urutan yang sama. Tanda ini tidak mengubah status gate maupun exit code `test:report`, sehingga job pull request dan push ke branch lain tetap hijau bila gate `passed`.

**Key invariants**:

1. Registry tidak menyimpan hasil. Status hanya berasal dari exit code dan JUnit run yang tercatat di manifest; `skipped`, `not_run`, dan `missing_test` tidak pernah dihitung lulus.
2. Bukti lama tidak dapat terbaca sebagai bukti baru: gate menghapus file bukti yang dideklarasikan sebelum langkah, menghapus bundle lama tier sebelum tier mulai, menulis bundle lewat folder sementara lalu rename, mencatat SHA 256 sesudah langkah, dan laporan menolak bukti yang hash nya berbeda atau berasal dari attempt CI lain.
3. Kata `docker` tidak muncul di `scripts/**/*.ts` (INFRA-001, tanpa membedakan huruf besar), termasuk teks laporan dan pesan. Pemanggilan container hanya di `tests/orchestration/security-scan.ts` dan orkestrasi test yang sudah ada; modul kebijakan murni berada di `scripts/lib/security-policy.ts`.
4. Manifest, `security.json`, laporan, dan ringkasan job hanya memuat field terstruktur yang dinamai di spec ini, ditambah teks runner yang dipotong dan di-escape. Output langkah tidak ditangkap, tidak ada nilai environment yang ditulis, langkah hanya menerima environment daftar izin, dan file bukti runner yang diunggah apa adanya diperiksa lebih dulu terhadap nilai environment sensitif.
5. Ambang dan pengecualian pemindai tidak dapat dilemahkan lewat environment, argumen, flag, atau file konfigurasi pemindai milik repository. Jalannya hanya file di `tests/security/` yang masuk lewat review: entri bertanggal di `exceptions.json` dan allowlist tunggal di `gitleaks.toml` yang bentuknya dikunci GATE-007.
6. Tier cepat tidak membutuhkan Docker; tier nyata dan keamanan gagal tanpa Docker.
7. Workflow tidak memuat logika selain setup; setiap langkah gate adalah script root.
8. ID skenario stabil; tidak ada ID yang dihapus atau dinomori ulang.
9. Struktur JUnit yang tidak dikenali menurut baris *Pembaca JUnit* membuat langkah `failed`, tidak pernah `passed`. Pembaca JUnit tidak menambah dependency.
10. Tier berhenti pada langkah pertama yang tidak lulus; tidak ada retry otomatis. Run ulang di GitHub tercatat sebagai `runAttempt` baru, dan gate sah hanya bila ketiga tier dan laporan berasal dari attempt yang sama.
11. Tier dalam satu checkout dijalankan berurutan; tidak ada lock karena bentrokan port membuat langkah gagal secara terlihat, bukan lulus palsu.
12. Fixture test gate dibuat saat runtime di folder `mkdtemp` di luar repository; tidak ada file yang cocok pola discovery di-commit sebagai fixture.
13. Resource uji Docker hanya dihapus berdasarkan nama yang dibuat proses itu sendiri dan tercatat di memori sebelum resource dibuat. Tidak ada pembersihan, termasuk pembersihan sinyal, yang menentukan apa yang dihapus lewat pencarian pola nama atau label, sehingga run lain yang berjalan bersamaan tidak tersentuh.

**Security model**: Pelakunya pengembang lokal dan job GitHub Actions pada runner hosted untuk push serta pull request, termasuk pull request dari fork yang berjalan dengan token hanya baca dan tanpa secret dan yang dapat mengubah file apa pun di repository. Workflow hanya memakai `contents: read`, checkout dengan `persist-credentials: false` sehingga token tidak tertinggal di `.git/config` untuk langkah berikutnya, tidak merujuk `secrets.`, dan tidak memakai `pull_request_target`. Repository publik, sehingga artifact dapat diunduh pengguna GitHub mana pun: yang diunggah hanya bundle bukti yang dideklarasikan, yaitu JUnit apa adanya (termasuk `hostname` runner, `system-out`, dan pesan failure), screenshot, identitas image, hasil pemindaian credential acak milik orkestrasi nyata, dan `security.json` tanpa nilai secret, potongan baris, nama, atau email author. Setiap file bukti teks diperiksa lebih dulu terhadap nilai variable environment sensitif milik proses gate, dan langkah tier hanya menerima environment daftar izin, sehingga variable shell pengembang atau runner tidak sampai ke langkah maupun bukti; credential acak di dalam suite nyata tetap diperiksa orkestrasi masing masing. Pemindai container berjalan terisolasi (tanpa jaringan, filesystem hanya baca, user non root, tanpa capability, `no-new-privileges`, batas proses, memory, dan CPU, `--rm`, dan nama acak yang dihapus pada setiap jalur keluar), dan image serta action dipin digest atau SHA untuk membatasi risiko rantai pasok. Konfigurasi pemindai ditetapkan gate dari `tests/security/`: `.gitleaks.toml`, `.gitleaksignore`, komentar `gitleaks:allow`, atribut `.gitattributes` pada riwayat yang dibaca gitleaks, `.github/actionlint.yaml`, dan direktif di dalam `run` tidak berpengaruh, dan keberadaan file konfigurasi pemindai itu menggagalkan tier (`.gitattributes` tetap boleh ada untuk keperluan lain), sehingga perubahan untuk membungkam pemindai selalu terlihat di `tests/security/`. Pull request tetap dapat mengubah `tests/security/`, sehingga kontrolnya adalah review dan test GATE-007 yang mengunci bentuk allowlist, bukan pencegahan teknis. Hasil pemindai hanya membuktikan cakupan pemindai itu; tidak ditemukannya masalah bukan bukti aplikasi aman. Database advisory `bun audit` bersifat langsung, sehingga hasil dapat berubah tanpa perubahan kode; itu disengaja agar advisory baru terlihat.

**Configuration required**: Tidak ada variable environment aplikasi atau secret baru. File baru `tests/security/scanners.json` (tag dan digest indeks multi arch dibaca saat implementasi dengan `docker buildx imagetools inspect <image>:<tag>`, baris `Digest` teratas, sama seperti prosedur `pins.json`), `tests/security/gitleaks.toml` dengan bentuk di atas, `tests/security/actionlint.yaml` yang kosong, dan `tests/security/exceptions.json` (awalnya `{ "secrets": [], "dependencies": [] }`, karena sembilan temuan `generic-api-key` pada riwayat saat ini adalah checksum SHA 256 di `docs/testing/evidence/0001/candidate.json` dan fingerprint key PGP di `docs/testing/evidence/0002/reproducibility.json` yang ditutup allowlist). ## Consequences

**Positive**:

- Suite nyata (INFRA, DATA, MIG, READY-008, READY-009, dan TOOL nyata) mulai berjalan di Linux pada setiap push, sehingga regresi database dan browser tidak lagi bergantung pada run manual di macOS.
- Setiap langkah yang tidak berjalan terlihat sebagai `not_run`, bukan hilang di balik rantai `&&`.
- Laporan menghubungkan hasil, checksum artefak, identitas PostgreSQL, dan temuan pemindai pada satu kandidat, sehingga laporan release dapat menyalin bukti tanpa menebak.
- Registry yang salah rujuk dan file test tanpa pemilik ditolak sebelum suite berjalan.
- Tier cepat tetap dapat dijalankan tanpa Docker dengan nama perintah yang sama.
- Pemindai tidak dapat dibungkam lewat file konfigurasi atau komentar di repository; setiap pelonggaran terlihat di `tests/security/`.
- SIGTERM dari gate atau Ctrl+C pada suite nyata lokal tidak lagi meninggalkan container PostgreSQL berisi password acak, project Compose, network, volume, atau folder env file; tindak lanjut container `provision.test.ts` dari keputusan 53 spec 0006 ikut selesai.

**Negative / tradeoffs**:

- Setiap push menambah job nyata yang diperkirakan 7 sampai 10 menit (build image PostgreSQL dari nol belum pernah diukur di runner amd64) serta job keamanan dan laporan. Job berjalan paralel, tetapi status akhir baru tersedia setelah job terlama selesai.
- Aturan skip sebagai kegagalan membuat gangguan Docker di runner menggagalkan CI.
- Database advisory yang langsung dapat membuat commit yang sebelumnya hijau menjadi merah tanpa perubahan kode.
- Pemindaian seluruh riwayat dapat menemukan false positive lama yang harus dicatat sebagai pengecualian beralasan; pengecualian secret baru hanya dapat dicatat setelah commit pembawanya ada, sehingga commit itu merah satu kali.
- Allowlist checksum pada bukti test berarti nilai heksadesimal 64 atau 40 karakter di `docs/testing/evidence/*/*.json` tidak dilaporkan oleh aturan `generic-api-key`.
- Hanya *Re-run all jobs* yang menghasilkan gate sah; *Re-run failed jobs* selalu menghasilkan `incomplete`.
- Karena semua syarat kandidat release yang tidak terpenuhi dicatat, run lokal yang lulus selalu memuat empat alasan `not_ci`, dan run yang gate nya tidak lulus juga memuat alasan lain, misalnya `not_clean`, yang baru penting setelah gate diperbaiki.
- Script suite yang ada masih memuat `.env` lokal di dalam langkahnya sendiri; hanya CI yang dijamin tanpa `.env`.
- Pull image dari Docker Hub (`oraclelinux`, `rhysd/actionlint`) dapat terkena batas pull anonim.
- Ada tujuh script, empat file pin, konfigurasi, dan pengecualian, serta beberapa modul baru yang perlu dirawat; pin pemindai diperbarui manual.
- Frontend dibangun dua kali per push (tier cepat dan `test:database:real`).
- Empat file suite milik spec 0002, 0004, 0005, dan 0006 kini bergantung pada modul pembersihan sinyal spec ini. Ctrl+C pada suite nyata menunggu pembersihan sampai 60 detik dan Ctrl+C kedua tidak mempercepatnya; SIGKILL langsung atau event loop yang macet tetap dapat meninggalkan resource, yang namanya dicetak bila pembersihan sempat berjalan.
- Masa tenggang tier nyata 180 detik membuat SIGKILL pada daemon Docker yang menggantung baru terjadi sesudah tiga menit.

**Neutral**:

- `test:ci` tetap bernama sama tetapi kini menulis bundle dan manifest di `.local/feature-11/evidence/fast/`.
- Laporan release di `docs/testing/releases/` tetap ditulis manual dengan menyalin `report.md` run kandidat; generator tidak menulis ke `docs/`.
- Performance k6 (fitur 12) dan identitas image deployment (fitur 13) belum masuk gate; laporan menyebutnya di luar cakupan.
- Mengembalikan perubahan cukup dengan revert satu commit, karena tidak ada data atau migration.

## Follow-up

- [ ] Setelah push, periksa run GitHub Actions commit fitur ini (keempat job, isi ketiga artifact, dan `report.md`), lalu catat hasilnya pada laporan bukti fitur. Kegagalan khusus Linux pada tier nyata ditangani lewat siklus perbaikan.
- [ ] Ukur durasi build image PostgreSQL dan job nyata di runner amd64; sesuaikan `timeout-minutes` dan batas langkah bila terlalu longgar atau ketat.
- [ ] Setelah durasi run CI pertama terukur, tambahkan batas waktu total per tier beberapa menit di bawah `timeout-minutes` job, dengan langkah yang memakai sisa waktu tier bila lebih kecil dari batas langkah, agar gate sendiri yang menghentikan langkah lambat dan menulis manifest sebelum GitHub membatalkan job (keputusan 77).
- [ ] Fitur autentikasi yang menambah login ke e2e tier cepat menetapkan `trace` mati atau pemindaian credential pada `playwright.config.ts`, seperti `playwright.real.config.ts`, karena isi `trace.zip` yang terkompresi tidak terbaca pemeriksaan nilai sensitif gate (keputusan 74).
- [ ] Bila batas pull Docker Hub tercapai, rancang mirror image atau autentikasi pull lewat spec terpisah.
- [ ] Putuskan pemindaian kode statis (misalnya CodeQL atau Semgrep) dalam spec terpisah ketika kode bisnis pertama hadir.
- [ ] Pertimbangkan run terjadwal untuk advisory baru pada commit yang tidak berubah.
- [ ] Bila tier cepat melewati 10 menit atau tier nyata melewati 20 menit, rancang seleksi test berdasarkan perubahan lewat `/architect`.

# Rationale: Pengujian skenario dan gate CI

## Context

Fitur 11 pada scope meminta kriteria fitur terhubung dengan test serta bukti kandidat yang benar: runner hanya menemukan suite miliknya, registry mempunyai ID unik dan rujukan test yang valid, CI menjalankan pemeriksaan tipe, build, kontrak, test terkait, dan regression alur kritis, integration database serta E2E memakai komponen nyata, pemindai dipin dan temuannya dilaporkan, status gagal, dilewati, belum berjalan, dan belum tersedia dibedakan, dan laporan mengikat hasil pada kandidat yang sama. Data test memakai database terisolasi tanpa credential production, dan TOOL-001 sampai TOOL-004 dipertahankan.

Keadaan saat ini (dibaca dari kode pada 2026-10-04):

- `test:ci` adalah rantai `&&` empat belas script. Ketika satu script gagal, script berikutnya tidak berjalan dan tidak ada catatan tentang itu; keberhasilan hanya terlihat dari exit code job.
- `scripts/validate-scenarios.ts` memeriksa format dan keunikan ID, tetapi kriteria diperiksa dengan `source.includes(criterion)` (sehingga `AC-1` lolos karena `AC-10`), tag test dengan `content.includes(tag)` (lolos walau hanya ada di komentar), tidak ada schema, dan dua bentuk skenario (inline dan `checks`) diterima. Tidak ada pemeriksaan bahwa script check termasuk CI atau bahwa file dimiliki runner script itu.
- Discovery runner hanya dijaga konvensi: path eksplisit pada `bun test`, `testMatch` dan `testIgnore` Playwright, dan default Angular CLI. Belum ada bukti bahwa daftar yang ditemukan runner sama dengan yang diharapkan.
- Suite nyata `test:infrastructure`, `test:database:real`, `test:database:migration`, `test:tooling:real`, dan `test:readiness:real` berjalan di luar `test:ci`. READY-008, READY-009, INFRA, DATA, MIG, dan TOOL nyata belum pernah berjalan di Linux; aturan infrastruktur dan testing mencatatnya menunggu jalur CI dengan Docker. Suite nyata bergantung pada image `foundation-postgres:18-pinned` yang dibangun INFRA-002 dari `pins.json`.
- Workflow `application.yml` mempunyai satu job (`ubuntu-24.04`, action dipin SHA, batas 15 menit) yang hanya menjalankan `test:ci` lalu mengunggah `.local/feature-4/*.xml` dan `test-results/`. `upload-artifact` berjalan dengan `include-hidden-files: false`, sehingga belum pasti file di folder tersembunyi `.local/` ikut terunggah.
- Belum ada pemindai secret, dependency, atau workflow. `bun audit` pada lockfile saat ini menemukan empat advisory pada `postcss` 8.5.6, dua `high` dan dua `moderate`; versi itu adalah devDependency langsung yang dipakai build Angular lewat `.postcssrc.json`.
- Laporan bukti di `docs/testing/` ditulis manual; tidak ada artefak yang mengikat hasil runner, checksum OpenAPI dan SDK, build, dan temuan pemindai pada satu commit.

Kekuatan yang membatasi keputusan: aturan testing menetapkan enam status, registry tanpa hasil manual, runner dengan cakupan eksplisit, dan orkestrasi Docker hanya di `tests/`; INFRA-001 menolak kata `docker` di seluruh `scripts/**/*.ts` tanpa membedakan huruf besar; aturan keamanan meminta pemindai yang dipin dengan temuan dan cakupan dilaporkan; Docker bukan prasyarat runtime pengembang, sehingga pemeriksaan tanpa Docker harus tetap dapat dijalankan lokal. Repository bersifat publik, sehingga artifact CI dapat diunduh pengguna GitHub mana pun dan runner hosted standar tersedia tanpa biaya menit. Pipeline ini membuat commit di tahap terakhir, sehingga perubahan workflow hanya dapat dibuktikan di GitHub setelah push; setiap langkah CI harus dapat dibuktikan lokal lebih dulu. Build approach proyek adalah Tracer Bullet.

## Options considered

### Opsi 1: Perkuat tooling yang ada menjadi gate tiga tier dengan laporan terikat kandidat

Satu runner tier Bun (`scripts/gate.ts`) menjalankan langkah tier cepat, nyata, dan keamanan sebagai grup proses, mencatat setiap langkah dan bukti di manifest, lalu `test:report` menggabungkan ketiga bundle dan mengikatnya pada commit serta pohon sumber yang sama. Validator registry diperketat, discovery dibuktikan lewat mode daftar runner dan JUnit, dan tiga pemindai dipin (gitleaks dan actionlint lewat digest image, `bun audit` lewat versi Bun). Empat job paralel di satu workflow. (basis: `docs/rules/testing.md` bagian pemetaan skenario dan CI, `docs/rules/security.md` bagian verifikasi, pola `runProcessGroup` dan pin `pins.json` yang sudah ada)

**Pros**:
- Nama `test:ci` dan seluruh script suite yang ada tetap; tidak ada suite yang ditulis ulang.
- Langkah yang tidak berjalan tercatat `not_run` dengan alasan; bukti lama tidak dapat terbaca sebagai bukti baru.
- Tier cepat tetap tanpa Docker dan memberi umpan balik dalam sekitar 3,5 menit, sementara tier nyata berjalan paralel.
- Laporan yang sama dihasilkan lokal dan di CI dari bundle yang sama bentuknya.
- Tanpa dependency npm baru.

**Cons**:
- Menambah tujuh script, beberapa modul, dan dua file pin serta pengecualian yang perlu dirawat.
- Workflow lebih panjang (empat job) dan butuh unggah serta unduh artifact antarjob.
- Pembaca JUnit tanpa dependency harus diuji terhadap format ketiga runner.

### Opsi 2: Satu job berurutan dengan rantai `&&` yang diperpanjang

Tambahkan suite nyata dan pemindai ke rantai `test:ci` (atau rantai kedua di job yang sama), lalu unggah semua JUnit. Laporan disusun manual dari artifact seperti sekarang.

**Pros**:
- Perubahan paling kecil; satu job, satu checkout, tanpa penggabungan bukti.
- Mudah dipahami siapa pun yang membaca `package.json`.

**Cons**:
- Rantai `&&` tidak mencatat langkah yang tidak berjalan, sehingga `not_run` tidak dapat dibedakan dari lulus tanpa membaca log.
- Tidak ada pengikatan bukti pada kandidat; JUnit lama dari run sebelumnya dapat terbawa.
- `test:ci` lokal menjadi membutuhkan Docker, padahal Docker bukan prasyarat pengembang.
- Umpan balik tier cepat menunggu build image dan suite nyata, sekitar 11 sampai 13 menit per push.

### Opsi 3: Tier cepat setiap push, suite nyata terjadwal atau manual

Push dan pull request hanya menjalankan `test:ci`; suite nyata berjalan lewat `schedule` harian atau `workflow_dispatch`.

**Pros**:
- Waktu CI per push tetap sekitar 3,5 menit.
- Gangguan Docker di runner tidak memblokir pull request.

**Cons**:
- Regresi database dan browser nyata baru terlihat sampai satu hari kemudian dan tidak terikat pada commit yang menyebabkannya.
- Bertentangan dengan scope yang meminta integration database dan E2E di CI memakai komponen nyata untuk kandidat.
- Workflow terjadwal pada repository publik dinonaktifkan GitHub setelah 60 hari tanpa aktivitas.

### Opsi 4: Action pihak ketiga untuk laporan test dan pemindaian

Pakai action marketplace untuk publikasi JUnit (misalnya action test reporter), `gitleaks-action`, dan `dependency-review-action`, setiap action dipin SHA.

**Pros**:
- Tampilan hasil test dan anotasi pull request yang kaya tanpa menulis generator laporan.
- Pemeliharaan pemindai berada pada penyedia action.

**Cons**:
- Langkah CI tidak lagi berupa script repo yang dapat dibuktikan lokal sebelum push.
- Sebagian action membutuhkan permission tulis (`checks: write`, `pull-requests: write`) atau lisensi untuk organisasi.
- `dependency-review-action` hanya menilai perubahan dependency pada pull request, bukan seluruh lockfile pada push.
- Status skenario, alur kritis, dan pengikatan kandidat tetap harus dibangun sendiri karena action tidak mengenal registry proyek.

## Rationale

Masalah utamanya bukan kurangnya suite, melainkan tidak adanya catatan yang dapat dipercaya tentang apa yang berjalan untuk kandidat mana. Rantai `&&` menyembunyikan langkah yang tidak berjalan, JUnit di `.local/` dapat berasal dari run lama, dan suite nyata tidak pernah menyentuh Linux. Opsi 1 menyelesaikan ketiganya dengan satu mekanisme: runner tier yang menghapus bukti sebelum langkah, mencatat hash sesudahnya, dan menulis manifest yang dibaca laporan. Karena mekanisme yang sama berjalan lokal dan di CI, setiap langkah dapat dibuktikan sebelum push, sesuai batas pipeline ini.

Pemisahan tier cepat dan nyata menjaga dua kekuatan yang saling tarik: Docker bukan prasyarat pengembang, tetapi scope meminta komponen nyata di CI. Tier cepat tetap tanpa Docker dengan nama perintah yang sama, sedangkan tier nyata berjalan paralel di job sendiri dengan aturan bahwa skip berarti gagal, sehingga runner tanpa Docker tidak pernah menghasilkan lulus palsu. Menjalankan semua suite di setiap push lebih aman daripada seleksi berdasarkan perubahan selama waktunya masih kecil; seleksi menambah risiko melewatkan regresi tanpa penghematan yang berarti.

Untuk pemindai, pilihan mengikuti stack yang ada dan pola pin yang sudah dipakai `pins.json`. `bun audit` sudah ada di Bun 1.4.2 yang dipin, membaca `bun.lock` secara langsung, dan dapat berjalan di folder terisolasi tanpa `.env`. gitleaks dan actionlint tidak mempunyai padanan di stack, sehingga dijalankan sebagai container yang dipin digest indeks multi arch, satu pin untuk macOS arm64 dan runner amd64, tanpa jaringan dan dengan mount hanya baca. Orkestrasi container berada di `tests/orchestration/` karena INFRA-001, sedangkan kebijakan murni di `scripts/lib/` dapat diuji tanpa Docker. Temuan `postcss` diselesaikan dengan menaikkan pin ke versi yang sudah ada di lockfile sebagai salinan bersarang, bukan dengan pengecualian, karena perbaikannya murah dan menjaga daftar pengecualian kosong sejak awal.

## Keputusan agent atas delegasi pemilik

Pemilik proyek mendelegasikan keputusan desain fitur ini ("jika membutuhkan /architect anda bisa menjalankannya dengan mengambil keputusan sendiri berdasarkan rekomendasi anda"). Tidak ada manusia selama run. Percakapan desain dijalankan sebagai pertimbangan internal: setiap pertanyaan dicatat dengan pilihan, rekomendasi, dan pilihan akhir. Semua keputusan berikut diambil oleh agent pada 2026-10-04 atas delegasi tersebut, tanpa konfirmasi manusia.

Framing yang disimpulkan: mode ENHANCEMENT (gate, validator, dan workflow sudah ada), platform tooling CLI dan CI tanpa UI maupun endpoint, stack dari `AGENTS.md` (Bun 1.4.2, Node 24.21.0, Angular CLI, Playwright 1.63.0, Docker untuk PostgreSQL 18), build approach Tracer Bullet dari scope.

**Tahap kebutuhan**

1. **Cakupan inti.** Pilihan: (a) discovery, registry, gate tiga tier, pemindai, dan laporan terikat kandidat di atas script yang ada; (b) validator dan job Docker saja, laporan tetap manual; (c) layanan pelaporan test pihak ketiga. Dipilih (a), karena setiap butir "Selesai ketika" pada scope membutuhkan bagian itu. (b) meninggalkan status dan pengikatan tanpa bukti; (c) menambah layanan luar dan secret.
2. **Arti test terkait.** Pilihan: (a) seluruh suite pada setiap push; (b) seleksi berdasarkan path yang berubah; (c) seluruh suite di `main`, seleksi di pull request. Dipilih (a): tier cepat sekitar 3,5 menit dan suite nyata sekitar 1,5 menit di macOS, sehingga seleksi hanya menambah risiko. Pilihan kedua (b), bila anggaran waktu terlampaui.
3. **Definisi alur kritis.** Pilihan: (a) APP-002, UI-001, READY-006, dan READY-009 ditandai `critical`; (b) semua skenario Playwright; (c) tanpa penanda. Dipilih (a): keempatnya alur pengguna lewat frontend, termasuk alur nyata lintas aplikasi. UI-002, READY-007, dan TOOL-007 tetap berjalan pada setiap push tanpa penanda.
4. **Taksonomi status.** Pilihan: (a) enam status aturan testing, generator mengeluarkan lima, `not_applicable` hanya untuk laporan release; (b) status baru `not_available` untuk environment; (c) lulus dan gagal saja. Dipilih (a): "belum tersedia" pada scope dipetakan ke `missing_test`, dan environment yang tidak tersedia menjadi `skipped` dengan alasan atau `not_run`. Status baru akan memisahkan laporan dari aturan dan template.
5. **Urutan agregasi skenario.** Pilihan: (a) `failed`, `missing_test`, `not_run`, `skipped`, `passed`; (b) `failed`, `skipped`, `not_run`, `missing_test`, `passed`. Dipilih (a): rujukan rusak lebih penting diperbaiki daripada eksekusi yang belum terjadi.
6. **Status gate dan kandidat release.** Pilihan: (a) gate `passed`, `failed`, `incomplete` ditambah tanda kandidat release terpisah; (b) memakai `ready`, `blocked`, `incomplete` langsung. Dipilih (a): gate per push bukan izin release; istilah `ready` tetap milik laporan release yang juga memuat performance dan pengecualian.

**Tahap model data**

7. **Schema database.** Tidak ada data persisten; pertanyaan schema `AGENTS.md` tidak berlaku. Database test tetap container terisolasi milik suite yang ada dengan credential acak, dan workflow tidak memakai secret.
8. **Model file bukti.** Pilihan: (a) manifest per tier dalam bundle berisi salinan bukti pada path repo aslinya; (b) satu manifest yang ditulis ulang setiap tier; (c) membaca langsung `.local/feature-*` tanpa bundle. Dipilih (a): unggah dan unduh artifact per tier menjadi satu folder dengan path tetap, lokal dan CI memakai bentuk yang sama, dan tier tidak saling menimpa. Model ditinjau ulang sebagai tabel entitas dan relasi pada spec, lalu diterima.
9. **Bentuk registry.** Pilihan: (a) hanya bentuk `checks`, field tidak dikenal ditolak, `critical` opsional; (b) tetap menerima bentuk inline. Dipilih (a); tiga skenario TOOL inline dipindah tanpa perubahan ID, kriteria, maupun test.

**Tahap stack dan tool**

10. **Bahasa tooling gate.** Pilihan: (a) script Bun tanpa dependency baru, YAML lewat `Bun.YAML.parse`, JUnit lewat pembaca kecil; (b) menambah package XML dan YAML; (c) fitur khusus GitHub. Dipilih (a); probe membuktikan `Bun.YAML.parse` membaca workflow pada Bun 1.4.2.
11. **Tempat urutan tier.** Pilihan: (a) `scripts/gate.ts` dengan tabel tier, `test:ci` tetap namanya; (b) rantai `&&` ditambah manifest per script; (c) Makefile atau task runner. Dipilih (a): hanya runner yang dapat mencatat `not_run` dan menghapus bukti lama.
12. **Susunan job CI.** Pilihan: (a) empat job, tiga tier paralel dan job laporan; (b) satu job berurutan; (c) tier cepat per push, nyata terjadwal. Dipilih (a). Pilihan kedua (b), bila penggabungan artifact terbukti bermasalah.
13. **Suite nyata per push.** Pilihan: (a) kelima suite nyata pada setiap push dan pull request; (b) sebagian per push, lengkap harian. Dipilih (a). `test:database:migration` tetap berjalan walau file yang sama ikut `test:database:real`, karena registry MIG merujuk script itu dan biayanya sekitar 17 detik.
14. **Pemindai secret.** Pilihan: (a) gitleaks sebagai container dipin digest indeks, mode `git`, `--redact`, tanpa jaringan; (b) binary gitleaks yang diunduh dengan checksum per platform; (c) secret scanning dan push protection GitHub saja; (d) trufflehog container. Dipilih (a): satu pin untuk dua arsitektur, mengikuti pola pin image yang ada, dan dapat dijalankan lokal. Pilihan kedua (b). (c) tidak dapat dijalankan lokal dan tidak masuk laporan.
15. **Pemindai dependency.** Pilihan: (a) `bun audit` dari Bun 1.4.2 di folder terisolasi; (b) osv-scanner container dipin digest; (c) Trivy; (d) Dependabot alerts saja. Dipilih (a): sudah ada di stack yang dipin dan membaca `bun.lock` langsung. Pilihan kedua (b), bila cakupan advisory registry npm terbukti kurang.
16. **Lint workflow.** Pilihan: (a) actionlint container dipin digest ditambah pemeriksaan struktur repo; (b) pemeriksaan struktur repo saja; (c) tidak ada. Dipilih (a): perubahan workflow baru terbukti di GitHub setelah push, sehingga kesalahan sintaks harus tertangkap lokal.
17. **Pemindaian kode statis.** Pilihan: (a) ditunda, checker proyek yang ada (`check:frontend:bundle`, `api:validate`, `api:check`) menutup kontrol kode saat ini; (b) CodeQL; (c) Semgrep container. Dipilih (a), dicatat di Follow-up.
18. **Kebijakan dependency.** Pilihan: (a) `high` dan `critical` gagal, `moderate` dan `low` dilaporkan, pengecualian paling lama 90 hari; (b) semua tingkat gagal; (c) hanya dilaporkan. Dipilih (a).
19. **Kebijakan secret.** Pilihan: (a) setiap temuan gagal kecuali fingerprint dikecualikan dengan alasan; (b) hanya dilaporkan; (c) hanya commit baru yang diperiksa. Dipilih (a): repository publik, sehingga secret di riwayat lama sama terbukanya dengan secret baru.
20. **Temuan awal `postcss`.** Pilihan: (a) naikkan pin 8.5.6 ke 8.5.28; (b) pengecualian sementara. Dipilih (a): versi 8.5.28 sudah ada di lockfile sebagai salinan bersarang `@tailwindcss/postcss`, `beasties`, dan `vite`, berada dalam rentang peer `@angular/build` (`^8.4.0`), dan memenuhi rentang `@tailwindcss/postcss` (`^8.5.16`).
21. **Lokasi pin dan pengecualian.** Pilihan: (a) `tests/security/`; (b) `config/`; (c) di workflow. Dipilih (a): berdampingan dengan test yang memakainya dan terbaca lokal.
22. **Tingkat rujukan.** `sources`: rujukan proyek dan praktik bernama tanpa tautan, karena tidak ada tautan yang diverifikasi web pada run ini. Versi dan digest gitleaks serta actionlint ditetapkan saat implementasi lewat `docker buildx imagetools inspect`, bukan dari ingatan.
23. **Penawaran Agent Skill dan MCP.** Tool baru (gitleaks, actionlint) memicu penawaran. Rekomendasi skill adalah mencari, tetapi pemasangan mengubah konfigurasi proyek dan mengunduh paket tanpa persetujuan manusia, sedangkan kedua tool hanya berjalan sebagai container CLI. Dipilih "Not now, later" dan dicatat di Follow-up.

**Tahap antarmuka**

24. **Nama script.** `test:ci` (tier cepat), `test:ci:real`, `test:ci:security`, `test:report`, `test:gate`, `check:test-discovery`, `check:workflow`, dan `check:security`. Pilihan kedua adalah satu `check:gate` gabungan; ditolak karena langkah terpisah memberi status yang lebih jelas di manifest.
25. **Bukti discovery.** Pilihan: (a) inventaris statis ditambah `playwright test --list` dan `ng test --list-tests` sebelum run, ditambah atribut file JUnit setelah run untuk `bun:test`; (b) inventaris statis saja; (c) menjalankan `bun test` dengan pola nama kosong. Dipilih (a). (c) ditolak karena memuat file test, termasuk deteksi Docker dan container, hanya untuk mendapat daftar.
26. **Resolusi judul test.** Pilihan: (a) literal string yang diawali tag dan spasi sebelum run, judul `--list` untuk Playwright, dan pencocokan judul JUnit setelah run; (b) `includes` seperti sekarang. Dipilih (a); probe menunjukkan seluruh 64 check non `command` lolos aturan ini.
27. **Isi laporan.** JSON untuk mesin dan Markdown berbahasa Indonesia mengikuti tabel template release, ditambahkan ke `GITHUB_STEP_SUMMARY`. Generator tidak menulis ke `docs/testing/releases/`.
28. **Identitas kandidat.** Pilihan: (a) commit ditambah SHA 256 pohon sumber dari `git ls-files --cached --others --exclude-standard`; (b) commit saja; (c) hash seluruh folder tanpa Git. Dipilih (a): pohon sumber mengikat tier pada file yang sama walau working tree belum masuk commit, sehingga tahap verify sebelum commit tetap dapat lulus gate tetapi dinyatakan bukan kandidat release.
29. **Kandidat release.** Gate `passed`, checkout bersih, event `push`, dan ketiga tier dari run CI yang sama. Pull request dikecualikan karena commit gabungannya bukan commit yang akan dirilis. Dipersempit pada keputusan 56: ref wajib `refs/heads/main` dan attempt CI sama.

**Tahap keamanan**

30. **Permission dan secret CI.** Tetap `contents: read`, tanpa `secrets.`, tanpa `pull_request_target`, ditegakkan `check:workflow`.
31. **Isi artifact publik.** Hanya bundle yang dideklarasikan; keluaran mentah pemindai tidak diunggah, `security.json` dinormalisasi tanpa `Secret`, `Match`, nama, atau email author. Bukti nyata sudah dipindai credential acaknya oleh orkestrasi setiap suite. Pemindaian gitleaks tambahan atas bukti sebelum unggah ditolak karena pemindaian nilai tepat yang ada lebih kuat untuk credential acak, dan tier cepat tidak mempunyai secret. Dilengkapi pada keputusan 59: JUnit diunggah apa adanya dan diperiksa terhadap nilai environment sensitif milik proses gate.
32. **Isolasi pemindai.** `--rm`, `--network none`, `--read-only` dengan `/tmp` sementara, `--user` UID dan GID host, repository hanya baca. Diubah pada keputusan 52: tanpa folder keluaran (laporan lewat stdout), ditambah batas resource, `--cap-drop ALL`, `no-new-privileges`, nama acak, dan UID 65534 untuk host root.
33. **Ambang tidak dapat dilemahkan.** Konstanta di kode; tidak ada variable environment atau flag untuk menurunkannya.

**Tahap kegagalan**

34. **Tier berhenti pada kegagalan pertama.** Pilihan: (a) berhenti dan mencatat sisanya `not_run`; (b) melanjutkan langkah yang independen. Dipilih (a), sesuai perilaku rantai sekarang; (b) membutuhkan metadata ketergantungan antarlangkah.
35. **Skip pada tier.** Testcase dilewati membuat langkah `skipped` dan tier gagal, di semua environment. Script suite tunggal (`bun run test:infrastructure`) tetap boleh melewati test tanpa Docker untuk pemakaian lokal.
36. **Batas waktu.** Per langkah 600.000 ms (cepat dan keamanan) dan 1.500.000 ms (nyata, karena build image INFRA-002 dibatasi 900.000 ms); job 15, 45, 15, dan 10 menit. Di dalam `check:security`: gitleaks 300 detik, `bun audit` 120 detik, actionlint 120 detik. `check:test-discovery`: 120 detik per perintah daftar. Semua batas kini juga tertulis di `index.md`, ditambah tarik image 300 detik, `docker rm -f` 60 detik, dan masa tenggang per tier (keputusan 52 dan 57).
37. **Sinyal.** SIGINT dan SIGTERM menghentikan grup proses aktif, langkah dicatat `failed` dengan alasan sinyal, manifest ditulis, exit 130 atau 143, mengikuti pola orkestrasi yang ada.
38. **Retry.** Tidak ada retry otomatis; Playwright tetap `retries: 0`. Run ulang GitHub tercatat sebagai `runAttempt` baru sehingga kegagalan awal tidak tersembunyi.
39. **Pemindai tidak dapat berjalan.** Dicatat `not_run` dan menggagalkan tier keamanan; tidak pernah dianggap tanpa temuan.
40. **Artifact hilang.** Langkah unduh `continue-on-error`, tier tanpa bundle menjadi `not_run`, gate `incomplete`.
41. **Tier berjalan bersamaan di satu checkout.** Tanpa lock; dicatat di aturan bahwa tier dijalankan berurutan. Bentrokan port membuat langkah gagal secara terlihat.

**Tahap cross check** (keputusan 42 sampai 63 diambil agent pada 2026-10-04 atas delegasi pemilik, setelah pemeriksa independen dari model berbeda mengembalikan daftar celah; ringkasannya ada di bagian *Cross check*)

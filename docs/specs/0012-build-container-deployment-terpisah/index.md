# 0012. Build container dan deployment terpisah

**Date**: 2026-10-05
**Status**: Accepted

## Summary

Frontend, backend, dan runner migration masing masing mendapat image sendiri yang dibangun dengan root monorepo sebagai build context, memakai base image yang dipin digest dan daftar izin konteks build, sehingga file `.env` dan secret lain tidak pernah ikut masuk. Topologi rujukan yang netral terhadap penyedia memakai satu edge nginx (server di depan yang melayani frontend statis, mengakhiri TLS, dan meneruskan `/api/` ke backend), backend dan PostgreSQL di jaringan internal, migration sebagai job sekali jalan, serta health dan readiness backend yang hanya terjangkau dari jaringan internal. Satu langkah baru tier nyata membuktikan topologi itu dengan container lokal pada setiap push: isi konteks build, TLS, header, CORS, jaringan, resource, shutdown, dan log tanpa data. Perintah baru `test:report:release` menyatakan kandidat release `ready`, `blocked`, atau `incomplete` dari bundle bukti CI per push dan kapasitas yang diunduh untuk commit yang sama, membaca identitas run dari manifest bundle itu sendiri, dan tidak pernah memberi izin deploy, mendorong image ke registry, atau melakukan deploy.

## Requirements

**User stories**:

- Sebagai pemilik operasi, Anda dapat membangun tiga image dari root monorepo dan menjalankan topologi rujukan di satu host Docker dengan langkah migration terpisah, tanpa secret di image.
- Sebagai pengembang, Anda mendapat bukti per push bahwa TLS, header, jaringan, health, shutdown, dan log topologi itu bekerja pada container nyata.
- Sebagai pemilik release, Anda mendapat status kesiapan `ready`, `blocked`, atau `incomplete` yang terikat pada commit, pohon sumber, dan identitas image, dan Anda tahu status itu bukan izin deploy.

**Acceptance criteria**:

- **AC-1**: Tiga Dockerfile dibangun dengan root monorepo sebagai build context (`docker build -f <Dockerfile> <root>`): `apps/frontend/Dockerfile` (image edge berisi build production Angular dan nginx), `apps/backend/Dockerfile` (image backend berisi satu bundle `bun build`), dan `database/Dockerfile` (image runner yang menyalin `database/` dan `libs/server/database/` dari konteks daftar izin, sehingga berisi `database/*.ts`, `database/migrations/`, dan `database/seeds/` hanya bila folder itu ada), dengan isi stage akhir, `USER` numerik, entrypoint, `STOPSIGNAL`, dan `HEALTHCHECK` menurut tabel *Image*. Setiap Dockerfile mempunyai file ignore khusus `<Dockerfile>.dockerignore` yang baris aturan pertamanya `*`, hanya memasukkan kembali path pada tabel *Daftar izin konteks build*, dan diakhiri `**/.env` serta `**/.env.*`; root mendapat `.dockerignore` daftar tolak sebagai pengaman. Setiap `FROM` dan `COPY --from=<image>` berbentuk `<repo>:<tag>@sha256:<64 heksadesimal kecil>` menurut tabel *Image dasar*. Stage akhir tidak mempunyai `ARG` atau `ENV` yang namanya cocok `/(PASSWORD|SECRET|TOKEN|KEY|CREDENTIAL|DATABASE_URL)/i`. Image hanya ditandai lokal lewat `docker build -t`: daftar izin `dockerArgs` orkestrasi menolak `push`, `login`, `logout`, `tag`, `save`, dan `load`; tidak ada baris yang cocok `/\bdocker (image )?(push|login|tag)\b/` di `deploy/`, `.github/workflows/`, `README.md`, maupun `docs/rules/deployment.md`; dan `deploy/compose.yaml` merujuk image hanya lewat variable tanpa kunci `build`.
- **AC-2**: Image dibangun dari salinan input build di folder `mkdtemp`, bukan dari checkout: salinan tidak memuat file bernama `.env` atau `.env.*`, `node_modules`, `dist`, maupun `.angular` dari checkout, lalu orkestrasi menanam file sentinel bernilai acak berbeda di setiap path pada baris *Sentinel konteks build*. Lapisan pertama adalah probe konteks: untuk setiap Dockerfile, orkestrasi membangun Dockerfile probe `FROM scratch` dengan `COPY . /context/` bersama salinan byte persis file ignore Dockerfile itu, dengan `--output type=local` ke folder `mkdtemp`, dan daftar file hasilnya harus sama persis dengan daftar yang diturunkan fungsi murni `expectedContext` dari tabel *Daftar izin konteks build* atas isi salinan, tidak memuat path yang nama dasarnya cocok `^\.env(\..*)?$`, dan tidak memuat nilai sentinel mana pun. Lapisan kedua adalah image akhir: untuk ketiga image, filesystem hasil `docker export`, keluaran `docker image inspect`, dan `docker history --no-trunc` tidak memuat satu pun nilai sentinel, filesystem tidak mempunyai path yang nama dasarnya cocok `^\.env(\..*)?$`, dan `Config.Env` tidak mempunyai key yang cocok pola secret AC-1. File statis frontend di image edge termasuk filesystem yang dipindai, dan orkestrasi menjalankan `checkFrontendBundle` dari `scripts/lib/frontend-bundle.ts` terhadap folder `/srv/frontend/` hasil export image edge (sumber aplikasi dari salinan, environment berisi nilai credential run), yang harus lulus. Credential hanya masuk saat runtime lewat environment service yang membutuhkannya (AC-8), dan sertifikat serta key TLS hanya lewat secret file Compose.
- **AC-3**: Migration adalah langkah deployment tersendiri. Job sekali jalan `docker compose ... run --rm migrate database/migrate.ts --apply` memakai image runner dengan `FOUNDATION_MIGRATOR_DATABASE_URL` saja, keluar 0, dan rerun mencetak `Migrations: 0 applied, <jumlah file> skipped`. Perintah bawaan image (`database/migrate.ts` tanpa `--apply`) keluar 1 dengan `Use --apply` tanpa perubahan database; orkestrasi membuktikannya dengan `compose run --name foundation-deploy-migrate-<hex> migrate` tanpa `--rm` dan tanpa perintah, lalu memakai container yang berhenti itu untuk check AC-8 dan menghapusnya dengan nama itu. Provisioning pertama kali memakai image yang sama dengan `database/provision.ts --apply` dan credential admin yang diteruskan dari environment shell operator lewat `-e <NAMA>` tanpa nilai di argumen; seed opsional memakai `database/seed.ts --apply`. Backend dan edge tidak pernah menjalankan provisioning, migration, atau seed. Backend yang dijalankan sebelum migration menjawab `GET /health/ready` 503, lalu 200 sesudah job migration selesai tanpa restart backend. Tidak ada schema, role, grant, atau privilege baru: backend tetap `foundation_backend` dengan `SELECT` pada `common.schema_migrations` saja (spec 0004), runner tetap `foundation_migrator` (spec 0005), dan edge tidak menerima credential database.
- **AC-4**: `createApp('production')` dan `createApp('development')` memasang `GET /health/live` dan `GET /health/ready`. `/health/live` menjawab 200 dengan JSON tepat `{"status":"live"}` tanpa menyentuh pool. `/health/ready` menjalankan satu transaksi pada pool backend (`SET LOCAL statement_timeout = '2s'`, lalu `SELECT EXISTS (SELECT 1 FROM common.schema_migrations WHERE name = ${REQUIRED_MIGRATION}) AS applied` dengan parameter) dan menjawab 200 `{"status":"ready"}` hanya bila hasilnya `true`; hasil `false`, pool tidak ada, koneksi atau query gagal, dan batas 5.000 ms menjawab 503 `{"status":"unavailable"}`. Penanda pemeriksaan aktif dilepas hanya saat promise query itu sendiri selesai (berhasil atau gagal), tidak saat batas 5.000 ms. Pemanggil yang datang selama query berjalan tidak pernah memulai query baru: sebelum batas pemeriksaan aktif tercapai ia menerima hasil bersama pemeriksaan itu, dan sesudah batas tercapai tetapi query belum selesai (koneksi atau database macet) ia langsung menerima 503 `{"status":"unavailable"}`. Dengan begitu paling banyak satu query readiness berjalan per proses, termasuk saat database dibekukan. Kedua route memakai urutan penjaga route readiness spec 0006 (404 `{"error":"Not found"}` untuk method selain GET termasuk HEAD dan untuk path yang tidak tepat; 400 `{"error":"Invalid request"}` untuk query string tidak kosong, `Content-Length` selain `0`, atau `Transfer-Encoding`), `Cache-Control: no-store` pada setiap jawaban handler, dan tidak memuat waktu, versi, jumlah, nama, atau pesan error. Komposisi production tetap menjawab 404 untuk `/api/status`, `/api/readiness`, `/openapi`, `/openapi/json`, dan path lain, tidak memasang plugin OpenAPI, dan tidak mempunyai endpoint admin, metrics, atau debug, menurut tabel *Kebijakan endpoint production*. Kedua operasi diekspor ke `openapi.json` menurut tabel *Kontrak OpenAPI*, `REQUIRED_OPERATIONS` mendapat dua entri, `bun run api:sync` menghasilkan `HealthService` tanpa edit manual, `bun run api:check` lulus, dan test kesesuaian SDK membuktikan `getHealthLive()` (200) serta `getHealthReady()` (503 tanpa database) terhadap backend harness spec 0009. Pada PostgreSQL 18 nyata dengan pool role `foundation_backend`, `/health/ready` menjawab 503 sebelum migration, saat `common.schema_migrations` belum ada, dan saat hak `SELECT` dicabut, lalu 200 sesudah migration dan sesudah `GRANT` dipulihkan; nama migration dikirim sebagai parameter; `SHOW statement_timeout` pada koneksi pool sesudah pemeriksaan sama dengan sebelumnya; dan container database yang dibekukan (`docker pause`) memberi 503 paling lama 5.500 ms sesudah request pertama, request berikutnya selama lebih dari 5.000 ms berikutnya tetap 503 sementara fungsi query nyata yang dibungkus penghitung dipanggil tepat satu kali, lalu 200 paling lama 15 detik sesudah `docker unpause`.
  - *Amandemen 2026-10-06 (spec [0014](../0014-akses-pengguna-lifecycle-sesi/index.md), tabel Perubahan deployment)*: kedua komposisi `createApp` memasang plugin auth sesudah log request dan sebelum health; production tetap tanpa OpenAPI dan route development. Backend production wajib `PUBLIC_ORIGIN` (gagal start tanpa nilai sah), `deploy/compose.yaml` memberinya dari `FOUNDATION_PUBLIC_ORIGIN`, edge membatasi `POST /api/auth/session` dengan `limit_req zone=sign_in` dan named location 429, image runner memuat `libs/server/auth/`, dan `DEPLOYMENT_CHECKS` mendapat `auth_account_job`, `auth_session_cookie`, `auth_origin_csrf`, `auth_capacity`, serta `auth_edge_rate_limit` dalam urutan tabel itu. DEP-006 memeriksa navigasi production Beranda lalu Akun.
- **AC-5**: Edge mengakhiri TLS pada port container 8443 dengan sertifikat dan key dari file yang di mount saat runtime (`/run/secrets/edge_tls_cert` dan `/run/secrets/edge_tls_key`), hanya TLS 1.2 dan TLS 1.3 dengan cipher baris *Konfigurasi edge*, HTTP/2 lewat ALPN `h2`, dan tanpa session ticket pada TLS 1.2; handshake TLS 1.1 ditolak server. Cara pembuktiannya tetap: `openssl s_client -alpn h2` mencetak `ALPN protocol: h2`; handshake `-tls1_2` tidak mencetak baris `TLS session ticket` (TLS 1.3 di luar klaim ini, karena OpenSSL tetap mengirim `NewSessionTicket` berbasis session cache); dan sebelum uji TLS 1.1, baris perintah yang sama dengan `-tls1_2` sebagai kontrol positif harus berhasil, lalu `-tls1_1 -cipher DEFAULT@SECLEVEL=0` harus gagal dengan alert `protocol version` dari server (keluaran memuat `alert protocol version`, bukan `no protocols available`). Port container 8080 menjawab setiap method dan path dengan 308 dan `Location: https://$host$request_uri`, mengirim `Cache-Control: no-store` (keputusan 67), tidak meneruskan apa pun ke backend, dan tidak mengirim `Strict-Transport-Security`; `$host` tidak membawa port, sehingga topologi rujukan mengasumsikan HTTPS publik pada port 443 (tertulis di `docs/rules/deployment.md`), dan uji pada port acak hanya memeriksa bentuk `Location` tepat `https://localhost<path dan query asli>`. Setiap jawaban HTTPS memuat `Strict-Transport-Security: max-age=31536000`. Uji memakai sertifikat yang dibuat per run oleh CA sementara dan memverifikasinya dengan CA itu lewat client Bun dan `openssl s_client -verify_return_error`, tidak dengan verifikasi yang dimatikan.
- **AC-6**: Setiap jawaban HTTPS edge di luar `/api/` memuat header tepat menurut tabel *Header dokumen*, termasuk `Content-Security-Policy` dengan nilai yang sama persis. `Cache-Control` dan pemilihan file mengikuti tabel *Cache dan fallback*: path yang segmen terakhirnya tidak mempunyai ekstensi dilayani `index.html` dengan status 200, path berekstensi yang tidak ada mendapat 404. Konfigurasi `production` di `apps/frontend/angular.json` memuat objek `optimization` tepat `{ "scripts": true, "styles": { "minify": true, "inlineCritical": false, "removeSpecialComments": true }, "fonts": { "inline": false } }` (objek lengkap, karena `@angular/build` 22.2.0 memperlakukan field objek yang tidak ditulis sebagai `false`), sehingga JS dan CSS tetap diminify, budget yang ada tetap berlaku, build tidak mengambil font dari jaringan, dan `index.html` hasil build tidak memuat elemen `<script>` tanpa `src` maupun elemen `<style>`. Di Chromium melalui edge, pada viewport 1280×812 dan 375×812, `/` menampilkan `h1` `Foundation`, stylesheet `styles-*.css` terpasang (`--radius-base` pada `:root` bernilai `.375rem`), navigasi hanya berisi `Beranda`, `/kesiapan` diarahkan ke `/`, tidak ada event `securitypolicyviolation` (termasuk Trusted Types), error console, atau page error, tidak ada request yang path nya memuat `/api/`, dan request ke origin lain hanya ke `https://fonts.googleapis.com` dan `https://fonts.gstatic.com`. Kedua origin Google dijawab test sendiri lewat `page.route` (CSS kosong dan font kosong, status 200) sehingga uji tidak bergantung pada jaringan luar, origin yang diminta dicatat sebagai bukti, dan request ke origin lain di luar edge digagalkan serta membuat test gagal; CSP tetap diterapkan browser sebelum lapisan jaringan, sehingga pelanggaran tetap terdeteksi.
- **AC-7**: Edge hanya meneruskan path berawalan `/api/` ke backend lewat `location ^~ /api/`, sehingga tidak ada location regex (termasuk aturan ekstensi tabel *Cache dan fallback*) yang mengambil path `/api/`; path API berekstensi seperti `/api/x.json` sampai ke backend. Edge mengirim header `X-Request-Id` bernilai `$request_id` (header yang sama dari client ditimpa) dan mengosongkan setiap header pada daftar *Header alamat client* sehingga tidak terkirim; backend memperlakukan header alamat dan skema apa pun dari request sebagai tidak dipercaya. Request yang masih memilih `location ^~ /api/` sesudah normalisasi nginx (location dipilih dari `$uri`, yaitu path yang `%XX` nya sudah di decode, segmen titiknya sudah diselesaikan, dan garis miring gandanya sudah digabung) dan yang path mentahnya (bagian `$request_uri` sebelum `?`) memuat segmen `.` atau `..`, `%2e`, `%2f`, atau `%5c` dalam huruf besar atau kecil, atau karakter `\`, ditolak 400 `{"error":"Invalid request"}` tanpa diteruskan; query string tidak diperiksa aturan ini, sehingga `?returnUrl=%2Fhome` tetap diteruskan. Path mentah berawalan `/api/` yang dinormalisasi ke luar `/api/` (misalnya `/api/%2e%2e/x` menjadi `/x`, `/api/..` menjadi `/`, dan `/api/x/..%2f..%2fhealth/live` menjadi `/health/live`) tidak menuntut 400: edge menjawabnya seperti path hasil normalisasi menurut tabel *Cache dan fallback* dengan *Header dokumen* (`index.html` 200 untuk path tanpa ekstensi, file itu atau 404 untuk path berekstensi) dan tidak meneruskannya ke backend, sedangkan path yang naik di atas root (misalnya `/api/../../x`) ditolak nginx sebelum location dipilih. Tidak ada URL lewat edge yang menghasilkan jawaban route `/health/` backend. Body lebih dari 1.024 byte mendapat 413 `{"error":"Payload too large"}` tanpa diteruskan; batas ini sama dengan `maxRequestBodySize` backend dan keduanya hanya berubah bersama (DEP-001). Backend yang tidak terjangkau memberi 502 `{"error":"Bad gateway"}`, kecuali selama jendela resolusi ulang upstream sesudah backend berhenti (AC-9), saat edge boleh menjawab 502 atau 504; upstream yang menerima koneksi tetapi tidak menjawab dalam 10 detik memberi 504 `{"error":"Gateway timeout"}`. Jawaban yang dibuat edge sendiri untuk `/api/` memakai `Content-Type: application/json` dan `Cache-Control: no-store`, dan setiap jawaban `/api/` memuat header tabel *Header API*, kecuali galat yang dibuat nginx sebelum location dipilih, yaitu 400 untuk baris header HTTP/1.1 yang melebihi `large_client_header_buffers` dan untuk path yang naik di atas root, serta 414 untuk request line HTTP/1.1 yang melebihi batas itu, yang mendapat header tabel *Header dokumen* dan body bawaan nginx tanpa versi. Pada HTTP/2 nginx membandingkan batas itu dengan panjang setiap field (termasuk `:path`) sesudah dikodekan HPACK (kompresi header HTTP/2 yang memakai kode Huffman, sehingga teks dapat menjadi lebih pendek): field yang sesudah dikodekan masih di dalam batas diproses seperti biasa walaupun teks aslinya lebih dari 8k, dan field di atas batas membuat request diakhiri tanpa jawaban (AC-10), bukan 400 atau 414; spec tidak menambah batas panjang sesudah di decode (keputusan 74 dan 75). Penghapusan header alamat client, penimpaan `X-Request-Id`, `Host` yang diteruskan, 504 nyata, dan 413 yang tidak sampai ke upstream dibuktikan lewat *Upstream stub*; 502 dan path berekstensi dibuktikan lewat backend nyata. Tidak ada jawaban edge maupun backend yang memuat header `Access-Control-*`, termasuk untuk request dengan `Origin` asing dan preflight `OPTIONS` dengan `Access-Control-Request-Method`; frontend dan API berbagi origin, sehingga daftar origin lintas origin yang diizinkan kosong.
- **AC-8**: `deploy/compose.yaml` mendefinisikan tepat service `edge`, `backend`, `postgres`, dan `migrate` (profil `migrate`) serta network `public`, `app` (`internal: true`), dan `data` (`internal: true`) menurut tabel *Topologi*; hanya `edge` yang mempublikasikan port. Probe membuktikan tabel *Keterjangkauan*: host menjangkau edge tetapi tidak mempunyai port backend atau PostgreSQL, network `app` menjangkau backend tetapi tidak PostgreSQL, network `data` menjangkau PostgreSQL, `docker network inspect` menunjukkan `Internal: true` untuk `app` dan `data`, dan network internal tidak menjangkau alamat di luar host. Klaim terakhir hanya dihitung bila probe kontrol dari network `public` ke alamat yang sama berhasil; bila kontrol gagal, check `egress_blocked` bernilai `not_run` dengan alasan `egress_control_failed` dan langkah tidak berstatus `passed`. Field deklaratif (restart, stop grace, log driver dan opsinya, CPU, memory, PIDs, shm, read only, tmpfs, `cap_drop`, `security_opt`, `dns_opt`, network, port, secret, healthcheck, `depends_on`, profil, dan key environment) dibuktikan dari `docker compose -f deploy/compose.yaml config --no-interpolate --format json` tanpa override, sehingga keluarannya tidak memuat nilai credential, dan sama dengan tabel *Topologi*; override uji hanya menambah `restart: "no"`, `pull_policy: never`, dan label. Keadaan runtime dibuktikan `docker inspect` atas container `edge`, `backend`, dan `postgres` milik project serta container `foundation-deploy-migrate-<hex>` dari AC-3: network, `Config.User` tepat `101:101` (edge), `1000:1000` (backend dan runner), dan `postgres` (image PostgreSQL), `NanoCpus`, `Memory`, `PidsLimit`, `ShmSize`, `ReadonlyRootfs`, `Tmpfs`, `CapDrop` `["ALL"]`, `SecurityOpt` `["no-new-privileges:true"]`, `DnsOptions` (`["ndots:0"]` pada edge, kosong pada yang lain), `RestartPolicy.Name` `no` (nilai override), `StopTimeout`, healthcheck, dan `LogConfig`. Environment yang ditambahkan ke setiap container itu (selisih dengan `Config.Env` image) sama persis dengan tabel *Environment per service*, sehingga backend tidak menerima credential migrator atau admin, runner tidak menerima credential backend kecuali pada run provisioning (yang hanya hidup selama langkah provisioning dan dihapus `--rm`), dan edge tidak menerima credential apa pun.
- **AC-9**: Pada topologi yang berjalan: (1) `docker compose stop backend` (SIGTERM) menghentikan backend dalam 6 detik dengan exit code 0 dan baris log `stopped`; selama backend berhenti edge tetap menjawab `/` 200, dan `/api/status` yang diminta setiap 500 ms menjawab 502 `{"error":"Bad gateway"}` atau 504 `{"error":"Gateway timeout"}` (keduanya JSON edge dengan header *Header API*) selama jendela resolusi ulang, lalu paling lama 15.000 ms sesudah `stop` selesai jawabannya 502 dan tetap 502 selama backend berhenti; sesudah `start backend`, `/api/status` lewat edge kembali menjawab 404 `{"error":"Not found"}` dari backend dalam 20 detik tanpa restart edge. (2) Backend yang dibuat ulang dengan `up -d --force-recreate --no-deps backend` kembali diteruskan edge dalam 20 detik tanpa restart edge, karena nama upstream diresolusi ulang. Bila probe langkah 1 *Build plan* membuktikan parameter `resolve` tidak bekerja, build memakai cadangan keputusan 35 (b) tanpa kembali ke `/architect`: frasa "tanpa restart edge" pada (1) dan (2) diganti "sesudah `docker compose restart edge`", sisa kriteria tetap, dan laporan build mencatat varian yang dipakai. (3) `docker compose stop postgres` membuat `/health/ready` 503 dalam 6 detik, sementara `/health/live` tetap 200 dan edge tetap melayani `/`; sesudah `start postgres`, `/health/ready` kembali 200 dalam 30 detik tanpa restart backend. (4) `docker compose stop edge` (SIGQUIT) menghentikan edge dengan exit code 0 dalam 15 detik. (5) `docker compose stop` atas seluruh service selesai dengan exit code 0 untuk setiap container dalam stop grace masing masing. Di luar topologi, proses `index.ts` production yang pemeriksaan readiness nya berakhir pada `connectionTimeout` pool 3 detik karena koneksi TCP ke host database tidak pernah selesai (host database berhenti atau tidak terjangkau) tetap menulis baris `stopped` lalu keluar 0 dalam 6 detik sesudah SIGTERM. Topologi tidak selalu mengambil jalur batas koneksi itu, karena `docker compose stop postgres` biasanya memberi galat koneksi yang cepat, sehingga kalimat ini dibuktikan DEP-007 pada macOS dan pada Linux, dan bukan oleh check DEP-005.
- **AC-10**: Log dibaca per container dengan `docker logs`, yang memisahkan stdout dan stderr. Setiap baris stdout edge adalah objek JSON dengan key tepat `time`, `requestId`, `method`, `path`, `status`, `bytes`, `requestTime`, `upstreamStatus`, dan `upstreamTime`, dengan tipe: `time`, `requestId`, `method`, dan `path` string; `status` dan `bytes` bilangan bulat, dengan `status` bernilai `0` untuk request yang diakhiri nginx tanpa mengirim jawaban (nginx sendiri mencatatnya `000`, misalnya stream HTTP/2 yang satu field header nya melebihi `large_client_header_buffers` sesudah dikodekan HPACK), sehingga setiap baris tetap JSON sah; `requestTime` angka detik; `upstreamStatus` dan `upstreamTime` string, kosong bila tidak ada upstream (file statis dan jawaban `return` edge). `path` adalah `$request_uri` sampai sebelum `?`. Request yang ditolak nginx sebelum URI nya selesai diurai (path yang naik di atas root seperti `/api/../../x` atau `/api/%2e%2e/%2e%2e/x`, atau request line yang tidak sah seperti `GET /a b c`) tetap tercatat satu baris dengan `status` 400 dan `upstreamStatus` kosong, tetapi `path` kosong karena `$request_uri` belum terisi; `method` juga kosong untuk request line yang tidak sah dan untuk stream HTTP/2 yang mengirim `:path` sebelum `:method`. Request line HTTP/1.1 yang melebihi `large_client_header_buffers` tercatat dengan cara yang sama, tetapi dengan `status` 414 serta `method` dan `path` kosong (keputusan 75). Baris seperti itu dicari lewat `requestId`, yang sama dengan header `X-Request-Id` jawaban 400 atau 414 nya, dan `path` tidak diisi dari sumber lain (keputusan 66). Tidak ada IP client, user agent, referer, query string, header, cookie, atau body di log edge. Error log edge ditulis ke stderr pada level `crit`; pesan `crit` nginx yang jarang (misalnya gagal menulis file sementara) masih dapat memuat baris request, dan risiko sisa itu dicatat di `docs/rules/deployment.md`. Backend production menulis satu baris JSON per request yang sampai ke Elysia kecuali jawaban health di bawah 500 (key tepat `time`, `level`, `event` bernilai `request`, `requestId`, `method`, `path` tanpa query, `status`, `durationMs`) dan baris JSON lifecycle (key tepat `time`, `level`, `event` dari kosakata baris *Log backend production*), dengan baris `info` hanya di stdout dan baris `error` hanya di stderr; teks lifecycle development tidak berubah. Request yang ditolak Bun sebelum Elysia (body di atas `maxRequestBodySize` yang dikirim langsung ke backend dari network internal, dengan 413 tanpa body) tidak menghasilkan baris log; lewat edge request itu sudah ditolak edge dan tercatat di log edge. `requestId` backend sama dengan header `X-Request-Id` bila cocok `^[0-9a-f]{32}$`, selain itu dibuat backend. Untuk satu request lewat edge, header jawaban `X-Request-Id`, baris log edge, dan baris log backend memuat ID yang sama. Nilai sentinel yang dikirim lewat query string, header `Authorization`, `Cookie`, header bebas, dan body, serta ketiga password run dan setiap DSN run, tidak muncul di stdout maupun stderr container mana pun milik run, termasuk saat 502. PostgreSQL berjalan dengan `log_min_messages=log`, `log_min_error_statement=panic`, dan `log_error_verbosity=terse`, sehingga statement gagal yang memuat sentinel tidak masuk log. Setiap service memakai log driver `json-file` dengan `max-size` `10m` dan `max-file` `3`, dan retensi log platform paling lama 30 hari tertulis di `docs/rules/deployment.md`.
  - *Amandemen 2026-10-06 (spec [0014](../0014-akses-pengguna-lifecycle-sesi/index.md), tabel Log keamanan)*: log backend production menjadi satu baris request per request ditambah paling banyak satu baris `auth` dengan `requestId` yang sama (semula satu baris per request). Guard `onRequest` plugin auth menulis baris request nya sendiri untuk jawaban 404, 400, 403, dan 415, karena `onAfterResponse` tidak berjalan untuk jawaban itu. `parseBackendLogLine` menerima varian `event` `auth`, dan `log_correlation` memeriksa satu masuk lewat edge mempunyai baris request dan baris `auth` dengan id yang sama.
- **AC-11**: Tier cepat mendapat langkah `test:deployment:plan` sesudah `test:performance:plan`, dan tier nyata mendapat langkah `test:deployment:real` sesudah `test:readiness:real` dan sebelum `test:performance:smoke`, dengan bukti tabel *Bukti langkah deployment*. Jenis bukti baru `deployment` sah hanya bila objeknya mempunyai `schema` 1, `status` `passed` atau `failed`, dan `checks` memuat tepat nama `DEPLOYMENT_CHECKS` (diekspor `scripts/lib/gate.ts` dan diimpor orkestrasi) dalam urutan itu dengan `status` `passed`, `failed`, atau `not_run`; `status` `passed` menuntut setiap check `passed`; dan langkah yang keluar 0 tetapi buktinya tidak sah atau berstatus selain `passed` gagal dengan alasan `evidence_invalid`. `test:report` menulis field `deployment` sesudah `performance` dan bagian *Deployment* di `report.md`, dan `outOfScope` per push menjadi `[{ area: 'capacity_profiles', feature: 12 }]`. Registry `tests/scenarios/deployment.json` memuat DEP-001 sampai DEP-009 dengan DEP-006 bertanda `critical`, `check:test-discovery` menerima config Playwright baru, dan kedua file workflow GitHub tidak berubah. SIGINT, SIGTERM, atau SIGHUP pada orkestrasi menghapus project Compose, container probe dan stub, container `foundation-deploy-migrate-<hex>`, image, dan folder sementara milik run itu saja, dengan nama eksplisit dan tidak lewat pola nama atau label, menolak nama project yang tidak cocok `^foundation-deploy-[0-9a-f]{12}$` atau berbeda dengan run itu, lalu keluar 130, 143, atau 129 dengan pembersihan selesai di bawah masa tenggang tier nyata 180.000 ms (DEP-008).
- **AC-12**: `bun run test:report:release` (`bun --no-env-file scripts/gate-report.ts release`) menghitung ulang laporan per push dari bundle `fast`, `real`, dan `security` serta laporan kapasitas dari bundle `capacity` di `.local/feature-11/evidence/` pada checkout commit kandidat, menurut *Perhitungan laporan release*: identitas CI setiap laporan dibaca dari `candidate.ci` manifest bundle nya, tidak dari variable `GITHUB_*` proses laporan, sehingga bundle per push dari run `push` dan bundle kapasitas dari run `workflow_dispatch` yang berbeda dapat dinilai bersama. Template laporan release dan aturan testing merujuk perintah ini, dan tidak ada script, workflow, atau langkah yang melakukan deploy atau mendorong image.

## Decision

**Chosen option**: Opsi 1, edge nginx dari image frontend yang mengakhiri TLS dan meneruskan `/api/` ke backend, backend serta PostgreSQL di network internal, migration sebagai job image runner, topologi rujukan di `deploy/compose.yaml`, bukti per push di tier nyata, dan status kesiapan release dari perintah laporan terpisah.

Bangun tiga image dari root monorepo dengan base yang dipin digest dan file ignore daftar izin per Dockerfile, tambahkan health dan readiness internal pada kedua komposisi backend, lalu buktikan topologi itu dengan container lokal tanpa registry dan tanpa deploy. Seluruh keputusan diambil agent atas delegasi pemilik pada 2026-10-05; alasan, pilihan, dan pertimbangan setiap pertanyaan ada di [rationale.md](rationale.md).

**Implementation skills**: `elysiajs` (skill pengguna, `~/.claude/skills/elysiajs/`), terutama `references/lifecycle.md` untuk urutan `onRequest` dan `onAfterResponse` serta `references/deployment.md` untuk bundle `--minify-whitespace --minify-syntax` tanpa minify identifier.

**Key invariants**:

1. Tidak ada build image dari konteks selain root monorepo, tidak ada `ARG` atau build secret untuk credential, dan tidak ada image yang didorong ke registry atau di deploy oleh kode proyek.
2. Edge adalah satu satunya container dengan port terpublikasi; backend, runner, dan PostgreSQL hanya berada di network internal, sehingga tidak dapat menjangkau internet.
3. Health hanya di luar `/api/`, sehingga edge tidak pernah meneruskannya; readiness tidak menulis database, menjalankan paling banyak satu query per proses (penanda dilepas hanya saat query selesai, termasuk sesudah batas 5.000 ms), dan jawabannya tidak memuat data.
4. Provisioning, migration, dan seed hanya berjalan sebagai job image runner yang dipanggil eksplisit; startup backend tidak menunggu dan tidak menjalankan migration.
5. Komposisi development, route spec 0006, teks lifecycle development, dan perilaku `serve` tidak berubah; plugin logging dipasang hanya bila `createApp` menerima `log`, dan didaftarkan sebelum route agar berlaku untuk semuanya.
6. Log tidak pernah memuat query string, header, cookie, body, IP client, DSN, SQL, pesan error, atau stack; correlation ID dari client tidak dipercaya edge.
7. Kebijakan CSP tidak dilonggarkan di kode build untuk meloloskan test. Nilai CSP pada tabel *Header dokumen*, termasuk tiga nama policy Trusted Types, sudah final; pelanggaran lain oleh library membuat DEP-006 gagal dan dicatat sebagai temuan pada laporan build, bukan diselesaikan dengan menghapus atau menambah directive. Perubahan nilai CSP hanya lewat pembaruan spec ini dengan alasan tertulis.
8. Orkestrasi hanya menghapus project, container, image, dan folder yang dibuat run itu, dengan nama eksplisit yang lolos penjaga; tidak menyentuh project Compose `foundation` atau container suite lain.
9. Status release `ready` tidak pernah memberi izin deploy dan tidak memicu langkah apa pun; identitas CI yang menjadi dasarnya dibaca dari manifest, tidak dari environment proses laporan.
10. Edge dan backend memakai batas body yang sama (1.024 byte); keduanya hanya berubah bersama.
11. Edge meneruskan ke backend hanya request yang `$uri` hasil normalisasinya memilih `location ^~ /api/` dan yang path mentahnya bebas penanda traversal AC-7; path lain, termasuk path mentah `/api/` yang dinormalisasi ke luar `/api/`, tidak pernah sampai ke backend.
12. Backend tidak menurunkan alamat, skema, atau host client dari header request, termasuk `Host`; URL absolut hanya dibangun dari konfigurasi (keputusan 72).

**Security model**: Pelaku publik hanya mencapai edge pada HTTPS dan redirect HTTP. Edge melayani file statis tanpa credential, menolak path traversal dan body besar, tidak mempercayai header correlation dari client, mengosongkan header alamat dan skema client pada daftar *Header alamat client*, dan tidak mengirim CORS, sehingga tidak ada origin lain yang mendapat izin membaca jawaban API lewat browser. Backend dan fitur berikutnya memperlakukan header alamat atau skema apa pun dari request sebagai tidak dipercaya, begitu pula `Host`, yang edge teruskan apa adanya dari client pada listener tanpa `server_name`; URL absolut seperti tautan reset password dan redirect dibangun hanya dari konfigurasi (keputusan 72). Header dokumen menerapkan CSP tanpa script inline, Trusted Types, larangan frame, HSTS, dan `nosniff` sesuai aturan keamanan bahwa header dokumen ditangani server yang mengirim dokumen. Operator dengan akses Docker setara root di host dan dapat membaca environment container lewat `docker inspect`, seperti aturan infrastruktur; karena itu setiap service hanya menerima credential miliknya. Password `foundation_admin` ada di environment service `postgres` (`POSTGRES_PASSWORD`, dipakai entrypoint spec 0002 hanya saat cluster dibuat) dan di `.env.deploy` operator sebagai `FOUNDATION_POSTGRES_PASSWORD`, dalam file yang sama dengan DSN kedua role runtime. Berbeda dengan `.env.infrastructure` aturan infrastruktur, file itu tidak memisahkan credential admin dari credential runtime, sehingga pihak yang dapat membaca `.env.deploy` mendapat ketiganya; risiko ini diterima sampai secret manager platform dipilih, dan `docs/rules/deployment.md` meminta file itu diperlakukan sebagai secret setingkat admin (keputusan 71); DSN admin dan password role hanya ada di shell operator dan diteruskan pada run provisioning, tidak pernah ke backend, edge, atau run migration biasa; image tidak memuat secret. Rotasi password role, pembaruan sertifikat TLS, dan izin file key ditulis di `docs/rules/deployment.md`. Backend memakai role runtime minimum tanpa DDL, runner memakai migrator, dan pemisahan network membatasi siapa yang dapat menjangkau PostgreSQL. Container berjalan non root, root filesystem read only (kecuali PostgreSQL), tanpa capability, `no-new-privileges`, dengan batas CPU, memory, dan proses. TLS di dalam host antara edge, backend, dan PostgreSQL tidak dipakai karena lalu lintas itu tidak keluar dari network internal satu host; jalur yang melintasi jaringan lain wajib TLS dan memerlukan spec baru. Tidak ada autentikasi, rate limit login, atau CSRF karena belum ada operasi yang mengubah data (fitur 15). Bukti ini tidak membuktikan ketahanan terhadap banjir trafik, yang tetap membutuhkan kontrol edge platform, dan tidak memindai kerentanan paket OS ketiga image (`bun audit` hanya mencakup paket npm); keduanya tertulis di `boundary` dan `release.md`. Status `ready` bersandar pada identitas CI yang ditulis run itu sendiri ke manifest, sehingga pihak yang dapat mengubah bundle lokal dapat memalsukannya; karena status itu tidak pernah memberi izin deploy, risiko ini diterima dan dinyatakan di `release.md`.

## Consequences

**Positive**:

- Pertama kali ada artefak deployment yang dapat dibangun, dijalankan, dan dibuktikan dengan perintah yang sama di lokal dan CI, terikat pada pohon sumber yang sama dengan bukti gate.
- Health production tersedia tanpa membuka diagnostik ke publik, dan readiness memberi sinyal urutan migration sebelum trafik yang dibaca platform atau operator; Compose rujukan sendiri tidak menahan edge sampai backend siap.
- Status kesiapan release dihitung dari bukti CI yang diunduh untuk commit yang sama, tidak ditulis tangan, dan tidak dapat disalahartikan sebagai izin deploy.

**Negative / tradeoffs**:

- Tier nyata per push bertambah beberapa menit (build tiga image, termasuk `bun install` lengkap untuk frontend, dan topologi lima container); durasi di runner GitHub belum terukur dan timeout job 45 menit dapat perlu dinaikkan lewat perubahan workflow tersendiri.
- Empat base image baru dirawat manual (Node, Bun yang sudah ada, nginx), dan pembaruan Bun harus mengubah Dockerfile serta `tests/performance/images.json` bersama.
- `style-src 'unsafe-inline'` tetap ada karena style komponen Angular disisipkan saat runtime tanpa nonce; injeksi style lebih terbatas dari injeksi script, tetapi tetap risiko yang diterima.
- Browser pengguna memuat font dari Google, sehingga alamat IP pengguna terlihat oleh pihak ketiga sampai font di host sendiri.
- Tidak ada TLS di dalam host dan tidak ada rate limit; topologi multi host atau database terkelola memerlukan spec baru.
- Mematikan inline critical CSS sedikit menunda tampilan pertama karena stylesheet harus diunduh sebelum render.
- Backend production kini menulis satu baris log per request, yang menambah volume log.
- Request yang ditolak nginx sebelum URI nya selesai diurai (path di atas root, request line yang tidak sah) tercatat tanpa `path`, dan untuk sebagian juga tanpa `method`, sehingga operator tidak dapat melihat path yang dicoba dari log edge; baris itu hanya membawa `requestId`, `status` 400, dan waktu (keputusan 66).
- Pada HTTP/2 batas header edge diukur sesudah dikodekan HPACK, sehingga header yang teks aslinya lebih dari 8k tetapi kodenya lebih pendek tetap diteruskan ke backend, sedangkan lewat HTTP/1.1 header yang sama ditolak 400; request line HTTP/1.1 yang terlalu panjang mendapat 414, bukan 400 (keputusan 74 dan 75).
- Batas body 1.024 byte di edge dan backend kelak harus dinaikkan bersama bila fitur membutuhkan body lebih besar.
- Status `ready` bersandar pada identitas CI yang ditulis run sendiri ke manifest dan tidak diverifikasi ke GitHub, dan paket OS image tidak dipindai kerentanannya; keduanya dinyatakan di `release.md`.
- Redirect HTTP mengasumsikan HTTPS publik pada port 443 dan memantulkan `Host` client sampai `server_name` ditetapkan.

**Neutral**:

- Image ID adalah identitas build lokal; digest registry baru ada bila pipeline deploy kelak mendorong image, dan build belum dibuktikan dapat direproduksi byte per byte.
- Tier kapasitas tetap mengukur komposisi development; laporan kapasitas menyebutnya di `outOfScope`.
- Worker belum mempunyai image; fitur 16 menambah Dockerfile dan baris topologi sendiri.
- Production tanpa `DATABASE_URL` tetap dapat berjalan tetapi tidak pernah `ready`.
- Setiap migration baru wajib memperbarui `REQUIRED_MIGRATION` pada commit yang sama; DEP-001 gagal bila konstanta tertinggal dari file migration terakhir.

# Rationale: Build container dan deployment terpisah

## Context

> Catatan premis: pemilik belum memilih penyedia cloud atau platform target, dan tugas ini melarang deploy ke mana pun maupun mendorong image ke registry. Karena itu fitur ini tidak dapat membuktikan deployment nyata. Yang dapat dibuktikan adalah artefak (image), kontrak operasi (environment, port, health, urutan langkah), dan satu topologi rujukan yang netral terhadap penyedia, dijalankan dengan container lokal. Platform nyata, TLS di luar satu host, dan pipeline deploy menjadi spec tersendiri sesudah pemilik memilih platform. Topik ini juga memuat beberapa keputusan (image, topologi, health, log, status release); keputusan itu saling terikat pada satu topologi yang dibuktikan bersama, sehingga ditulis dalam satu spec seperti spec 0010 dan 0011, bukan umbrella.

Fitur 13 pada scope meminta artefak frontend dan backend yang siap deployment dengan konfigurasi dan kontrol operasi yang dapat dibuktikan. Selesai ketika: image memakai root monorepo sebagai build context; secret tidak masuk image atau bundle; migration berjalan sebagai langkah deployment tersendiri; konfigurasi TLS, header frontend, CORS, jaringan, resource, health dan readiness, serta shutdown sesuai topologi; log dan correlation ID tidak membocorkan data; kandidat release memiliki bukti dan status `ready`, `blocked`, atau `incomplete` yang benar. Datanya memakai schema dan role hasil specs tanpa privilege tambahan; retensi log serta kebijakan endpoint admin, metrics, dan OpenAPI diputuskan sebelum deployment; bukti kesiapan tidak otomatis memberi izin deploy. Worker mendapat image sendiri pada fitur 16.

Keadaan saat ini (dibaca dari kode pada 2026-10-05):

- `createApp('production')` di `apps/backend/src/app.ts` hanya memasang `onError`, sehingga setiap path production menjawab 404. `GET /api/status` dan `GET /api/readiness` hanya development (spec 0001 AC-4, spec 0006 AC-1). `index.ts` membuat pool hanya bila `DATABASE_URL` ada, mendengar `HOST` dan `PORT` (production boleh `0.0.0.0`), dan berhenti dalam lima detik pada SIGTERM atau SIGINT dengan teks `Backend stopped`. Test READY-001 menjalankan backend production tanpa `DATABASE_URL` dan mengharapkan proses tetap berjalan.
- Build production frontend (`bun run build:frontend`) statis; `/` adalah halaman pengantar tanpa request API, dan `/kesiapan` hanya ada di development (spec 0006 AC-9, spec 0007). SDK memakai `provideApiConfiguration('')`, yaitu origin yang sama. `provideMaterialSymbols()` memuat stylesheet dari `fonts.googleapis.com`, dan READY-007 hanya mengizinkan origin Google Fonts itu. `index.html` hasil build memuat satu `<script>` inline milik Beasties (penyisip critical CSS bawaan Angular) dan satu `<style>` inline.
- Migration dan seed berjalan lewat `database/migrate.ts` dan `database/seed.ts` dengan role migrator, provisioning lewat `database/provision.ts` dengan admin (spec 0004, 0005); runner menurunkan root dari lokasi modulnya dan hanya membutuhkan modul bawaan Bun serta `libs/server/database/client.ts`.
- `docker-compose.yml` root hanya infrastruktur; aturan infrastruktur menyebut file deployment runtime diatur terpisah. Aturan backend, database, dan worker sudah menamai lokasi `apps/backend/Dockerfile`, `database/Dockerfile`, dan Dockerfile frontend dengan build context root.
- Gate spec 0010 mempunyai tier `fast`, `real`, dan `security`, laporan dengan kandidat release, `outOfScope` `deployment_image` fitur 13, dan tindak lanjut untuk mengikat laporan pada identitas image. Spec 0011 menjalankan backend development dari `oven/bun:1.4.2-slim` yang dipin dengan root filesystem read only, user host, dan tanpa capability. INFRA-001 melarang kata `docker` di `scripts/**/*.ts`.

Kekuatan yang membatasi keputusan: aturan keamanan meminta HTTPS production, header dokumen dari server yang mengirim dokumen, CORS hanya untuk origin yang dinyatakan, kebijakan akses eksplisit untuk debug, metrics, admin, dan OpenAPI, container non root berbatas resource tanpa secret di image, akses database terpisah dari jaringan publik, dan log tanpa body, cookie, atau token. Aturan testing meminta bukti dengan komponen nyata, status `ready`, `blocked`, dan `incomplete` yang jujur, dan bukti kesiapan bukan izin deploy. Satu manifest dan lockfile root berlaku untuk semua image. Tanpa keputusan ini, image dapat menyalin `.env` checkout (yang memang ada di mesin ini), health production tidak ada sehingga orkestrator tidak dapat membedakan proses hidup dari siap, dan status release tetap ditulis tangan.

## Options considered

### Opsi 1: Edge nginx dari image frontend, backend dan database di network internal, topologi rujukan Compose

Image frontend berisi build Angular dan nginx yang mengakhiri TLS, menambah header dokumen, melayani file statis, dan meneruskan `/api/` ke backend di network internal. Backend berjalan dari bundle Bun, PostgreSQL dari image proyek di network internal lain, dan migration sebagai job image runner. `deploy/compose.yaml` adalah topologi rujukan yang juga dipakai orkestrasi uji. (basis: aturan keamanan tentang header dokumen dan pemisahan akses database, aturan infrastruktur tentang file deployment terpisah, pola pin dan hardening spec 0010 dan 0011)

**Pros**:
- Origin sama untuk frontend dan API, sehingga CORS tidak diperlukan dan SDK tidak berubah.
- Satu titik publik dengan TLS dan header, backend dan database tidak terpublikasi.
- File topologi yang sama dipakai operator dan uji, sehingga dokumentasi tidak menyimpang dari yang dibuktikan.

**Cons**:
- nginx adalah tool baru yang dipin dan dirawat, dengan konfigurasi yang perlu dibuktikan (pewarisan `add_header`, resolusi upstream).
- Compose adalah alat Docker; platform lain menerjemahkan kontrak yang sama ke format nya sendiri.

### Opsi 2: Edge proxy terpisah dari server statis frontend

Tiga container HTTP: proxy edge (nginx atau Caddy) untuk TLS dan routing, server statis frontend, dan backend.

**Pros**:
- Pemisahan tanggung jawab edge dan aset statis, mudah mengganti salah satunya.

**Cons**:
- Satu container dan satu hop tambahan tanpa kebutuhan yang terukur; header dokumen tetap harus ditetapkan di dua tempat atau diteruskan.

### Opsi 3: Backend Elysia juga melayani frontend statis

Satu image Bun melayani `index.html`, aset, dan API, dengan TLS di depan oleh platform.

**Pros**:
- Paling sedikit bagian bergerak; tanpa tool baru.

**Cons**:
- Bertentangan dengan judul fitur (deployment terpisah) dan aturan yang menyebut image frontend dan backend sendiri.
- Header dokumen, cache aset, dan proxy menjadi kode aplikasi yang harus ditulis dan diamankan sendiri; backend tidak dapat diskalakan terpisah dari aset.

### Opsi 4: Origin terpisah untuk frontend dan API

Frontend statis di satu origin (misalnya CDN) dan backend di origin lain dengan CORS daftar izin dan URL backend saat bootstrap.

**Pros**:
- Cocok dengan hosting statis terkelola dan CDN.

**Cons**:
- Menambah CORS, preflight, dan konfigurasi URL runtime yang harus dibuktikan; cookie sesi fitur 15 kelak lebih sulit (`SameSite`, `__Host-`).
- Bergantung pada penyedia yang belum dipilih.

## Rationale

Masalah utamanya adalah membuktikan kontrol operasi tanpa platform. Opsi 1 menempatkan semua kontrol yang diminta scope (TLS, header, CORS, network, resource, health, shutdown, log) pada komponen yang dapat dijalankan lokal dan dipindahkan ke platform mana pun sebagai kontrak: tiga image, satu daftar environment per service, dua path health, dan urutan langkah. Origin yang sama menutup CORS dan URL runtime sekaligus, dan cocok dengan rekomendasi aturan keamanan untuk cookie `__Host-` saat fitur 15 tiba. Opsi 3 paling sederhana tetapi memindahkan header dan proxy ke kode aplikasi yang harus dibuat dan diamankan sendiri, dan aturan proyek sudah memilih image terpisah. Opsi 2 dan 4 menambah bagian atau konfigurasi tanpa kekuatan yang memintanya sekarang.

Pemakaian ulang menentukan detail: base Bun yang sama dengan spec 0011, penjaga route readiness spec 0006, runner database spec 0005 apa adanya, pola orkestrasi dan pembersihan `readiness-real.ts` dan `performance-real.ts`, serta tier, manifest, dan laporan spec 0010. Bukti diletakkan di tier nyata per push karena tier itu sudah mempunyai Docker, PostgreSQL yang dipin, dan Chromium, dan karena kandidat release spec 0010 hanya berasal dari push ke `main`; dengan begitu kandidat release selalu membawa bukti image. Status `ready`, `blocked`, atau `incomplete` dihitung ulang dari bundle, bukan dari `report.json` yang dapat basi, agar status tidak lebih kuat dari bukti nya.

## Keputusan agent atas delegasi pemilik

Pemilik proyek mendelegasikan keputusan desain ("jika membutuhkan /architect anda bisa menjalankannya dengan mengambil keputusan sendiri berdasarkan rekomendasi anda"). Tidak ada manusia selama run. Percakapan desain dijalankan sebagai pertimbangan internal: setiap pertanyaan dicatat dengan pilihan, rekomendasi, dan pilihan akhir. Semua keputusan berikut diambil oleh agent pada 2026-10-05 atas delegasi tersebut, tanpa konfirmasi manusia.

Framing yang disimpulkan: mode FEATURE (kemampuan deployment baru di atas stack dan gate yang ada, dengan membaca kode yang harus diintegrasikan), platform backend API, frontend statis, tooling CLI, dan CI; stack dari `AGENTS.md` (Bun 1.4.2, Elysia 1.4.30, Angular 22.2 dengan `@ojiepermana/angular` 22.1.14, PostgreSQL 18 image proyek, Docker); build approach Tracer Bullet dari scope; workflow GA. Tidak ada spec yang tumpang tindih untuk diperbarui atau digantikan; spec 0001, 0002, 0004, 0005, 0006, 0008, 0009, 0010, dan 0011 menjadi batasan. Tidak ada data regulasi yang disentuh.

**Tahap kebutuhan**

1. **Pekerjaan inti dan batas.** Pilihan: (a) tiga image, topologi rujukan, health internal, log, bukti per push, dan status release, tanpa deploy dan registry; (b) ditambah pipeline deploy ke platform contoh; (c) hanya Dockerfile tanpa bukti topologi. Dipilih (a): (b) dilarang dan memilih penyedia atas nama pemilik; (c) tidak membuktikan TLS, header, network, atau shutdown. Di luar cakupan: TLS antarservice, image worker, kapasitas dengan image deployment, backup, autentikasi.
2. **Bentuk topologi.** Pilihan: Opsi 1 sampai 4 di atas. Dipilih Opsi 1, alasan di *Rationale*.
3. **Titik TLS.** Pilihan: (a) edge container dengan sertifikat dan key yang di mount saat runtime; (b) load balancer platform, container hanya HTTP; (c) TLS di setiap hop. Dipilih (a): dapat dibuktikan lokal dan tetap berlaku bila platform kelak meneruskan TCP; (b) bergantung pada platform yang belum ada; (c) menambah sertifikat internal tanpa jaringan yang tidak dipercaya di topologi satu host.
4. **TLS ke database.** Pilihan: (a) tanpa TLS di network internal satu host, wajib TLS saat database berada di host atau layanan lain dengan spec baru; (b) `verify-full` sekarang dengan CA sendiri. Dipilih (a): (b) membutuhkan opsi CA di `createDatabasePool`, `hba_file` production, dan file key milik UID 26 di mount, semuanya tanpa jaringan yang dilintasi pada topologi ini. Tidak ada aturan atau spec yang mewajibkan TLS internal; tindak lanjut spec 0002 tentang TLS dicatat tetap terbuka.
5. **Format topologi rujukan.** Pilihan: (a) `deploy/compose.yaml` ditambah langkah operator, dipakai juga oleh uji; (b) orkestrasi `docker run` di test saja; (c) manifest Kubernetes. Dipilih (a): (b) membuat topologi hanya ada di kode test; (c) memilih platform dan tidak dapat dibuktikan tanpa cluster. Compose root tetap infrastruktur saja; file ini terpisah sesuai aturan infrastruktur.
6. **Tempat bukti.** Pilihan: (a) langkah baru tier nyata per push; (b) tier dan workflow manual baru seperti kapasitas; (c) lokal saja. Dipilih (a): perkiraan beberapa menit per push masih wajar, kandidat release per push membawa bukti image, dan tidak ada workflow yang berubah. (b) menambah file workflow dan pengikatan antarrun; (c) tidak memberi bukti CI.
7. **Status kesiapan release.** Pilihan: (a) perintah `test:report:release` yang menghitung ulang laporan per push dan kapasitas dari bundle; (b) status di `test:report` per push; (c) hanya di template manual. Dipilih (a): bukti kapasitas berasal dari workflow lain, sehingga (b) selalu `incomplete` di CI; (c) membiarkan status ditulis tangan. Sesudah cross check, identitas CI setiap laporan dibaca dari manifest bundle nya (`bundleCi`), bukan dari `GITHUB_*` proses laporan, karena satu proses tidak pernah sekaligus berevent `push` dan `workflow_dispatch`, dan pemilik release menjalankan perintah ini lokal tanpa variable itu.

**Tahap data**

8. **Schema dan data persisten.** Tidak ada entitas, migration, role, atau grant baru; pertanyaan schema `AGENTS.md` tidak berlaku. Readiness memakai `SELECT` yang sudah ada.

**Tahap stack dan tool**

9. **Server edge.** Pilihan: (a) nginx 1.30.5 alpine (Docker Official Image, jalur stable); (b) Caddy; (c) HAProxy; (d) server Bun buatan sendiri. Dipilih (a): matang, konfigurasi header, cache, dan proxy standar, `$request_id` bawaan untuk correlation ID, dan resolusi ulang upstream dengan parameter `resolve` di open source. Caddy unggul pada ACME otomatis yang tidak dipakai di sini; HAProxy tidak melayani file statis; (d) berarti menulis reverse proxy sendiri.
10. **Base runtime backend.** Pilihan: (a) `oven/bun:1.4.2-slim` yang sudah dipin; (b) `oven/bun:1.4.2-distroless`; (c) alpine (musl); (d) Oracle Linux 10 dengan binary Bun. Dipilih (a): digest yang sama sudah terbukti di spec 0011 dengan root filesystem read only dan tanpa capability, mempunyai user `bun`, dan sama dengan engines. (b) lebih kecil tetapi berjalan sebagai root secara default dan belum diuji; dicatat sebagai pilihan kedua. (c) belum diuji; (d) menambah unduhan dan verifikasi binary.
11. **Paket backend.** Pilihan: (a) satu bundle `bun build --target bun --minify-whitespace --minify-syntax` dijalankan Bun yang dipin; (b) `bun build --compile` menjadi binary; (c) source dengan `node_modules` production. Dipilih (a): tanpa `node_modules` di image, runtime tetap Bun yang dipin, dan `HEALTHCHECK` dapat memakai `bun -e`. Skill `elysiajs` merekomendasikan (b) dan flag minify yang sama tanpa minify identifier; (b) adalah pilihan kedua karena binary menyembunyikan versi runtime dari pin. (c) membawa dependency Angular karena manifest root bersama.
12. **Builder frontend.** Pilihan: (a) `node:24.21.0-trixie-slim` dengan binary Bun disalin dari image Bun yang dipin, menjalankan `bun install --frozen-lockfile` dan `bun run build:frontend`; (b) build di host lalu menyalin `dist`; (c) Bun saja. Dipilih (a): build hermetic dengan script root yang sama, OS sama dengan image Bun. (b) bergantung pada keadaan checkout; (c) Angular CLI tidak resmi didukung di Bun.
13. **Image runner migration.** Pilihan: (a) source `database/` dan `libs/server/database/` di image Bun slim; (b) bundle runner. Dipilih (a): runner menurunkan root dan direktori migration dari lokasi modul, sehingga bundle akan mengubah perilaku yang sudah dibuktikan spec 0005.
14. **Lokasi pin.** Pilihan: (a) digest di `FROM` Dockerfile dengan DEP-001 yang mencocokkan Bun dengan `tests/performance/images.json` dan tag dengan `engines`; (b) file pin baru. Dipilih (a): satu sumber per image tanpa file ketiga yang dapat menyimpang.
15. **Agent Skills dan MCP untuk tool baru (nginx, Docker).** Pilihan sesuai `internal/tool-discovery.md`: cari, sebut sendiri, tolak, atau nanti. Rekomendasi skill adalah mencari, tetapi pencarian menjalankan paket yang diunduh (`npx skills find`) dan pemasangan memerlukan pilihan manusia, sehingga dipilih "nanti": tidak ada pencarian atau pemasangan, dan bagian `## Follow-up` spec mencatatnya untuk `/sync` atau pemilik.
16. **Kontrol konteks build.** Pilihan: (a) file ignore daftar izin per Dockerfile ditambah `.dockerignore` root daftar tolak; (b) `.dockerignore` root saja. Dipilih (a): file `.env` checkout ada di mesin ini; daftar izin membuat path baru tidak pernah ikut tanpa perubahan yang terlihat di review.
17. **Bukti tanpa secret.** Pilihan: (a) build dari salinan `mkdtemp` dengan sentinel tertanam lalu memindai filesystem, config, dan history; (b) memeriksa daftar file image saja; (c) menanam sentinel di checkout. Dipilih (a): tanpa mengubah checkout; (b) tidak membuktikan file yang lolos; (c) mengubah working tree pengembang. Sesudah cross check, (a) dipertebal menjadi dua lapisan: probe konteks `FROM scratch` dengan salinan byte persis file ignore membuktikan semantik file ignore secara langsung (sebagian besar sentinel tidak akan pernah sampai ke image akhir walau file ignore rusak, karena bundle backend dan `dist` frontend tidak menyalinnya), dan pemindaian image akhir tetap menjadi lapisan kedua. Image runner menyalin folder `database/` utuh dari konteks daftar izin, sehingga `database/seeds/` yang belum ada tidak menggagalkan build dan file ignore yang rusak langsung terlihat di filesystem image.

**Tahap antarmuka**

18. **Permukaan health.** Pilihan: (a) `/health/live` dan `/health/ready` di luar `/api/` pada kedua komposisi, tanpa login, hanya jaringan internal; (b) `/api/health/*` yang diblokir edge; (c) port manajemen terpisah. Dipilih (a): edge yang hanya meneruskan `/api/` membuat health tidak publik secara konstruksi, bukan karena daftar tolak; (c) menambah listener dan konfigurasi.
19. **Semantik readiness.** Pilihan: (a) siap bila migration terakhir yang dibutuhkan build (`REQUIRED_MIGRATION`) tercatat; (b) jumlah migration seperti route development; (c) hanya koneksi database. Dipilih (a): memaksa urutan migration sebelum trafik dan dapat diuji (503 lalu 200 tanpa restart). (b) menyatakan siap pada database yang belum dimigrasi; (c) tidak membuktikan hak baca role runtime.
20. **Concurrency readiness.** Pilihan: (a) pemanggil bersamaan berbagi hasil pemeriksaan yang berjalan; (b) 429 seperti route development. Dipilih (a): probe orkestrator dan healthcheck dapat tumpang tindih, dan 429 akan dibaca sebagai tidak siap; query tetap paling banyak satu per proses. Penanda dilepas hanya saat query selesai, seperti `createReadinessCheck` spec 0006, dan pemanggil sesudah batas 5.000 ms selama query masih macet langsung mendapat 503 tanpa query baru; tanpa aturan ini database yang dibekukan membuat setiap probe memulai query baru dan menghabiskan pool lima koneksi milik route lain.
21. **OpenAPI.** Pilihan: (a) kedua operasi masuk `openapi.json` dengan tag `health`; (b) disembunyikan dari dokumen. Dipilih (a): dokumen mencakup seluruh route nyata, checker dan SDK tetap sinkron, dan kontrak operator tertulis di satu tempat. SDK mendapat `HealthService` yang tidak dipakai frontend.
22. **Jawaban galat edge untuk API.** Pilihan: (a) body JSON `{"error":...}` untuk 400, 413, 502, dan 504; (b) halaman bawaan nginx. Dipilih (a): bentuk sama dengan galat backend, sehingga adapter SDK memetakannya sebagai kegagalan umum tanpa HTML.
23. **Correlation ID.** Pilihan: (a) edge membuat `$request_id`, menimpa header client, meneruskan dan mengembalikan `X-Request-Id`; backend menerima hanya 32 heksadesimal dan membuat sendiri selain itu; (b) mempercayai ID dari client; (c) tanpa correlation ID. Dipilih (a): (b) memungkinkan injeksi log dan pemalsuan; (c) tidak memenuhi scope.
24. **Cakupan log backend.** Pilihan: (a) satu baris JSON per request di production kecuali health yang sukses, ditambah lifecycle JSON, lewat sink yang hanya diberikan `index.ts` production; (b) hanya galat 5xx; (c) tanpa log request. Dipilih (a): correlation dari edge ke backend dapat dibuktikan lewat request 404 biasa karena production belum mempunyai route yang dapat gagal 5xx; sink yang disuntik menjaga test READY lama tetap diam dan development tidak berubah.

**Tahap keamanan**

25. **CSP.** Pilihan: (a) header statis dengan `script-src 'self'`, `style-src 'self' 'unsafe-inline'` ditambah origin Google Fonts, Trusted Types, dan `inlineCritical: false`; (b) nonce per request lewat `sub_filter` nginx dan atribut `ngCspNonce`; (c) hash script Beasties yang dihitung saat build. Dipilih (a): tanpa script inline sama sekali, dan dokumentasi Angular menyebut `'unsafe-inline'` untuk style ketika nonce tidak dapat dibuat. (b) membuat `index.html` tidak dapat di cache, bergantung pada substitusi setiap jawaban, dan nonce placeholder yang bocor bila substitusi gagal; (c) masih membutuhkan style inline dan pecah saat Angular mengubah script nya. Risiko style inline diterima di Consequences. Sesudah cross check, `trusted-types` memuat juga `angular#components`: `@angular/cdk` 22.2.0 (`fesm2022/private.mjs`) membuat policy itu dengan `createHTML` identitas untuk HTML yang sudah lewat sanitizer Angular (`_setInnerHtml`) dan untuk registry ikon Material, lalu memanggil `console.error` bila CSP menolaknya. Policy itu milik library Angular resmi dan tidak membuka bypass sanitizer, sedangkan `angular#unsafe-bypass` dan `angular#unsafe-jit` tetap ditolak. Objek `optimization` production ditulis lengkap karena `normalizeOptimization` di `@angular/build` 22.2.0 mengubah field objek yang tidak ditulis menjadi `false` (minify JS dan CSS akan mati), dan `fonts.inline` bernilai `false` agar build image tidak mengambil font dari jaringan; `index.html` tidak memuat tautan font, sehingga hasil build tidak berubah karena itu.
26. **Header lain.** Dipilih HSTS `max-age=31536000` tanpa `includeSubDomains` dan `preload` (domain belum ada dan subdomain milik pemilik tidak diketahui), `nosniff`, `Referrer-Policy: no-referrer` (juga menutup referer ke Google Fonts), `X-Frame-Options: DENY` sebagai pelengkap `frame-ancestors`, COOP dan CORP `same-origin`, dan `Permissions-Policy` dengan fitur yang dikenal saja agar Chromium tidak mencetak galat console. COEP tidak dipakai karena memblokir stylesheet Google Fonts.
27. **CORS.** Pilihan: (a) tanpa CORS, daftar origin lintas origin kosong; (b) daftar izin satu origin. Dipilih (a): origin sama; header CORS apa pun hanya menambah permukaan.
28. **Kebijakan endpoint production.** Dipilih tabel *Kebijakan endpoint production*: OpenAPI tidak dilayani, route diagnostik hanya development, health internal, admin dan metrics tidak ada sampai spec pemiliknya. Pilihan lain (OpenAPI publik, metrics di `/api/metrics`) membuka informasi tanpa kebutuhan.
29. **Data log dan retensi.** Pilihan retensi: (a) paling lama 30 hari di platform, rotasi `json-file` 10m × 3 per container lokal; (b) 90 hari; (c) tanpa batas. Dipilih (a): log tidak memuat data pribadi atau secret, dan 30 hari cukup untuk investigasi insiden tanpa menimbun data; kebutuhan hukum diputuskan saat produk mempunyai audiens. Log edge tanpa IP, user agent, referer, dan query; error log `crit` karena level `error` nginx mencetak baris request lengkap dengan query; PostgreSQL `log_min_messages=log`, `log_min_error_statement=panic`, dan `log_error_verbosity=terse` karena pesan error dan statement dapat memuat nilai data, termasuk password pada `CREATE ROLE` provisioning yang gagal.
30. **Hardening dan angka resource.** Dipilih non root, read only (kecuali PostgreSQL yang menulis `PGDATA`), `cap_drop ALL`, `no-new-privileges`, dan batas tabel *Topologi*: backend 1 CPU dan 512 MiB sama dengan environment spec 0011, PostgreSQL sama dengan batas development, edge 0,5 CPU dan 128 MiB, runner 0,5 CPU dan 256 MiB. Angka ini nilai rujukan, bukan klaim kapasitas.
31. **Pemisahan network.** Pilihan: (a) `public`, `app` internal, dan `data` internal; (b) satu network bersama. Dipilih (a): edge tidak dapat menjangkau PostgreSQL, dan backend serta runner tidak mempunyai jalur keluar ke internet, yang juga membatasi dampak SSRF kelak.

- Status release: identitas CI dibaca dari manifest (`bundleCi` dan parameter `reportCi`), kode `image_differs` ditambah, `candidate_differs` dibandingkan dengan checkout, prosedur unduh keempat artifact ditulis di `docs/rules/deployment.md`, dan DEP-004 memakai dua identitas CI serta kasus bundle lokal dan commit lain.
- Konteks build: probe konteks per Dockerfile ditambah sebagai lapisan pertama; `checkFrontendBundle` dijalankan atas file statis hasil export image.
- Edge: `location ^~ /api/`, map traversal hanya atas path dan menolak `\`, batas body 1.024 byte sama dengan backend, daftar *Header alamat client*, `mime.types`, header dokumen di level `server`, tipe nilai log, jendela 502 atau 504 sesudah backend berhenti, dan *Upstream stub* untuk header yang dikosongkan, penimpaan `X-Request-Id`, 504 nyata, dan 413.
- Operasi: field deklaratif dari `compose config --no-interpolate` tanpa override, container runner bernama untuk inspect, `Config.User` numerik, pengecualian run provisioning, kontrol egress dari network `public`, log lewat `docker logs` per stream, pemindaian password dan DSN di log, batas total orkestrasi 1.200.000 ms, dan batas waktu untuk setiap perintah.
- Test: DEP-008 (sinyal orkestrasi) dan DEP-009 (readiness pada PostgreSQL nyata), aturan penanda readiness sesudah batas, route Google Fonts dan listener lewat init script pada DEP-006, READY-003 dan SDK-005 beserta bentuk akhir `app.ts`, `DEPLOYMENT_CHECKS` dengan kolom kriteria, dan tabel *Dokumen yang diperbarui*.
- Keamanan dan dokumen: `angular#components` di `trusted-types`, objek `optimization` lengkap, cara pembuktian ALPN, ticket, dan TLS 1.1, rotasi password role dan sertifikat, izin file key, asumsi port 443, risiko sisa pesan `crit`, batas tanpa pemindaian paket OS, dan klaim credential admin yang diperbaiki.

Bagian rekomendasi yang tidak diikuti (satu baris alasan per butir):

- Tanpa `COPY database/` utuh untuk runner (celah konteks build): ditolak, karena probe konteks kini membuktikan file ignore secara langsung, sedangkan salinan folder utuh menangani `database/seeds/` yang belum ada dan membuat file ignore rusak terlihat di image akhir.
- `pause` dan `unpause` backend untuk mengamati 504 (celah jendela 502): ditolak, karena *Upstream stub* yang menerima koneksi tanpa menjawab memberi 504 nyata tanpa membekukan backend topologi.
- Pemeriksaan runtime bahwa `main-*.js` terminifikasi (celah `optimization`): ditolak, karena DEP-001 membandingkan seluruh objek `optimization` yang menentukan minify, dan budget production tetap berlaku.
- Menaikkan `maxRequestBodySize` backend ke 16 KiB (celah batas body): ditolak, karena belum ada route yang membutuhkan body, dan batas yang lebih kecil di kedua sisi lebih aman.
- Mencari `docker push`, `docker login`, dan `docker tag` di seluruh `docs/` (celah dokumen): dipersempit ke `deploy/`, workflow, `README.md`, dan `docs/rules/deployment.md`, karena spec dan aturan sah menyebut perintah itu sebagai larangan.
- Mengurangi risiko sisa pesan `crit` nginx dengan level `alert` atau `emerg` (celah log): ditolak, karena level itu menyembunyikan galat `crit` yang dibutuhkan untuk diagnosis; risiko sisa dicatat di `docs/rules/deployment.md` dan sentinel tetap dipindai di log.
- Membuktikan tidak adanya session ticket pada TLS 1.3 (celah TLS): ditolak, karena OpenSSL tetap mengirim ticket stateful dari session cache; klaim dipersempit ke TLS 1.2.
- Port publik redirect dari variable `FOUNDATION_EDGE_PUBLIC_PORT` (celah redirect 308): ditolak untuk sekarang, karena topologi rujukan memakai port 443 dan domain belum ada; asumsi dicatat dan `server_name` tetap tindak lanjut.

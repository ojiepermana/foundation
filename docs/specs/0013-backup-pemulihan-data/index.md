# 0013. Backup dan pemulihan data

**Date**: 2026-10-06
**Status**: Accepted

## Summary

Database `foundation` di backup setiap hari dan sebelum setiap migration memakai `pg_dump` format custom dari image PostgreSQL 18 proyek yang sama, dijalankan sebagai container sekali jalan di network data dengan role baru `foundation_backup` yang hanya dapat membaca. Backup tidak memuat role maupun password role; pemulihan selalu masuk ke target baru yang terisolasi, membuat ulang role lewat provisioning dengan password baru, lalu membuktikan data, riwayat migration, dan readiness sebelum trafik dipindahkan. Sasaran yang diputuskan: kehilangan data paling lama 24 jam (RPO), pemulihan paling lama 4 jam (RTO), retensi 35 hari dengan 7 backup terbaru selalu disimpan, akses hanya untuk pemilik operasi, dan penyimpanan di folder host terkunci ditambah salinan di luar host yang dibuat di luar kode proyek. Bukti restore tercatat per push pada kandidat release lewat tier nyata, dan per environment lewat catatan latihan restore; kode proyek tidak pernah mengunggah backup ke mana pun. Credential backup tidak dapat menulis tetapi tetap setingkat admin untuk kerahasiaan, karena dapat membaca seluruh data dan verifier password role, dan checksum hanya mendeteksi kerusakan, sehingga operator membandingkan sha256 dengan catatan terpisah sebelum setiap restore.

## Requirements

**User stories**:

- Sebagai pemilik operasi, Anda dapat membuat, memeriksa, dan memulihkan backup dengan perintah Compose yang tetap, tanpa credential admin pada job backup dan tanpa password role di dalam file backup.
- Sebagai pemilik operasi yang menghadapi insiden, Anda mempunyai langkah tertulis untuk memulihkan data ke target baru, merotasi credential, dan mencabut sesi (setelah fitur 15), dengan sasaran waktu yang jelas.
- Sebagai pemilik release, Anda melihat bukti bahwa backup kandidat dapat dipulihkan dengan data dan migration yang konsisten, dan catatan latihan restore terbaru untuk environment tujuan.

**Acceptance criteria**:

- **AC-1**: `docs/rules/backup.md` (baru) menetapkan setiap baris tabel *Keputusan operasi*: RPO paling lama 24 jam lewat backup `scheduled` harian ditambah backup `pre-migration` sebelum setiap migration pada database yang sudah berisi data (paling sedikit satu baris di `common.schema_migrations`), dan paling lama 25 jam bila host hilang karena salinan di luar host boleh terlambat 1 jam; RTO paling lama 4 jam dari keputusan memulihkan sampai edge target baru menerima trafik; retensi 35 hari dengan 7 backup lengkap terbaru selalu disimpan di folder host, ditambah aturan salinan di luar host baris *Retensi*; cakupan seluruh database `foundation` tanpa role, password role, dan pengaturan level database; akses, termasuk bahwa `.env.backup` setingkat admin untuk kerahasiaan karena role backup dapat membaca seluruh data dan verifier password semua role di `pg_authid`, dan bahwa setiap role memakai password acak `openssl rand -hex 24`; lokasi penyimpanan (path absolut, folder dibuat `install -d -m 0700` dengan owner UID dan GID container, file yang disalin kembali di `chown` ke UID itu dan `chmod 0600`, aturan nilai `.env.deploy` berlaku untuk `.env.backup`); enkripsi; checksum yang hanya mendeteksi kerusakan dan bukan keaslian; pemantauan `check` dengan ambang 26 jam; dan latihan restore paling lambat setiap 30 hari per environment yang menyimpan data nyata. Dokumen itu juga memuat runbook restore baris *Runbook restore*, prosedur insiden baris *Prosedur insiden*, dan string wajib tabel *Dokumen yang diperbarui* secara harfiah.
- **AC-2**: `database/provision.ts` menangani role `foundation_backup` menurut tabel *Matriks role backup* dan tabel *Kasus provisioning role backup*: role dibuat hanya bila belum ada dan `FOUNDATION_BACKUP_PASSWORD` diberikan, lalu diverifikasi setiap kali role ada. Variable yang ada tetapi kosong atau kurang dari 16 karakter selalu gagal `Missing or invalid FOUNDATION_BACKUP_PASSWORD`, ada atau tidaknya role; hanya variable yang tidak ada berarti role backup tidak dipakai. Tanpa role dan tanpa variable itu, output dan perilaku provisioning sama persis dengan sebelumnya, sehingga test DATA lama dan setiap harness yang memanggil provisioning tetap lulus tanpa diubah. Setiap kasus tabel *Kasus provisioning role backup* menghasilkan exit, pesan, dan report tepat seperti tabel itu, dan kasus yang gagal tidak mengubah apa pun. Pada PostgreSQL 18 nyata: `foundation_backup` tanpa `SET ROLE` ditolak membaca `common.schema_migrations`; sesudah `SET ROLE pg_read_all_data` dapat membacanya, tetapi `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `CREATE TABLE users.x (id int)`, dan `CREATE TEMP TABLE` ditolak; `SET ROLE foundation_owner` ditolak; `foundation_backend` tidak dapat `SET ROLE pg_read_all_data`; runner migration tetap lulus `verifyIdentity` dengan role backup ada; dan batas yang didokumentasikan terbukti apa adanya, yaitu sesudah `SET ROLE pg_read_all_data` role itu dapat membaca `pg_catalog.pg_authid`.
- **AC-3**: `deploy/backup.yaml` mendefinisikan tepat service `backup` (profil `backup`) dan `restore` (profil `restore`) serta network `data` dan `restore_data` yang keduanya `external`, menurut tabel *Topologi backup*: tanpa port, tanpa kunci `build`, image hanya lewat variable, dan environment tepat menurut tabel itu. `docker compose --env-file .env.backup -f deploy/backup.yaml --profile backup run --rm backup create <alasan>` dengan alasan `scheduled`, `pre-migration`, atau `manual` keluar 0, mencetak satu baris `Backup created: <nama>.dump (<ukuran> bytes, sha256 <heksadesimal>)`, dan meninggalkan di `FOUNDATION_BACKUP_DIR` tepat tiga file baru `<nama>.dump`, `<nama>.dump.sha256`, dan `<nama>.json` dengan mode 0600 menurut *Nama dan isi backup*: dump hasil `pg_dump` dengan argumen tepat baris *Perintah pg_dump*, file checksum tepat satu baris yang menamai dump itu dan lulus `sha256sum --check --strict`, manifest satu baris JSON ringkas dengan key tepat dalam urutannya, dan `pg_restore --list` atas dump memuat header `dbname: foundation` serta entri `TABLE DATA` untuk setiap tabel sumber; pemeriksaan isi itu dijalankan container alat milik test (*Resource uji*). Kegagalan keluar 1 dengan tepat satu baris kategori tabel *Pesan script*, tidak meninggalkan file apa pun yang dibuat run itu, tidak menyentuh file yang sudah ada, dan tidak menjalankan retensi. Hal itu dibuktikan dengan komponen nyata untuk `connection`, `invalid connection string`, `permission denied` (termasuk DSN role login selain `foundation_backup`, misalnya superuser `foundation_admin`), `row level security`, `lock timeout`, `wrong database`, `interrupted` (TERM, INT, dan `docker stop` saat `pg_dump` menunggu lock, keluar 143 atau 130), `Backup directory unavailable`, `Backup directory must be mode 0700`, dan `Backup already exists`, dan hanya lewat pemeriksaan statis BKP-001 untuk `time limit`, `killed`, `archive invalid`, `internal`, dan `Retention failed`, karena keadaan itu tidak dapat dipicu komponen nyata tanpa mengubah konstanta script. Tidak ada baris di `deploy/backup.yaml` maupun `deploy/backup/*.sh` yang mengunggah atau menyalin backup ke luar folder backup, dan setiap service hanya bergabung dengan satu network external, yaitu network data project yang `internal: true` menurut spec 0012: `backup` dengan `data` (network sumber dari `.env.backup`) dan `restore` dengan `restore_data`, yang namanya hanya dari shell, sehingga restore tanpa `FOUNDATION_RESTORE_DATA_NETWORK` berhenti di Compose sebelum container dibuat.
- **AC-4**: Secret disaring. Teks dump yang diurai `pg_restore --file=-` memuat sentinel baris fixture (kontrol positif) tetapi tidak memuat password run mana pun (admin, migrator, backend, backup sumber dan target), DSN run, sentinel `ALTER DATABASE foundation SET foundation.backup_probe`, `CREATE ROLE`, `PASSWORD`, maupun `SCRAM-SHA-256`. Keluaran stdout dan stderr setiap container `backup` dan `restore` milik run, manifest, file checksum, dan `.local/feature-14/restore.json` tidak memuat password atau DSN run, termasuk saat `FOUNDATION_BACKUP_DATABASE_URL` maupun `FOUNDATION_ADMIN_DATABASE_URL` rusak dengan dua bentuk yang terbukti dicetak ulang libpq (spasi di password dan persen encoding tidak sah) dengan password sentinel. Password DSN tidak pernah ada di argumen proses alat PostgreSQL (baris *Pemisahan DSN*): selama `pg_dump` backup dan `psql` restore berjalan, argumen setiap proses container run yang dibaca `docker top` tidak memuat password, dan `--dbname` memuat DSN tanpa password. `scripts/serve.ts` menghapus `FOUNDATION_BACKUP_PASSWORD` dan `FOUNDATION_BACKUP_DATABASE_URL` dari environment proses anak, seperti variable provisioning yang sudah ada.
- **AC-5**: Restore ke target terisolasi membuktikan data dan migration konsisten. Pada cluster PostgreSQL 18 baru milik run (container dan network sendiri, tidak pernah sumber): provisioning dengan empat password baru, `restore <nama>.dump` keluar 0 dengan `Restore completed: <nama>.dump`, provisioning ulang mencetak hanya `verified` termasuk `database privileges: verified`, runner migration dengan set migration yang sama dengan sumber mencetak `Migrations: 0 applied, <n> skipped`, `database/fingerprint.ts --digest` dengan role backup target sama persis dengan fingerprint sumber yang diambil sesudah backup tanpa penulisan di antaranya (tabel, jumlah baris, digest, sequence, jumlah dan nama migration terakhir), `GET /health/ready` dari `createApp('production')` dengan pool `foundation_backend` berpassword baru menjawab 200, dan password migrator, backend, serta backup milik sumber gagal autentikasi di target. Durasi dari awal run Compose `restore` BKP-004 sampai readiness 200 pertama dicatat sebagai `restore.durationMs` dan paling lama 300.000 ms. Fingerprint yang menunggu lock pada target berakhir `Fingerprint failed` dengan exit 1 sesudah `lock_timeout` 30 detik, tidak menunggu tanpa batas.
- **AC-6**: Restore menolak target dan backup yang tidak aman, setiap kali keluar 1 dengan pesan tabel *Pesan script* dan tanpa mengubah target menurut kolom bukti tabel *Urutan uji target*: nama tidak sah (path, `..`, atau tidak cocok pola), backup tidak lengkap, checksum tidak cocok, file checksum yang menamai file lain, archive tidak sah dengan checksum yang cocok, `FOUNDATION_ADMIN_DATABASE_URL` tidak ada, identitas target bukan `foundation_admin` di database `foundation`, target belum diprovision, target tidak kosong, versi major header dump berbeda dengan target, dan `pg_restore` yang gagal sesudah semua pemeriksaan lulus (transaksi tunggal dibatalkan, pesan `Restore failed: pg_restore`). Runner migration dengan set migration repository atas target yang dipulihkan dari sumber yang riwayatnya memuat migration fixture tambahan keluar 1 dengan `Migration history drift` tanpa perubahan. TERM atau INT saat `psql` restore menunggu lock pada langkah 9 *Urutan restore* keluar 143 atau 130 dengan tepat satu baris `Restore failed: interrupted` tanpa mengubah target.
- **AC-7**: Retensi dan pemeriksaan. Sesudah `create` berhasil, script menghapus menurut tabel *Retensi*: 7 backup lengkap terbaru tidak pernah dihapus, backup lengkap yang lebih tua dari 35 hari dihapus, file sisa (`.partial` dengan nama yang ditulis `create`, atau set tidak lengkap) yang lebih tua dari 24 jam dihapus, dan file lain, subfolder, serta symlink tidak pernah disentuh, termasuk `.foundation-*.partial` dengan nama lain (misalnya nama yang memuat baris baru); setiap backup lengkap yang dihapus tercatat tepat satu baris `Backup removed: <nama>` dan setiap file sisa yang dihapus tepat satu baris `Leftover removed: <file>`, dalam urutan tabel *Retensi*. `check` memeriksa backup lengkap terbaru menurut tabel *Check*: keluar 0 dengan `Latest backup: <nama> (<jam> h old)` bila file checksum nya sah dan cocok dan umurnya paling lama 26 jam, dan keluar 1 dengan `Backup directory unavailable`, `Backup directory must be mode 0700`, `No backup found`, `Backup checksum mismatch: <nama>` (diperiksa lebih dulu dari umur), atau `Latest backup too old: <nama> (<jam> h old)`.
- **AC-8**: Bukti restore tercatat pada kandidat. `tests/integration/database/backup.test.ts` berjalan di `test:database:real` dan menulis `.local/feature-14/restore.json` menurut *Isi restore.json*; langkah `test:database:real` di `scripts/lib/gate.ts` mendeklarasikan file itu sebagai bukti wajib berjenis `data`; `tests/orchestration/database-real.ts` berubah menurut baris *Perubahan database-real.ts* (hapus `restore.json` lama sebelum run, label secret baris *Label secret* di daftar pindai dan environment build, pemindaian `restore.json` bersama JUnit, batas `bun test` 600.000 ms, dan kegagalan bila `restore.json` tidak ada atau tidak `passed`); registry `tests/scenarios/backup.json` memuat BKP-001 sampai BKP-008 dan lolos `test:scenarios`; setiap container, network, project Compose, dan folder sementara test didaftarkan pada `tests/orchestration/signal-cleanup.ts` sebelum dibuat dan dihapus dengan panggilan yang dikenali GATE-009, dan `tests/integration/gate/signal-cleanup.test.ts` berubah menurut baris *Perubahan GATE-009*, sehingga `bun run test:gate` lulus; `tsconfig.tooling.json` dan `tsconfig.contract.json` memuat file test dan `database/fingerprint.ts` baru sehingga `typecheck:tooling` dan `typecheck:contract` memeriksanya; dan `bun run test:ci:real` lulus dengan `restore.json` di bundle tier nyata.
  - *Amandemen 2026-10-06 (spec [0014](../0014-akses-pengguna-lifecycle-sesi/index.md), tabel Keputusan hook backup)*: `restore.json` mendapat field `sessions` (`{ beforeRevokeStatus: 200, afterRevokeStatus: 401, revoked: number, rerunRevoked: 0 }`, dengan `sessions` di himpunan `failures`), diisi BKP-009 sebagai test terakhir `backup.test.ts`: sesi yang dibuat di sumber sebelum backup diterima di target sesudah restore, ditolak sesudah `revoke-sessions --all --apply`, dan run kedua mencabut 0. Batas `bun test` `test:database:real` naik dari 600.000 ms menjadi 900.000 ms dengan grace 75.000 ms tetap, masih di bawah batas langkah tier nyata 1.500.000 ms.
- **AC-9**: Bukti environment dan prosedur. `docs/testing/restore-drill-template.md` memuat heading tetap baris *Template latihan restore*; satu catatan latihan pertama `docs/testing/restore-drills/<YYYY-MM-DD>-topologi-rujukan-lokal.md` ditulis dari runbook restore pada `deploy/compose.yaml` dengan image yang dibangun lokal dari checkout kandidat, berisi commit (`git rev-parse HEAD` saat latihan), pohon input build (dihitung sebelum catatan ditulis, perintah baris *Value sourcing*), ID keempat image (frontend, backend, runner, dan PostgreSQL), nama dan checksum backup beserta hasil pembandingan dengan catatan di luar folder backup, waktu setiap langkah, jumlah baris per tabel tanpa nilai data, hasil migration dan readiness, RPO terukur dan RTO latihan terukur (berakhir pada readiness 200 karena edge tidak dijalankan pada latihan lokal), hasil pemeriksaan isolasi network data langkah 10 *Runbook restore*, serta pembersihan, tanpa password atau DSN. `docs/rules/deployment.md` meneruskan `-e FOUNDATION_BACKUP_PASSWORD` pada langkah provisioning, menambah langkah backup `pre-migration` sebelum migration, dan menautkan `docs/rules/backup.md`; template laporan release mendapat bagian *Backup dan pemulihan*. Langkah pencabutan sesi pada runbook dan prosedur insiden tertulis `tidak berlaku sampai fitur 15` beserta kontrak hook baris *Hook fitur 15*.
  - *Amandemen 2026-10-06 (spec [0014](../0014-akses-pengguna-lifecycle-sesi/index.md), tabel Dokumen yang diperbarui)*: string wajib BKP-001 untuk `docs/rules/backup.md` mengikuti tabel itu di spec 0014: langkah 8 *Runbook restore* mencabut seluruh sesi lewat `revoke-sessions --all --apply`, ketiga baris insiden dan paragraf *Hook fitur 15* memuat string barunya, dan string `tidak berlaku sampai fitur 15` keluar dari daftar sehingga kalimat AC ini yang memintanya tidak berlaku lagi. Tabel lama di bawah tidak diubah; BKP-001 menerapkan amandemen ini saat membaca tabel itu.

## Decision

**Chosen option**: Opsi 1, backup logis `pg_dump` format custom dari image PostgreSQL 18 proyek sebagai job Compose sekali jalan dengan role baca saja, restore `pg_restore` ke target baru yang diprovision ulang, dan bukti per push di suite database nyata.

Backup harian dan sebelum migration dibuat dengan alat yang sudah ada di image `foundation-postgres:18-pinned`, disimpan sebagai tiga file (dump, checksum, manifest) di folder host terkunci, dan dipulihkan hanya ke target terisolasi yang kemudian diverifikasi oleh provisioning, runner migration, fingerprint, dan readiness yang sudah ada. (basis: aturan keamanan tentang backup yang dapat dipulihkan dan privilege minimum, spec 0002, 0004, dan 0005, serta probe 2026-10-06 di rationale.) Seluruh keputusan diambil agent atas delegasi pemilik pada 2026-10-06; pertanyaan, pilihan, rekomendasi, dan alasannya ada di [rationale.md](rationale.md).

## Feature design

**Data model sketch**: Tidak ada tabel, schema, migration, atau seed baru, dan pertanyaan schema `AGENTS.md` dijawab tidak berlaku: metadata backup disimpan sebagai file manifest dan checksum di samping dump, tidak di database (keputusan 9 rationale). Satu objek tingkat cluster bertambah, yaitu role login `foundation_backup` (tabel *Matriks role backup*), yang mengubah matriks role spec 0004 lewat catatan amandemen. Backup mencakup seluruh database `foundation`: `common` (termasuk `common.schema_migrations`), `users`, `auth`, ACL schema `public`, dan schema yang ditambahkan fitur berikutnya, tanpa daftar schema yang harus dirawat.

**Keputusan operasi**:

| Hal | Keputusan |
| --- | --- |
| RPO (batas data yang boleh hilang) | Paling lama 24 jam. Backup `scheduled` setiap hari pukul 02.00 UTC, backup `pre-migration` sebelum setiap migration pada database yang sudah berisi data (paling sedikit satu baris di `common.schema_migrations`; deploy pertama tanpa baris itu tidak membutuhkannya), dan backup `manual` sebelum operasi data berisiko. Bila host hilang, RPO paling lama 25 jam karena salinan di luar host boleh terlambat 1 jam. RPO lebih kecil dari 24 jam membutuhkan arsip WAL (catatan perubahan PostgreSQL) dan spec baru |
| RTO (batas waktu pemulihan) | Paling lama 4 jam dari keputusan memulihkan sampai edge target baru menerima trafik, mengikuti *Runbook restore*; diukur dan dicatat pada setiap latihan. Latihan lokal tanpa edge mencatat RTO latihan sampai readiness 200 |
| Retensi | 35 hari, dengan 7 backup lengkap terbaru selalu disimpan walau lebih tua; penghapusan otomatis hanya sesudah backup baru berhasil (tabel *Retensi*). Jaminan 7 backup berlaku di folder host. Salinan di luar host menyimpan paling sedikit 7 versi terbaru lewat aturan jumlah versi; bila platform hanya mendukung aturan umur 35 hari, wajib ada alert bila tidak ada objek baru selama 27 jam (ambang `check` ditambah 1 jam keterlambatan salinan), dan penghapusan lifecycle dihentikan selama alert itu aktif |
| Cakupan | Seluruh database `foundation` tanpa filter schema. Tidak mencakup role, password role, pengaturan level database atau role, maupun database lain di cluster; semuanya dibuat ulang provisioning |
| Akses | Hanya pemilik operasi, yaitu pemegang secret setingkat admin (`.env.deploy`), yang membaca, menyalin, dan memulihkan backup. Job terjadwal hanya memegang `.env.backup` (credential `foundation_backup` dan path folder), yang tidak dapat menulis tetapi setingkat admin untuk kerahasiaan: sesudah `SET ROLE pg_read_all_data` role backup membaca seluruh data dan verifier password SCRAM semua role di `pg_authid` (probe cross check). Karena itu setiap role memakai password acak `openssl rand -hex 24`, dan kebocoran `.env.backup` ditangani seperti kebocoran `.env.deploy`. Identitas penyimpanan di luar host: unggah hanya tulis, restore hanya baca, hapus hanya lewat lifecycle. CI dan pengembang tidak pernah menyentuh backup environment; test hanya memakai data fixture di folder sementara |
| Penyimpanan | Folder host absolut (path relatif dianggap Compose sebagai nama volume) di luar checkout dan di luar volume Docker, misalnya `/var/backups/foundation/postgres`, dibuat `install -d -m 0700 -o <uid> -g <gid>` dengan UID dan GID container (default 26), sebaiknya di disk lain dari volume `pgsql_data`. File yang disalin kembali dari luar host di `chown <uid>:<gid>` dan `chmod 0600`. `.env.backup` mengikuti aturan nilai `.env.deploy` (penggantian `$` oleh Compose dan persen encoding DSN). Environment yang menyimpan data nyata wajib mempunyai salinan di luar host, di failure domain berbeda (host, disk, atau zona), dengan versioning atau object lock, paling lambat 1 jam sesudah backup dibuat; salinan itu dibuat alat platform, tidak oleh kode proyek |
| Enkripsi | Enkripsi at rest wajib pada setiap lokasi penyimpanan (disk terenkripsi atau enkripsi layanan penyimpanan) dan enkripsi transport ke salinan di luar host. Enkripsi sisi client belum dipakai; keputusannya menjadi hook fitur 15 sebelum hash credential dan sesi tersimpan. Checksum SHA 256 hanya mendeteksi kerusakan, bukan keaslian: sebelum restore, operator membandingkan sha256 dump dengan catatan di luar folder backup (langkah 1 *Runbook restore*) |
| Pemantauan | `backup check` sesudah setiap backup terjadwal; alert bila job backup atau `check` keluar bukan 0, atau bila job tidak berjalan. Ambang 26 jam (RPO ditambah 2 jam toleransi jadwal). Penjadwal menyimpan log nya, termasuk baris `Backup created:`, paling sedikit 35 hari di luar folder backup sebagai catatan sha256 yang independen |
| Latihan restore | Setiap environment yang menyimpan data nyata: paling lambat setiap 30 hari, sebelum penggunaan production pertama, dan sesudah perubahan `deploy/backup.yaml`, `deploy/backup/*.sh`, role provisioning, atau pin image PostgreSQL. Dicatat dengan `docs/testing/restore-drill-template.md` |
| Bukti kandidat | Setiap push lewat BKP-003 sampai BKP-007 di `test:database:real` dan `.local/feature-14/restore.json` di bundle tier nyata |

**Matriks role backup** (amandemen matriks spec 0004; baris role lain tidak berubah):

| Aspek | `foundation_backup` | Perbaikan otomatis |
| --- | --- | --- |
| Pembuatan | `CREATE ROLE foundation_backup LOGIN NOINHERIT NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS PASSWORD <literal>` hanya bila role belum ada dan `FOUNDATION_BACKUP_PASSWORD` diberikan; literal dibuat `pg_catalog.quote_literal` seperti role lain | Tidak berlaku |
| Atribut | `rolcanlogin` true, `rolinherit` false, `rolsuper`, `rolcreatedb`, `rolcreaterole`, `rolreplication`, `rolbypassrls` false | Tidak; menyimpang gagal `Role drift: foundation_backup` |
| Membership | Tepat satu baris: anggota `foundation_backup`, role `pg_read_all_data`, `admin_option` false, `inherit_option` false, `set_option` true. Tidak ada baris lain yang anggota atau role nya `foundation_backup` | Baris itu dibuat bila hilang (`GRANT pg_read_all_data TO foundation_backup WITH ADMIN FALSE, INHERIT FALSE, SET TRUE`); baris lain atau opsi menyimpang gagal `Role membership drift` |
| Database `foundation` | `CONNECT` saja tanpa grant option | `CREATE` atau `TEMPORARY` tambahan diperbaiki dengan `REVOKE ALL ON DATABASE foundation FROM foundation_backup` lalu `GRANT CONNECT` (report `database privileges: repaired`); grant option gagal `Grant option drift`, sama dengan role runtime. Role ini masuk daftar grantee yang dikenal hanya untuk ACL database, dan masuk pemeriksaan grant option ACL database |
| Schema `public`, `common`, `users`, `auth` | Tanpa privilege langsung | Tidak; grant langsung gagal `Unknown privilege drift`, karena role ini bukan grantee yang dikenal pada ACL schema |
| `common.schema_migrations` | Tanpa grant langsung | Tidak; grant langsung gagal `Unknown privilege drift` |
| Pengaturan role | `ALTER ROLE foundation_backup IN DATABASE foundation SET search_path = pg_catalog` | Ditulis setiap run, seperti role runtime. Snapshot pengaturan sebelum dan sesudah memasukkan role ini, sehingga `search_path` yang diubah atau dihapus tercatat `database privileges: repaired` |
| Privilege efektif | `has_database_privilege` `CONNECT` true, `CREATE` dan `TEMPORARY` false; `has_schema_privilege` `USAGE` dan `CREATE` false untuk keempat schema; `pg_has_role('foundation_backup','pg_read_all_data','SET')` true; `pg_has_role` `MEMBER` false untuk `foundation_owner`, `foundation_migrator`, `foundation_backend`, dan `pg_write_all_data` | Tidak; menyimpang gagal `Effective privilege drift` |
| Report | `foundation_backup: created` atau `verified` dan `foundation_backup membership: created` atau `verified`, ditulis hanya bila role ada atau dibuat | Tidak berlaku |

Pesan baru tetap memakai kategori yang ada; regex kategori aman di `provision.ts` ditambah `Unknown privilege drift` (sekarang tercetak sebagai `Database provisioning failed`, ditemukan pada probe 2026-10-06). Daftar grantee yang dikenal pada pemeriksaan `Unknown privilege drift` dan `Grant option drift` ditulis tanpa subquery skalar per role, misalnya `x.grantee <> 0 AND x.grantee NOT IN (SELECT oid FROM pg_catalog.pg_roles WHERE rolname IN (...))`: subquery skalar untuk role yang belum ada menghasilkan NULL, dan `NOT IN` dengan NULL tidak pernah benar, sehingga pemeriksaan diam diam mati saat role backup tidak ada. Pernyataan `REVOKE` dan `GRANT` untuk `foundation_backup` hanya dijalankan bila role itu ada. Grant `pg_read_all_data` memberi baca seluruh tabel, sequence, dan katalog (termasuk `pg_authid`), tetapi tidak melewati row level security dan tidak mencakup large object; fitur yang memakai salah satunya wajib mengamandemen spec ini lebih dulu (invariant 8).

**Perintah pg_dump** (argumen tepat, dalam urutan ini): `timeout --signal=TERM --kill-after=30s 3600 pg_dump --dbname="$dsn_address" --role=pg_read_all_data --format=custom --compress=zstd --no-password --lock-wait-timeout=30s --file=/backup/.<nama>.dump.partial`. Sebelumnya, sesudah pemeriksaan folder dan nama, `split_dsn "$FOUNDATION_BACKUP_DATABASE_URL"` (baris *Pemisahan DSN*; penolakan `Backup failed: invalid connection string`), lalu `timeout --signal=TERM --kill-after=10s 60 psql -X -w -At -v ON_ERROR_STOP=1 --dbname="$dsn_address" -c 'SELECT session_user'` memeriksa role login: kegagalan `psql` dipetakan ke kategori tabel *Pesan script* dengan cadangan `pg_dump`, dan hasil selain `foundation_backup` gagal `Backup failed: permission denied`, karena role lain yang dapat `SET ROLE pg_read_all_data`, misalnya superuser `foundation_admin`, membuat backup tanpa galat (invariant 3). Kedua langkah ini berjalan sebelum file apa pun dibuat. Sesudah `pg_dump`, pemeriksaan baris *Header archive*. Tidak ada `pg_dumpall`, `--create`, `--globals-only`, `--roles-only`, filter `--schema` atau `--table`, maupun `--enable-row-security`. pg_dump 18 menjalankan `--lock-wait-timeout` sebagai `statement_timeout` pada `LOCK TABLE`, sehingga lock yang tertahan memberi `canceling statement due to statement timeout`, bukan teks `lock timeout` (probe cross check 2026-10-06).

**Perintah restore** (sesudah semua pemeriksaan tabel *Urutan restore* lulus): `timeout --signal=TERM --kill-after=30s 10800 pg_restore --dbname="$dsn_address" --clean --if-exists --single-transaction --exit-on-error --no-password /backup/<nama>.dump`. `--clean --if-exists` mengganti schema dan tabel kosong hasil provisioning target dengan isi dump dalam satu transaksi, sehingga kegagalan apa pun mengembalikan target ke keadaan sebelum restore (dibuktikan kasus `restore_failed`). `pg_restore` berjalan sebagai `foundation_admin`, superuser bootstrap, dan menjalankan SQL apa pun di dalam archive. Checksum tidak melindungi dari archive yang dipalsukan bersama checksum nya, sehingga keaslian dipastikan operator lewat langkah 1 *Runbook restore*; risiko ini diterima sampai hook fitur 15 butir (4).

**Pemisahan DSN** (`split_dsn` dan `percent_decode`, sama persis di kedua script): argumen proses terbaca setiap pengguna host lewat `/proc/<pid>/cmdline` (mode 0444; pada host Linux proses container tampil di tabel proses host), sedangkan environment proses hanya terbaca UID yang sama dan root (mode 0400), dan DSN itu sendiri sudah ada di environment container. Karena itu password tidak pernah masuk argumen (review 2026-10-06; sebelumnya `--dbname` memuat DSN lengkap, sehingga password `foundation_backup` terlihat sampai 3.600 detik dan password superuser target sampai 10.800 detik). DSN bentuk URI `postgres://` atau `postgresql://` dibagi seperti libpq: userinfo sampai `@` pertama sebelum `/` pertama, dan password sesudah `:` pertama userinfo. Password di decode persen seperti libpq ke `PGPASSWORD` yang diekspor ke alat PostgreSQL, dan URI tanpa password menjadi `dsn_address` untuk `--dbname`, sehingga libpq tetap mengurai user, host, port, database, dan parameter lain beserta pesan galatnya. Ditolak sebelum alat apa pun dipanggil, dengan `Backup failed: invalid connection string` atau `Restore failed: invalid connection string`: bentuk selain URI itu (misalnya `host=... password=...`), password dengan spasi atau persen encoding tidak sah termasuk `%00` (aturan libpq, probe review 2026-10-06), dan parameter query `password`, karena semuanya membawa password ke argumen. Keduanya diuji BKP-001 lewat bash host atas vektor DSN, dan BKP-006 membaca argumen proses nyata lewat `docker top`.

**Urutan restore** (`foundation-restore.sh <nama>.dump`; berhenti pada pemeriksaan pertama yang gagal):

1. Argumen tepat satu dan cocok pola nama ditambah `.dump`, tanpa `/`; selain itu `Usage: foundation-restore.sh <name>.dump` atau `Invalid backup name`.
2. `${FOUNDATION_ADMIN_DATABASE_URL:-}` tidak kosong (variable yang tidak ada di container sama dengan kosong, sehingga `set -u` tidak menghentikan script); selain itu `Missing FOUNDATION_ADMIN_DATABASE_URL`.
3. Ketiga file ada sebagai file biasa (bukan symlink); selain itu `Backup incomplete: <nama>`.
4. File checksum tepat satu baris yang cocok `^[0-9a-f]{64}  <nama>\.dump$` dengan nama dari argumen yang sudah divalidasi, lalu `cd /backup && sha256sum --check --strict --status <nama>.dump.sha256` keluar 0; selain itu `Backup checksum mismatch: <nama>`. Pemeriksaan baris lebih dulu wajib, karena `sha256sum --check` memeriksa file apa pun yang dinamai file checksum (probe cross check: baris yang menamai file lain lulus).
5. `pg_restore --list` atas dump keluar 0, memuat `;     dbname: foundation`, dan memuat baris `Dumped from database version:` yang cocok pola versi; selain itu `Backup archive invalid: <nama>`.
6. `split_dsn` atas DSN admin (baris *Pemisahan DSN*; penolakan `Restore failed: invalid connection string`), lalu `timeout --signal=TERM --kill-after=10s 60 psql -X -w -At -v ON_ERROR_STOP=1 --dbname="$dsn_address"` dengan password di `PGPASSWORD` dan `PGCONNECT_TIMEOUT=10`: `current_user` dan `session_user` `foundation_admin`, `current_database()` `foundation`. Kegagalan `psql` dipetakan ke kategori tabel *Pesan script*: kategori `connection` mencetak `Restore target unavailable`, kategori lain `Restore failed: <kategori>` (misalnya `invalid connection string`); identitas lain mencetak `Invalid restore target`.
7. Major `server_version_num / 10000` target sama dengan major dari baris `Dumped from database version:` header dump (langkah 5); manifest tidak dibaca. Selain itu `Backup major version mismatch`.
8. Ketiga role `foundation_owner`, `foundation_migrator`, `foundation_backend` ada dan `common.schema_migrations` ada; selain itu `Restore target not provisioned`.
9. Target kosong: `common.schema_migrations` tanpa baris, tidak ada relation (`relkind` `r`, `p`, `v`, `m`, `S`, `f`) di schema selain `pg_catalog`, `information_schema`, dan `pg_*` kecuali `common.schema_migrations`, dan tidak ada schema selain `public`, `common`, `users`, `auth`, dan schema sistem; selain itu `Restore target not empty`.
10. Perintah restore; keberhasilan mencetak `Restore completed: <nama>.dump`.

**Umur dari nama** (dipakai *Retensi* dan *Check*): stempel `YYYYMMDDTHHMMSSZ` ditulis ulang ke bentuk ISO `YYYY-MM-DDTHH:MM:SSZ` sebelum aritmetika, karena GNU `date` 9.5 di image menolak bentuk stempel (probe cross check); umur detik adalah `date -u +%s` dikurangi `date -u -d <ISO> +%s`, dan umur negatif (jam container mundur) dihitung 0.

**Retensi** (dijalankan `create` hanya sesudah backup baru lengkap; waktu dari `date -u` container; urutan nama memakai `LC_ALL=C`):

1. Hanya entri langsung di `/backup` yang berupa file biasa; subfolder dan symlink tidak pernah disentuh.
2. Backup lengkap: nama yang ketiga file nya ada sebagai file biasa. Diurutkan menurun menurut nama (stempel waktu).
3. Tujuh backup lengkap pertama selalu disimpan.
4. Backup lengkap lain yang umurnya lebih dari 35 × 86.400 detik dihapus, berurutan manifest, checksum, dump, dengan satu baris `Backup removed: <nama>` per backup dalam urutan menurun nama.
5. File yang namanya cocok pola backup tetapi setnya tidak lengkap, serta file `.partial` yang seluruh namanya cocok `^\.foundation-[0-9]{8}T[0-9]{6}Z-(scheduled|pre-migration|manual)\.(dump|dump\.sha256|json)\.partial$` (nama yang ditulis `create`), dihapus bila umur stempel nama (atau umur `mtime` untuk `.partial`) lebih dari 86.400 detik, dengan satu baris `Leftover removed: <file>` per file dalam urutan nama, sesudah semua baris `Backup removed`. Nama `.foundation-*.partial` lain tidak pernah disentuh atau dicetak, sehingga nama yang memuat baris baru tidak dapat menyisipkan baris palsu, misalnya `Backup created:`, ke log penjadwal yang menjadi catatan sha256 independen (review 2026-10-06).

**Check** (`foundation-backup.sh check`; berhenti pada langkah pertama yang gagal):

1. `/backup` direktori yang dapat dibaca dengan mode 0700; selain itu `Backup directory unavailable` atau `Backup directory must be mode 0700`.
2. Backup terbaru adalah nama terbesar (`LC_ALL=C`) di antara backup lengkap; tidak ada backup lengkap mencetak `No backup found`.
3. Checksum lebih dulu dari umur: format baris dan `sha256sum --check --strict` seperti langkah 4 *Urutan restore*; gagal mencetak `Backup checksum mismatch: <nama>`, juga bila backup itu sekaligus terlalu tua.
4. Umur menurut *Umur dari nama*; `<jam>` adalah umur detik dibagi 3.600 dibulatkan ke bawah. Lulus bila umur paling besar 93.600 detik (26 jam, inklusif) dengan `Latest backup: <nama> (<jam> h old)` dan exit 0; selain itu `Latest backup too old: <nama> (<jam> h old)` dan exit 1.

**Fingerprint** (`database/fingerprint.ts`, Bun.SQL, berjalan di host atau di image runner sebagai `database/fingerprint.ts`): menerima tanpa argumen atau tepat `--digest` (selain itu `Use no argument or --digest`), membaca `FOUNDATION_BACKUP_DATABASE_URL` (kosong: `Missing FOUNDATION_BACKUP_DATABASE_URL`), membuat pool `max: 1`, dan dalam satu transaksi `REPEATABLE READ READ ONLY` menjalankan `SET LOCAL ROLE pg_read_all_data`, `SET LOCAL row_security = off`, `SET LOCAL lock_timeout = '30s'`, `SET LOCAL TimeZone = 'UTC'`, `SET LOCAL DateStyle = 'ISO, YMD'`, `SET LOCAL IntervalStyle = 'postgres'`, `SET LOCAL extra_float_digits = 1`, dan `SET LOCAL bytea_output = 'hex'`. `row_security = off` wajib: tanpa itu, tabel ber RLS terbaca 0 baris tanpa galat (probe cross check), sehingga sumber dan target sama sama kosong dan perbandingan lulus palsu; dengan itu, tabel ber RLS membuat fingerprint gagal `Fingerprint failed`. `lock_timeout` 30 detik, sama dengan `--lock-wait-timeout=30s` backup, mengakhiri tunggu lock (misalnya migration yang sedang berjalan) sebagai `Fingerprint failed` dengan exit 1; tanpa itu fingerprint menunggu tanpa batas (probe review 2026-10-06). Identitas wajib `session_user` `foundation_backup`, `current_user` `pg_read_all_data`, database `foundation`, versi minimal 180000 (selain itu `Invalid fingerprint target`). Tabel: `relkind` `r` atau `p` yang bukan partisi, di schema selain `pg_catalog`, `information_schema`, dan `pg_*`, urut schema lalu nama; per tabel `SELECT count(*)::text AS rows, coalesce(sum(hashtextextended(t::text, 0)::numeric), 0)::text AS digest FROM <schema>.<tabel> AS t`. Sequence: `relkind` `S` dengan `last_value::text` dan `is_called`. Identifier hanya berasal dari baris katalog dan di quote server dengan `format('%I.%I', schema, nama)` sebelum dipakai `tx.unsafe`. Keluaran satu baris JSON `{"schema":1,"tables":[{"schema","name","rows"}],"sequences":[{"schema","name","lastValue","isCalled"}],"migrations":{"count","last"}}`, dan dengan `--digest` setiap tabel mendapat `digest`. Tipe: `rows`, `lastValue`, dan `digest` string (teks dari PostgreSQL, agar bigint dan numeric tidak terpotong), `isCalled` boolean, `migrations.count` number, dan `migrations.last` string nama migration terakhir menurut `name` atau `null` bila kosong. Kegagalan lain `Fingerprint failed`, exit 1, tanpa DSN. Catatan latihan memakai mode tanpa `--digest`.

**Runbook restore** (isi `docs/rules/backup.md`; project target bernama misalnya `foundation-drill-20261006` untuk latihan atau `foundation-deploy-20261006` untuk pemulihan; setiap langkah harus keluar 0 sebelum berikutnya, dan waktunya dicatat):

1. Pilih backup lengkap (terbaru, atau terakhir sebelum kerusakan). Bandingkan sha256 dump dengan catatan yang disimpan di luar folder backup dan di luar identitas unggah (baris `Backup created:` di log penjadwal, atau metadata versi objek yang terkunci); bila berbeda atau tidak ada catatan, archive tidak dipercaya dan backup lain dipilih, karena checksum di samping dump hanya mendeteksi kerusakan dan `pg_restore` berjalan sebagai superuser. Bila host sumber hilang, salin ketiga file dari penyimpanan di luar host ke folder backup host target (dibuat `install -d -m 0700 -o <uid> -g <gid>`), lalu `chown <uid>:<gid>` dan `chmod 0600` ketiganya; file milik UID lain tidak terbaca container dan tampil sebagai `Backup checksum mismatch`.
2. Siapkan env file target (salinan `.env.deploy` dengan password baru `openssl rand -hex 24` untuk admin, migrator, backend, dan backup, image tag kandidat yang sama), lalu `docker compose -p <target> --env-file <env target> -f deploy/compose.yaml up -d --wait postgres`.
3. Provisioning target dengan password baru, termasuk `-e FOUNDATION_BACKUP_PASSWORD`, memakai perintah provisioning `docs/rules/deployment.md` dengan `-p <target>`.
4. `FOUNDATION_RESTORE_DATA_NETWORK=<target>_data docker compose --env-file .env.backup -f deploy/backup.yaml --profile restore run --rm -e FOUNDATION_ADMIN_DATABASE_URL restore <nama>.dump`, dengan DSN admin target di shell. Tanpa `FOUNDATION_RESTORE_DATA_NETWORK`, Compose berhenti sebelum container dibuat.
5. Provisioning ulang (perintah langkah 3); hasil harus `verified`, atau `repaired` hanya untuk privilege yang diperbaiki otomatis menurut matriks spec 0004 dan tabel *Kasus provisioning role backup*; kegagalan drift berarti archive membawa grant yang tidak dikenal, dan target tidak dipakai.
6. Migration (`--profile migrate run --rm migrate database/migrate.ts --apply`): `0 applied` bila backup dari versi skema kandidat, atau migration tertunda diterapkan bila backup lebih lama. `Migration history drift` berarti backup berasal dari kandidat yang lebih baru atau menyimpang: hentikan dan pakai image kandidat yang cocok.
7. `--profile migrate run --rm -e FOUNDATION_BACKUP_DATABASE_URL migrate database/fingerprint.ts` dengan DSN `foundation_backup` target (password baru langkah 3) di shell; catat jumlah baris per tabel dan migration terakhir.
8. Pencabutan seluruh sesi: tidak berlaku sampai fitur 15 (*Hook fitur 15*).
9. `up -d --wait backend`, baca readiness seperti langkah 5 `docs/rules/deployment.md` sampai `200 {"status":"ready"}`.
10. Latihan: jalankan pemeriksaan isolasi pada network data target yang `internal: true`, `FOUNDATION_DATA_NETWORK=<target>_data docker compose --env-file .env.backup -f deploy/backup.yaml --profile backup run --rm --entrypoint bash backup -c 'timeout 3 bash -c "exec 3<>/dev/tcp/1.1.1.1/443"'`, yang wajib keluar bukan 0; hitung pohon input build sebelum menulis catatan (*Value sourcing*); tulis catatan latihan dengan RTO latihan sampai readiness 200 langkah 9, karena edge tidak dijalankan pada latihan lokal; lalu hapus project latihan dengan `docker compose -p <target> ... down --volumes` sesudah memastikan nama project. Pemulihan: hentikan edge project lama, `up -d --wait edge` di project target, biarkan project lama berhenti tanpa menghapus volume sampai insiden ditutup, lalu perbarui `.env.backup` (`FOUNDATION_DATA_NETWORK` dan DSN backup baru) dan jalankan `create manual` sebagai titik awal baru.

Sampai itu, langkah 8 tertulis `tidak berlaku sampai fitur 15`.

**Template latihan restore** (`docs/testing/restore-drill-template.md`, heading tetap): `## Identitas` (environment, tanggal, peran pelaksana, commit, pohon input build, ID image frontend, backend, runner, dan PostgreSQL), `## Backup yang dipulihkan` (nama, alasan, `createdAt`, umur saat restore, ukuran, checksum cocok, hasil pembandingan sha256 dengan catatan di luar folder backup beserta sumber catatan itu, asal salinan), `## Langkah dan waktu` (tabel sepuluh langkah *Runbook restore* dengan mulai, selesai, dan hasil), `## Hasil verifikasi` (provisioning, migration, jumlah baris per tabel, readiness, password lama ditolak, pencabutan sesi, pemeriksaan isolasi network data), `## RPO dan RTO terukur` (umur backup sebagai RPO aktual, total waktu sebagai RTO terukur, dibandingkan dengan 24 jam dan 4 jam; latihan lokal tanpa edge menulis RTO latihan sampai readiness 200 dan menyebut batas itu), `## Pembersihan`, dan `## Temuan dan tindak lanjut`. Catatan tidak memuat password, DSN, nama orang, atau nilai data; hanya jumlah baris.

**State transitions**: Backup: `.partial` → lengkap (manifest ditulis terakhir, lalu `done`) → disimpan → dihapus retensi (lebih tua dari 35 hari dan di luar 7 terbaru). Run yang gagal sebelum `done` → file run dihapus, file lain tetap. Target restore: cluster baru → diprovision (kosong) → dipulihkan → terverifikasi (provisioning, migration, fingerprint, readiness) → dihapus (latihan) atau menerima trafik (pemulihan). Kegagalan restore di tengah mengembalikan target ke keadaan diprovision kosong (dibuktikan `restore_failed`).

**Key invariants**:

1. Backup tidak pernah memuat role, password role, pengaturan level database atau role, maupun database lain; restore selalu membuat ulang role lewat provisioning dengan password baru.
2. Restore hanya masuk ke target yang diprovision dan kosong, tidak pernah ke database yang berisi data; script menolak target lain sebelum menyentuhnya, dan restore berjalan dalam satu transaksi, sehingga `pg_restore` yang gagal tidak meninggalkan perubahan (dibuktikan `restore_failed`).
3. Job backup hanya memegang credential `foundation_backup`, yang membaca lewat `SET ROLE pg_read_all_data` dan tidak dapat menulis; backend, worker, dan edge tidak pernah menerimanya, dan job menolak DSN role login lain sebelum `pg_dump`. Role itu tetap dapat membaca seluruh data dan `pg_authid`, sehingga credential nya setingkat admin untuk kerahasiaan, walaupun tidak untuk perubahan. Container restore hanya menerima DSN admin target dan hanya berada di network data target yang dinamai shell (`FOUNDATION_RESTORE_DATA_NETWORK`); tanpa nama itu Compose tidak membuat container.
4. Backup lengkap hanya bila manifest ada (ditulis terakhir) dan file checksum tepat satu baris yang menamai dump nya sendiri dan cocok; restore dan `check` memeriksa checksum sebelum hal lain. Checksum mendeteksi kerusakan, bukan pemalsuan.
5. Retensi berjalan hanya sesudah backup baru berhasil, tidak pernah menghapus 7 backup lengkap terbaru, dan hanya menyentuh file yang cocok pola di root folder backup.
6. Script hanya mencetak pesan kategori tetap; keluaran mentah alat PostgreSQL dan nilai environment tidak pernah dicetak, dan password DSN tidak pernah masuk argumen proses.
7. Kode proyek tidak pernah mengunggah backup, mendorong image, atau melakukan deploy; container backup dan restore hanya berada di network internal.
8. Backup mencakup seluruh database tanpa filter, sehingga schema dan tabel baru ikut otomatis. Fitur yang menyalakan row level security atau memakai large object wajib mengamandemen spec ini lebih dulu: `pg_dump` dan fingerprint berjalan sebagai `pg_read_all_data` dengan `row_security` off, sehingga gagal dengan jelas pada tabel ber RLS dan tidak melewatkan baris, dan `BYPASSRLS` pada `foundation_backup` tidak mengubah hal itu karena role efektifnya `pg_read_all_data`.
9. Riwayat migration sesudah restore hanya diverifikasi runner spec 0005, tidak pernah disunting manual.
10. Fingerprint dan pemeriksaan restore hanya membaca, dengan `row_security` off; test membandingkan sumber dan target hanya bila sumber tidak ditulis di antaranya.
11. Script tidak pernah menghapus file yang tidak dibuat run nya sendiri, kecuali lewat retensi sesudah backup baru lengkap.

**Security model**: Backup memuat seluruh data aplikasi, dan sesudah fitur 15 juga hash credential dan sesi, sehingga diperlakukan sebagai secret setingkat admin: hanya pemilik operasi yang membaca dan memulihkannya, file 0600 di folder 0700, enkripsi at rest pada setiap lokasi, dan salinan di luar host dengan identitas terpisah untuk unggah, baca, dan hapus. Job backup memakai role baru `foundation_backup` yang tidak dapat menulis, membuat objek, atau menjadi owner, dan file `.env.backup` miliknya tidak memuat credential admin atau runtime. Namun `.env.backup` setingkat admin untuk kerahasiaan: sesudah `SET ROLE pg_read_all_data`, role itu membaca seluruh data (kelak termasuk hash credential di `auth`) dan verifier SCRAM semua role di `pg_authid`, termasuk superuser bootstrap, karena `pg_read_all_data` memberi `SELECT` pada setiap katalog dan tidak dapat dicabut per katalog (probe cross check). Verifier itu hanya bahan tebakan offline, sehingga setiap role wajib memakai password acak berentropi tinggi (`openssl rand -hex 24`), dan kebocoran `.env.backup` memicu rotasi keempat role. Pada topologi satu host, akses Docker tetap setara root dan dapat membaca environment container lain (aturan infrastruktur), sehingga pemisahan ini nyata terutama saat job berjalan dengan identitasnya sendiri di platform. Restore memakai credential admin target dari shell, tidak pernah dari file, dan setiap restore merotasi credential database karena password role dibuat baru. Restore menjalankan `pg_restore` sebagai superuser atas archive yang dapat memuat SQL apa pun, sedangkan job backup dan identitas unggah dapat menulis archive dan checksum nya; checksum di samping dump hanya mendeteksi kerusakan. Risiko archive palsu diterima sampai hook fitur 15 butir (4) memutuskan tanda tangan atau enkripsi terautentikasi, dengan mitigasi wajib pembandingan sha256 terhadap catatan independen pada langkah 1 *Runbook restore*. Script menyaring keluaran alat PostgreSQL menjadi kategori karena libpq terbukti mencetak ulang potongan password pada connection string yang rusak, dan tidak pernah menaruh password di argumen proses (*Pemisahan DSN*), karena argumen terbaca setiap pengguna host, sedangkan environment hanya terbaca UID yang sama dan root. Tidak ada endpoint HTTP baru, tidak ada perubahan backend, OpenAPI, atau SDK. Belum ada data regulasi; saat fitur pengguna menyimpan data pribadi, retensi 35 hari menjadi batas berapa lama data yang dihapus pengguna masih ada di backup, dan hal itu dicatat untuk kebutuhan hukum produk.

## Consequences

**Positive**:

- Pertama kali ada backup dan pemulihan yang dapat dijalankan, dengan sasaran tertulis dan bukti per push bahwa backup kandidat benar benar dapat dipulihkan dengan data dan riwayat migration yang sama.
- Tidak ada alat, image, atau dependency baru: `pg_dump`, `pg_restore`, dan `psql` sudah ada di image PostgreSQL yang dipin, dan verifikasi memakai provisioning, runner, dan readiness yang sudah terbukti.
- Restore selalu merotasi credential database dan tidak dapat menimpa database yang berisi data.

**Negative / tradeoffs**:

- RPO 24 jam berarti sampai satu hari data dapat hilang; RPO dalam hitungan menit memerlukan arsip WAL dan spec baru.
- Satu role login baru menambah satu credential untuk dirawat dan dirotasi, dan menambah jalur baca ke seluruh data (termasuk `auth` kelak) dan ke verifier password semua role di `pg_authid`, sehingga `.env.backup` dijaga setingkat `.env.deploy`.
- Restore menjalankan isi archive sebagai superuser; sampai hook fitur 15 butir (4), keaslian archive hanya dijaga pembandingan sha256 manual dengan catatan terpisah.
- Salinan di luar host, enkripsi sisi client, dan penjadwal masih tanggung jawab platform dan pemilik operasi; tanpa itu backup hilang bersama host.
- `pg_restore --single-transaction` menahan lock setiap objek; database dengan ribuan objek dapat membutuhkan `max_locks_per_transaction` lebih besar.
- Data yang dihapus pengguna masih ada di backup sampai 35 hari.
- `test:database:real` bertambah dua container PostgreSQL dan beberapa run Compose per push; durasi di runner GitHub belum terukur.
- Catatan latihan environment ditulis manual dan tidak dihitung otomatis oleh `test:report:release`.

**Neutral**:

- Backup logis bergantung pada major PostgreSQL yang sama; upgrade major memerlukan prosedur terpisah.
- `deploy/compose.yaml` dan tabel *Topologi* spec 0012 tidak berubah; backup memakai file Compose sendiri.
- Penjadwal (systemd timer, cron, atau platform) dipilih operator; dokumen memberi contoh.

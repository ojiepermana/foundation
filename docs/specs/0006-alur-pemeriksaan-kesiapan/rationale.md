# Rationale: alur pemeriksaan kesiapan lintas aplikasi

## Context

`doctor` dan `serve` sudah memeriksa PostgreSQL, role, dan riwayat migration sebelum aplikasi dijalankan, tetapi `GET /api/status` hanya membuktikan proses backend hidup. Belum ada alur yang membuktikan browser, SDK hasil generate, proxy `/api`, backend, dan database nyata bekerja bersama. Fitur 2 (spec 0003, AC-9 dan TOOL-007) menunggu alur browser itu, dan scope menyebut fitur 10 sebagai alur nyata pertama Foundation.

Fondasinya sudah tersedia dan diterima. Spec 0004 memberi `foundation_backend` hak `SELECT` pada `common.schema_migrations`, satu pool per proses dengan batas koneksi tiga detik, dan janji bahwa route database fitur 10 menjawab 503 terkendali bila backend dijalankan tanpa URL. Spec 0007 memasang wrapper layout dengan satu item Kesiapan ke halaman pengantar statis di `/`, menyatakan halaman root tidak membuat request API, dan meminta spec ini meratifikasi atau merevisi route `/`. Spec 0008 menjadikan checker OpenAPI sebagai allow list: tepat satu response 2xx per operasi, body 2xx wajib merujuk komponen bernama, response `default` ditolak, dan operasi wajib ditambah melalui spec fitur pemilik route. Spec 0009 menetapkan bahwa `@sdk` hanya diimpor `app.config.ts` dan adapter `features/<fitur>/<fitur>-api.ts`, adapter mengembalikan `Observable` dingin dan memetakan `HttpErrorResponse` ke tipe fitur, dan body error yang dibutuhkan UI dideklarasikan sebagai model bernama.

Scope fitur 10 meminta keputusan tentang akses endpoint diagnostik di luar development, batas waktu, dan batas request. GET tidak boleh mengubah data, login tidak boleh disimulasikan sebagai kontrol akses, dan Playwright harus membuktikan alur serta kondisi gagal tanpa mock database. Belum ada model sesi, kebijakan diagnostik production, atau jalur CI dengan PostgreSQL.

Kegagalan yang harus ditangani nyata: database berhenti setelah aplikasi berjalan, koneksi tertahan lock atau membeku, hak dicabut, dan beberapa tab memicu pemeriksaan bersamaan. Tanpa batas, request diagnostik dapat menumpuk query pada database yang lambat atau membiarkan halaman menunggu tanpa akhir.

## Options considered

### `/api/status` saja

Halaman memanggil route status yang sudah ada.

**Pros**: Tidak ada query, route, atau model baru, dan permukaan production tetap sama.

**Cons**: Browser tidak membuktikan akses database maupun privilege runtime, sehingga scope fitur 10 dan AC-9 spec 0003 tidak terpenuhi.

### Route baca metadata khusus development dan halaman di `/kesiapan` (dipilih)

Route `GET /api/readiness` membaca jumlah baris `common.schema_migrations` dengan role runtime, dan halaman development baru di `/kesiapan` memakainya melalui adapter. `/` tetap halaman pengantar statis.

**Pros**: Membuktikan alur penuh dengan data minimum yang sudah ada. AC-5 dan AC-6 spec 0007, UI-002, dan APP-002 tetap berlaku. Route production yang tidak ada dan fallback spec 0007 menyembunyikan halaman di production tanpa kode khusus.

**Cons**: Menambah query, batas waktu, penanda concurrency, dan state gagal di UI. Target navigasi AC-2 spec 0007 berubah.

### Route yang sama dengan panel yang menggantikan isi `/` pada build development

Pilihan draft 2026-10-03: `/` menampilkan panel kesiapan di development dan halaman pengantar di production.

**Pros**: Item Kesiapan ke `/` dari spec 0007 tidak berubah, dan fitur 2 cukup membuka `/`.

**Cons**: Satu route menampilkan dua komponen menurut mode build. Halaman root di development membuat request API dan mengimpor adapter, sehingga AC-5 spec 0007 serta UI-001, UI-002, dan APP-002 harus ditulis ulang.

### Route diagnostik production sekarang

Route yang sama dipasang juga di production dengan kontrol akses.

**Pros**: Satu endpoint dapat dipakai operasi deployment kelak.

**Cons**: Model autentikasi, eksposur jaringan, dan kebijakan health production belum disepakati; keputusan itu milik fitur 13 dan 15.

## Rationale

Metadata migration sudah dimiliki schema `common` dan dapat dibaca role backend tanpa DDL atau grant baru, sehingga jumlah barisnya cukup untuk membuktikan query nyata dengan privilege runtime tanpa mengirim nama file atau checksum. `available` sengaja hanya berarti pembacaan berhasil; `doctor` tetap membuktikan kelengkapan migration sebelum `serve`.

Halaman di `/kesiapan` dipilih karena spec 0007 sudah diterima dengan janji bahwa halaman root tidak membuat request API, dan janji itu dibuktikan tiga test yang sudah lulus. Memindahkan diagnostik ke route sendiri hanya mengubah target satu item navigasi, sedangkan menaruhnya di `/` mematahkan satu AC dan tiga test yang sudah diterima. Fallback path tidak dikenal dari spec 0007 sekaligus menjadi perilaku production untuk `/kesiapan`.

Batas lima detik, satu pemeriksaan aktif dengan 429, dan batas statement dua detik dipilih karena probe pada PostgreSQL 18 nyata menunjukkan `Query.cancel()` Bun 1.4.2 tidak membatalkan query yang tertahan lock, sedangkan `statement_timeout` lokal transaksi menghentikannya tepat waktu. Penanda yang ditahan sampai query selesai menjamin retry tidak pernah menumpuk query pada database yang membeku. Status 400, 429, dan 503 dapat dinyatakan di bawah allow list spec 0008 (response non 2xx boleh inline maupun `$ref`), dan model bernama untuk 429 dan 503 membuat SDK mengeluarkan tipe yang dipersempit adapter sesuai spec 0009.

## Keputusan agent atas delegasi pemilik

Pemilik proyek mendelegasikan keputusan desain ("jika membutuhkan /architect anda bisa menjalankannya dengan mengambil keputusan sendiri berdasarkan rekomendasi anda"). Tidak ada manusia selama run. Spec ini diperbarui di tempat dari draft 2026-10-03, sehingga percakapan bertahap tidak diulang; setiap keputusan yang terbuka atau berubah dicatat dengan pilihan dan alasannya. Semua keputusan berikut diambil oleh agent pada 2026-10-04 atas delegasi tersebut, tanpa konfirmasi manusia.

**Tahap kebutuhan**
1. **Letak halaman.** Pilihan: (a) route baru `/kesiapan`, `/` tetap pengantar; (b) panel menggantikan `/` di development (draft); (c) kartu manual di `/` tanpa request saat dibuka. Dipilih (a): (b) dan (c) sama sama membuat halaman root mengimpor adapter dan mengirim request, melanggar AC-5 spec 0007.
2. **Navigasi.** Pilihan: (a) `Beranda` ke `/` dan `Kesiapan` ke `/kesiapan` di development, hanya `Beranda` di production; (b) `Kesiapan` ke `/kesiapan` saja; (c) item `Kesiapan` tetap ke `/` dengan tautan di halaman pengantar. Dipilih (a): setiap halaman tetap dapat dicapai lewat navigasi, dan label `Kesiapan` tidak lagi menunjuk halaman tanpa pemeriksaan. Label berbahasa Indonesia mengikuti label shell yang sudah ada.
3. **Pemicu pemeriksaan.** Pilihan: (a) sekali saat dibuka lalu manual; (b) polling berkala; (c) hanya manual. Dipilih (a), sesuai draft: hasil langsung terlihat tanpa beban berkala.
4. **Satu tombol.** Pilihan: (a) satu tombol `Periksa ulang` di semua state; (b) `Muat ulang` dan `Coba lagi` menurut state (draft). Dipilih (a): label tidak berganti saat tombol sedang difokus, dan istilah tetap konsisten sesuai aturan UI/UX.

**Tahap model data**
5. Tidak ada data baru. Fitur membaca `common.schema_migrations` milik spec 0004 dengan hak yang sudah ada; pertanyaan schema `AGENTS.md` tidak berlaku karena keputusan schema sudah tercatat di scope (baris Data fitur 10) dan spec 0004.

**Tahap kontrak dan antarmuka**
6. **Nama operasi.** `getDevelopmentReadiness` pada tag `development` dengan `security: []`, mengikuti `getDevelopmentStatus`, sehingga SDK memakai `DevelopmentService` yang sama. Pilihan kedua, tag baru `readiness`, ditolak karena route tetap bagian permukaan development.
7. **Response yang dideklarasikan.** 200, 429, dan 503 dengan model bernama; 400 dan 500 inline seperti route status. Pilihan kedua, model bernama untuk 400, ditolak karena UI tidak pernah mengirim input tambahan dan memperlakukan 400 sebagai kegagalan umum.
8. **Busy.** Pilihan: (a) 429 `{"status":"busy"}`; (b) request serentak menunggu hasil pemeriksaan yang sama. Dipilih (a): penanda sederhana, semantik HTTP yang benar untuk batas concurrency, dan sudah diantisipasi tindak lanjut spec 0009. (b) tetap harus menjawab sesuatu ketika query lama masih tertahan sesudah batas waktu.
9. **Penolakan input.** Query string tidak kosong, `Content-Length` selain `0`, atau `Transfer-Encoding` menghasilkan 400. Pemeriksaan memakai header karena probe menunjukkan Bun tidak menyampaikan body GET ke handler. Pilihan kedua, schema `query` Elysia, ditolak karena Elysia membersihkan properti tambahan alih alih menolaknya dan tidak menangkap body.
10. **Operasi wajib.** Entri kedua `REQUIRED_OPERATIONS` memeriksa komponen sukses secara ketat, dengan literal `available` lewat `const`, `enum`, atau keduanya seperti entri status. Fixture checker ikut diperbarui karena rule `required-operation` berlaku untuk setiap dokumen.

**Tahap kegagalan**
11. **Batas respons.** 5.000 ms, sesuai draft: di atas batas koneksi pool tiga detik dan di bawah `idleTimeout` 10 detik listener. Pilihan kedua 3.000 ms ditolak karena sama dengan batas koneksi sehingga penyebab kegagalan menjadi kabur.
12. **Batas statement.** `SET LOCAL statement_timeout = '2s'` di dalam transaksi. Pilihan: (a) lokal transaksi; (b) parameter `connection` pada factory pool; (c) `Query.cancel()` saat batas tercapai. Dipilih (a): tidak mengubah default pool untuk route lain. (c) ditolak karena probe membuktikan pembatalan tidak pernah selesai.
13. **Penahanan penanda.** Penanda dilepas hanya ketika query selesai, tanpa batas waktu tahan. Pilihan kedua, melepas penanda setelah batas tetap, ditolak karena query yang tertahan dapat menumpuk pada database yang membeku; akibatnya halaman menunjukkan `busy` sampai socket selesai, dicatat di Consequences.
14. **Log.** Route tidak menulis log kegagalan. Pilihan kedua, satu baris tetap per kegagalan, ditunda karena respons sudah menjadi diagnostik dan setiap log menambah permukaan kebocoran.
15. **Batas waktu di klien.** Tidak ditambahkan; respons dibatasi backend. Kebijakan interceptor dari tindak lanjut spec 0009 tetap terbuka.

**Tahap frontend**
16. **Tipe hasil adapter.** Union model SDK `ReadinessAvailable`, `ReadinessUnavailable`, dan `ReadinessBusy` ditambah `network` dan `failed` milik fitur, semuanya dibedakan field `status`. Adapter tidak pernah error, sehingga komponen tidak menerima `HttpErrorResponse`.
17. **State.** Komponen memakai `rxResource` (API publik Angular 22) atas `Observable` adapter, dengan `reload()` yang dijaga `isLoading()`. Pilihan kedua, signal dengan subscription manual, ditolak karena `rxResource` sudah membatalkan request saat reload dan saat komponen dihancurkan, sesuai skill `angular-developer`.
18. **Tombol saat loading.** `aria-disabled="true"` dengan klik yang diabaikan, bukan atribut `disabled`, agar focus keyboard tidak hilang ketika tombol yang sedang difokus dinonaktifkan.
19. **Format waktu dan jumlah.** `Intl.DateTimeFormat` dengan locale dan zona waktu browser, `datetime` berisi nilai server, dan jumlah tanpa pemisah ribuan. Pilihan kedua, `DatePipe` Angular, ditolak karena membutuhkan registrasi data locale tambahan.
20. **Gerbang development.** `isDevMode()` untuk route dan navigasi. Pilihan kedua, `define` atau `fileReplacements` di `angular.json`, ditolak karena menambah konfigurasi untuk hasil yang sama.

**Tahap test dan bukti**
21. **Lapisan bukti.** CI tanpa database: unit dan integration backend, Vitest adapter terhadap harness spec 0009, Playwright jalur 503 dan production. Database nyata: READY-008 di `tests/integration/database/` sehingga ikut `test:database:real` beserta pemindaian artefaknya, dan READY-009 lewat `test:readiness:real`. Pilihan kedua, menjalankan PostgreSQL di `test:ci`, ditunda ke fitur 11.
22. **Bukti production frontend.** Playwright melayani `dist` production lewat `page.route`. Pilihan: (a) `page.route` atas `dist`; (b) `webServer` ketiga `ng serve --configuration production`; (c) server statis baru. Dipilih (a): bundle production nyata di browser nyata tanpa port, proses, atau dependency tambahan.
23. **Konfigurasi Playwright nyata.** File `playwright.real.config.ts` tanpa `webServer` dengan akhiran `.real.e2e.spec.ts`, sehingga spec yang sama dapat dijalankan terhadap aplikasi dari orkestrasi fitur ini maupun dari `serve` milik fitur 2.
24. **Container test.** Tanpa `--rm` dan pada port host tetap, karena probe menunjukkan pool yang sama pulih setelah `docker start` hanya bila port tidak berubah.
25. **Jumlah yang diharapkan.** Banyaknya file `database/migrations/*.sql`, sumber yang sudah ada di repository, sehingga test tidak membutuhkan variable tambahan.

**Rujukan dan workflow**
26. **Tingkat rujukan.** Tanpa bagian References dan tanpa kutipan basis, mengikuti pilihan pemilik pada header scope ("penulisan tanpa bagian referensi").
27. **Workflow.** Pemeriksaan silang dan penautan scope dijalankan tahap pipeline terpisah. Status tetap `Proposed` sampai `/develop` memajukannya. Pemeriksaan silang oleh model lain sudah dijalankan; hasil dan tindak lanjutnya tercatat di bagian *Cross check* di bawah.

## Cross check 2026-10-04

Model lain membaca spec ini secara read only dan mengembalikan 18 temuan (4 major, 14 minor), sebagian saling tumpang tindih. Tidak ada manusia selama run, sehingga agent memilih opsi yang direkomendasikan, `Apply the recommended fixes`, atas delegasi pemilik. Setiap keputusan di bawah diambil oleh agent pada 2026-10-04 atas delegasi tersebut, tanpa konfirmasi manusia. Klaim yang dapat diperiksa murah diverifikasi lebih dulu di checkout ini.

**Diterima dan diterapkan**
28. **Rejection terlambat** (dua temuan major). Benar: diulang dengan Bun 1.4.2, pola `query.finally(release)` di samping `Promise.race` mencetak pesan error ke stderr lalu keluar dengan exit code 1 ketika query menolak sesudah batas. Ditetapkan: promise transaksi dibuat sekali dan langsung diberi handler akhir untuk kedua hasil, race memakai turunan yang sudah memetakan kedua hasil, timer dibersihkan, cek dan pasang penanda tanpa `await`, tanpa retry (AC-3, AC-4, invariant 2 dan 4, baris *Pelepasan penanda*). READY-002 mendapat kasus terlambat yang gagal dan berhasil, hitungan panggilan, listener `unhandledRejection`, dan pengamatan console; READY-008 memeriksa proses tetap hidup dan stderr kosong.
29. **Batas `test:database:real`** (major). Benar: `run()` memakai `timeout: 120000` untuk seluruh direktori. Dinaikkan menjadi 300.000 ms dengan rincian anggaran di *Value sourcing*. Pilihan kedua, script terpisah untuk READY-008, ditolak karena pemindaian JUnit dan bundle `test:database:real` sudah menjadi bukti credential yang diinginkan. Environment backend READY-008 dinyatakan eksplisit.
30. **Anchor test kontrak dan SDK-007** (major). Benar: anchor tanda tangan `createApp` ada di `openapi-contract.test.ts` baris 170 dan 245, anchor `.use(developmentRoutes);` di baris 262 dan `probeComposition` `sdk.test.ts`, dan SDK-007 mengharapkan tiga ekspor. Komposisi ditetapkan `.use(createReadinessRoutes(options.database)).use(developmentRoutes);` agar anchor komposisi tetap utuh, dan langkah 1 Build plan memuat daftar tertutup perubahan test yang diizinkan.
31. **Penjaga container READY-009** (major). Ditetapkan pola nama, label `foundation.test=readiness`, penolakan container Compose, pemanggilan Docker dengan array argumen, kegagalan (bukan skip) saat variable kosong, dan catatan Follow-up untuk fitur 2. Pilihan kedua, mengizinkan nama apa pun yang diberikan pengembang, ditolak karena dapat menghentikan PostgreSQL Compose bersama. Cara penjaga mengenali container Compose diputuskan ulang oleh keputusan 42 sampai 46 di bawah, karena aturan "tanpa label `com.docker.compose.project`" ternyata tidak pernah dapat lolos.
32. **502 dan 504 ke `network`.** Benar: `node_modules/vite/dist/node/chunks/node.js` Vite 8.3.0 menulis 502 `text/plain` saat proxy gagal. Backend tidak pernah menjawab 502 atau 504, sehingga keduanya dipetakan ke `network`.
33. **Urutan dan `no-store`.** Urutan 404, 400, 503 tanpa pool, lalu 429 dinyatakan di AC-1. READY-008 memeriksa `no-store`, key tepat, dan `checkedAt` pada 200, 429, dan 503, serta 400 saat pemeriksaan aktif.
34. **`HEAD` dan garis miring akhir.** Benar: probe Elysia 1.4.30 di checkout ini meneruskan `HEAD /api/readiness` dan `GET /api/readiness/` ke handler GET. Pilihan: (a) 404 lewat `Response` tetap; (b) menerima `HEAD` seperti GET dan mengujinya. Dipilih (a): kontrak hanya mendeklarasikan `get`, dan `HEAD` tidak boleh menjalankan query atau mengambil penanda.
35. **Bukti AC-8 dan AC-7.** Ditambahkan pengukuran elemen tidak terpotong, indikator focus, Enter dan Space, jumlah `1234567`, node status yang sama, pemeriksaan source impor, state `available` pada 375×812 di READY-009, bentuk item navigasi dengan `exactMatch: true`, dan `aria-current`. Nama class publik `@ojiepermana/angular` 22.1.14 diperiksa di file deklarasi terpasang dan dicantumkan di AC-8.
36. **READY-007.** Origin luar yang diizinkan `fonts.googleapis.com` dan `fonts.gstatic.com`, ditambah larangan request `/api/` dari origin mana pun. Chunk lazy boleh ada di `dist`; buktinya perilaku.
37. **READY-001.** Proses production dari `src` dan `dist/backend/index.js` dengan pesan tetap bila `dist` tidak ada, dan socket mentah hanya mengirim header.
38. **Nilai READY-009.** Timeout test Playwright 120.000 ms, interval tekan ulang 1.000 ms, nilai `playwright.real.config.ts`, `runProcessGroup` dan `listeners`, serta environment allow list untuk setiap proses anak.
39. **Profil k6 dan lonjakan.** k6 dicatat `not_applicable` karena tidak ada target kapasitas, concurrency dibatasi desain, dan k6 tidak terpasang. Lonjakan 50 request serentak dengan pemeriksaan `pg_stat_activity` dan `/api/status` ditambahkan ke READY-008.
40. **Artefak Playwright.** Trace dan video dimatikan agar pemindaian byte bermakna; setiap proses anak berjalan dengan allow list environment dan `--no-env-file`.
41. **Validasi body 200 dan tanggal.** Adapter memeriksa field 200 dan menolak `checkedAt` yang ditolak `Date.parse` pada 200 dan 503, sehingga format waktu tidak pernah melempar `RangeError`.

**Ditolak atau diterapkan sebagian**
- Varian READY-006 dengan backend `webServer` dihentikan: ditolak, karena `webServer` Playwright tidak dapat dihentikan di tengah `test:e2e`; pemetaan 502 dibuktikan READY-004 dan sumber Vite.
- Pemeriksaan READY-008 untuk koneksi di pause yang kemudian gagal: ditolak, karena tidak ada urutan Docker yang membuat query gagal sesudah batas secara deterministik; perilakunya dibuktikan READY-002.
- Pemakaian ulang `scripts/lib/readiness.ts`: ditolak, karena `waitForReadiness` membutuhkan identitas grup yang tidak dikembalikan `runProcessGroup`; polling 60 detik ditetapkan, sedangkan `process-group.ts` dan `ports.ts` tetap dipakai.
- Gerbang build agar chunk kesiapan hilang dari `dist` production: ditolak, sesuai keputusan 20, karena chunk tidak memuat credential dan tidak pernah dimuat.
- Perubahan asersi APP-003 dan APP-004 yang disebut temuan anchor: ditolak, karena keduanya tetap sah dengan opsi default `createApp` dan tidak boleh diubah.

## Penjaga container Compose 2026-10-04

Builder berhenti di langkah 1 Build plan karena penjaga container keputusan 31 tidak dapat dipenuhi. Penjaga mewajibkan container harness berlabel `foundation.test=readiness` dan tanpa label `com.docker.compose.project`. Container mewarisi label image, dan `foundation-postgres:18-pinned` dibangun suite spec 0002 lewat Compose, sehingga setiap container dari image itu membawa `com.docker.compose.project=foundation-infra-test-<hex>`, `com.docker.compose.service`, dan `com.docker.compose.version`. Akibatnya READY-008 tidak pernah dapat menghapus container miliknya sendiri, dan pemeriksaan image yang ditambahkan builder di `tests/integration/database/readiness.test.ts` selalu gagal sebelum container dibuat. Penjaga tetap dibutuhkan karena test nyata menjalankan `docker pause`, `stop`, `start`, dan `rm -f`, dan host ini menjalankan banyak project Compose sekaligus, termasuk PostgreSQL Compose bersama milik pengembang.

Tidak ada manusia selama run. Setiap keputusan di bawah diambil oleh agent pada 2026-10-04 atas delegasi pemilik ("jika membutuhkan /architect anda bisa menjalankannya dengan mengambil keputusan sendiri berdasarkan rekomendasi anda"), tanpa konfirmasi manusia. Bukti tercatat pada butir terakhir *Bukti probe 2026-10-04*.

**Pilihan yang dibandingkan**

- **(a) Kenali container Compose dari label yang hanya dipasang Compose pada container yang dibuatnya (dipilih).** Pola nama dan label `foundation.test=readiness` tetap, lalu container ditolak bila memuat salah satu dari `com.docker.compose.oneoff`, `com.docker.compose.config-hash`, atau `com.docker.compose.container-number`. Pros: sesuai pertanyaan sebenarnya (apakah Compose membuat container ini), tidak bergantung pada image mana yang dipakai, dan dapat diuji sebagai fungsi murni tanpa Docker. Cons: bersandar pada perilaku Compose yang diamati, bukan kontrak tertulis.
- **(b) Bandingkan project container dengan project image, atau tolak project `foundation`.** Pros: hanya memakai label yang sudah dipahami. Cons: container Compose yang dibuat dari image hasil build project yang sama mempunyai nilai yang sama dengan imagenya, misalnya container `foundation-infra-test-<hex>` milik suite spec 0002 atau `foundation-postgres-1` dari `foundation-postgres:18-dev`, sehingga perbandingan menerimanya dan hanya tambalan nama `foundation` yang menutup satu kasus. Butuh inspect kedua atas image, dan menolak container harness dari image dev yang berguna bagi fitur 2.
- **(c) Bangun `foundation-postgres:18-pinned` tanpa label Compose.** Pros: penjaga lama dapat dipakai apa adanya. Cons: build image milik spec 0002 dan skenario INFRA yang sudah diterima harus diubah, Compose memasang label itu pada setiap image yang dibangunnya, dan image dev tetap berlabel project `foundation`.
- **(d) Harness membangun atau memberi tag ulang image sendiri.** Pros: label image dikuasai harness. Cons: `docker tag` mempertahankan label, dan Dockerfile tidak dapat menghapus label yang diwarisi, hanya mengosongkan nilainya, sehingga penjaga berbasis keberadaan key tetap gagal. Menambah waktu build serta image yang harus dibersihkan.
- **(e) Hanya pola nama, seperti `provision.test.ts`.** Pros: paling sederhana. Cons: menghapus lapisan kedua yang sengaja dipilih keputusan 31 untuk aksi yang dapat menghentikan database orang lain.

**Keputusan**

42. **Aturan penjaga.** Dipilih (a): penjaga memeriksa nama dengan pola pemiliknya, lalu `docker container inspect` (hanya objek container), lalu label `foundation.test` bernilai tepat `readiness` dan tidak ada satu pun dari tiga key container Compose, berapa pun nilainya. Label project, service, version, dan OCI yang diwarisi dari image tidak dinilai. Ketiga key dipakai bersama, bukan salah satunya, karena probe menunjukkan container one off `docker compose run` tidak membawa `container-number`; aturan yang hanya memeriksa key itu akan meloloskannya. (b) ditolak karena meloloskan container Compose yang project nya sama dengan imagenya, (c) karena berada di luar fitur ini dan tidak menolong image dev, (d) karena label yang diwarisi tidak dapat dihapus, dan (e) karena menghapus lapisan pengaman kedua.

## `aria-current` pada pemuatan pertama 2026-10-04

Builder berhenti di langkah 3 Build plan. AC-7 dan READY-006 meminta hanya item yang cocok yang mempunyai `aria-current` pada setiap halaman, termasuk ketika `/` dibuka langsung. Kenyataannya, membuka atau memuat ulang `/` membuat link `Beranda` tampil aktif tanpa `aria-current`, pada sidebar 1280×812 maupun drawer 375×812. Agent memeriksa penyebabnya di `node_modules`: anchor `NavigationItem` milik `@ojiepermana/angular` 22.1.14 memasang `[attr.aria-current]="routerActive.isActive || isActive() ? 'page' : null"` dan sekaligus `routerLinkActive` tanpa `ariaCurrentWhenActive`. `RouterLinkActive.update()` milik `@angular/router` 22.2.0 berjalan dalam microtask sesudah content init dan setiap `NavigationEnd`, lalu memanggil `removeAttribute('aria-current')` karena `ariaCurrentWhenActive` tidak diisi. Binding hanya menulis ketika nilainya berubah. Item yang sudah aktif saat anchor pertama kali dirender tetap bernilai `'page'`, sehingga atributnya tidak pernah kembali. Sesudah item dipilih dari navigasi, nilai binding berubah sesudah microtask itu, sehingga atribut ditulis lagi.

Tidak ada manusia selama run. Setiap keputusan di bawah diambil oleh agent pada 2026-10-04 atas delegasi pemilik ("jika membutuhkan /architect anda bisa menjalankannya dengan mengambil keputusan sendiri berdasarkan rekomendasi anda"), tanpa konfirmasi manusia. Bukti tercatat pada butir terakhir *Bukti probe 2026-10-04*.

Tiga fakta tambahan mengubah bobot pilihan. Pertama, 22.2.0, versi terbaru di npm (dist tag `latest`, terbit 2026-09-28), memakai template yang sama: tag `v22.2.0` di repository library lokal masih memasang `routerLinkActive` dan binding yang sama, sehingga memindahkan pin ke 22.2.0 tidak menolong. Kedua, perbaikannya sudah ada di `main` repository library (juga di `origin/main`) tetapi belum dirilis: commit `3f2b221` (2026-10-03) mengganti `RouterLinkActive` di `NavigationItem` dengan perhitungan status aktif router milik komponen, dan `8102861` melakukan hal yang sama untuk entry grid flyout dan navbar. Ketiga, celahnya lebih luas dari laporan builder: pada drawer 375×812, membuka `/kesiapan` langsung juga membuat `Kesiapan` tanpa `aria-current`, karena anchor drawer baru dibuat saat drawer pertama kali dibuka, ketika item itu sudah aktif. Pada semua kasus yang diprobe, item yang tidak cocok tidak pernah mendapat `aria-current`.

**Pilihan yang dibandingkan**

- **(a) Perbaiki library, rilis, lalu pindahkan pin AC-8.** Pros: perbaikan sebenarnya, juga untuk `Beranda` di halaman spec 0007 dan build production; kedua test READY-006 pembukaan langsung lulus tanpa perubahan. Cons: kodenya sudah ada, tetapi rilis ke npm membutuhkan pemilik (credential dan aksi publik), dan pasangan versi Angular 22.2 dengan `@ojiepermana/angular` 22.1.14 adalah pilihan pemilik pada spec 0001 AC-1. Pin baru juga menuntut pemeriksaan ulang class publik AC-8 dan perubahan lain sejak 22.1.14 (misalnya migrasi form ke Signal Forms). Tanpa manusia, fitur 10 dan fitur 2 (yang menunggu READY-009) akan berhenti tanpa batas waktu. Pin 22.2.0 saja tidak memperbaiki apa pun.
- **(b) Revisi AC-7 dan READY-006 agar pemeriksaan `/` dilakukan sesudah navigasi di dalam aplikasi, lalu catat celah pemuatan pertama sebagai cacat library.** Pros: jujur, dapat dibangun sekarang, tanpa tambalan aplikasi. Cons: celah aksesibilitas ikut dirilis, dan tindak lanjutnya mudah terlupa bila hanya tertulis.
- **(b dengan canary) Seperti (b), dan kedua test pembukaan langsung menjadi canary yang menegaskan cacat masih ada (dipilih).** Pros: semua kelebihan (b), ditambah pengingat yang dapat dijalankan: pembaruan library atau router yang memperbaiki cacat membuat canary gagal, sehingga AC-7 dan test harus dikembalikan ke bentuk umum. Cons: test suite memuat satu asersi yang menyatakan perilaku salah, sehingga judul, komentar, dan laporan harus menyebutnya cacat yang diketahui.
- **(c) Ubah cara `/` di route, misalnya halaman pengantar lazy atau redirect, agar urutan waktu menghindari cacat.** Pros: test lama mungkin lulus pada sidebar. Cons: bergantung pada urutan waktu internal library, bukan kontrak publik; tidak menutup drawer 375×812, karena probe menunjukkan `/kesiapan` yang sudah lazy pun gagal di drawer; mengubah halaman spec 0007 yang dimuat langsung beserta UI-002 dan APP-002.
- **(d) Tambalan sisi aplikasi**, misalnya directive atau script yang menulis ulang `aria-current`, atau style yang menargetkan DOM library. Ditolak oleh `docs/rules/ui-ux.md`, yang melarang menargetkan struktur DOM internal library.
- **(e) Tambal `node_modules` (`bun patch`) atau pasang library dari git.** Cons: mengubah atau menyalin implementasi library, yang dilarang aturan Angular dan UI/UX; package dibangun dari monorepo library lewat script rilisnya, sehingga dependency git tidak dapat dipakai apa adanya; perubahan lockfile dan sumber dependency milik spec 0001.

**Keputusan**

47. **Pilihan.** Dipilih (b dengan canary), dengan (a) tetap sebagai keadaan akhir lewat Follow-up. Perbaikan memang milik library dan sudah ditulis; yang belum ada hanya rilis, dan rilis itu aksi pemilik. `docs/rules/ui-ux.md` meminta kekurangan library dilaporkan dan dikoordinasikan dengan pengguna, tanpa mengganti library atau membuat pengganti sepihak, sambil melanjutkan pekerjaan yang independen. Rekomendasi builder atas (a) diterima sebagai tujuan, dan (b) dipakai persis sebagai penahan sementara seperti saran builder. (c) ditolak karena tidak menutup drawer dan bergantung pada urutan waktu internal, (d) dan (e) karena melanggar aturan proyek.

Pada pemuatan pertama, yang dijamin hanya bahwa item yang tidak cocok tidak pernah bertanda; item yang cocok boleh tanpa atribut. Navigasi lewat tombol kembali dan maju browser juga benar menurut probe, tetapi tidak dimasukkan ke AC karena tidak ada test yang membuktikannya. Pemeriksaan lain pada kedua test tetap asersi biasa. Status spec tetap `In Progress`. Langkah verifikasi pembukaan langsung di `verify.md` disesuaikan dengan bunyi AC-7 yang baru.

Hasilnya: setiap nilai yang dibutuhkan AC-7 kini bersumber (baris *`aria-current` item navigasi* pada Value sourcing), judul dan bentuk canary ditetapkan agar builder tidak menebak, dan kasus drawer `/kesiapan` yang tidak dilaporkan builder tercakup oleh kalimat pemuatan pertama.

# 0006. Alur pemeriksaan kesiapan lintas aplikasi

**Date**: 2026-10-03
**Status**: Accepted

## Summary

Halaman development baru di `/kesiapan` menunjukkan apakah backend masih dapat membaca riwayat migration di PostgreSQL setelah aplikasi berjalan. Hasilnya datang dari satu route backend khusus development yang memakai role runtime, melalui SDK hasil generate dan proxy `/api`, sehingga alur browser sampai database terbukti nyata. Halaman `/` tetap halaman pengantar statis, dan build production tidak memasang halaman maupun route diagnostik ini. Batas waktu lima detik, satu pemeriksaan aktif per proses, dan pesan aman membuat kegagalan database terkendali dan dapat dicoba ulang tanpa restart. Penanda halaman aktif di navigasi berasal dari library; cacat library yang membuatnya hilang pada pemuatan pertama dicatat sebagai celah yang diketahui, dijaga test, dan ditutup lewat rilis library berikutnya.

## Requirements

**User stories**:
- Sebagai pengembang, Anda dapat membuka menu Kesiapan dan melihat apakah backend membaca database, kapan pemeriksaan terjadi, dan berapa migration yang tercatat.
- Sebagai pengembang, ketika database berhenti setelah aplikasi berjalan, Anda melihat pesan aman lalu dapat memeriksa ulang setelah database pulih tanpa memulai ulang frontend atau backend.
- Sebagai pemilik proyek, Anda mendapat bukti bahwa alur browser, SDK, proxy, backend, dan PostgreSQL bekerja bersama dengan role runtime, tanpa mock database dan tanpa credential yang bocor.

**Acceptance criteria**:
- **AC-1**: `GET /api/readiness` hanya dipasang pada `createApp('development')`, yang menurut `apps/backend/src/config/env.ts` hanya mendengar pada `127.0.0.1`. Route tidak memerlukan login dan dideklarasikan `security: []`. `createApp('production')`, termasuk backend production yang dijalankan sebagai proses dari `apps/backend/src/index.ts` maupun `dist/backend/index.js`, menjawab 404 dengan body `{"error":"Not found"}` untuk path ini tanpa query database. Pada komposisi development, handler memeriksa request dengan urutan tetap, dan hanya tahap terakhir yang menjalankan query atau memasang penanda pemeriksaan aktif: (1) method selain `GET` atau pathname selain tepat `/api/readiness` mendapat HTTP 404 dengan body `{"error":"Not found"}` (tanpa body untuk `HEAD`), karena Elysia 1.4.30 meneruskan `HEAD /api/readiness` dan `GET /api/readiness/` ke handler GET; (2) query string tidak kosong (`new URL(request.url, 'http://localhost').search` bukan string kosong; base tetap karena Bun memberi `request.url` relatif ketika header `Host` tidak membentuk URL absolut, keputusan 51), header `Content-Length` bernilai selain `0`, atau header `Transfer-Encoding` apa pun mendapat HTTP 400 dengan body tepat `{"error":"Invalid request"}`; (3) pool tidak ada mendapat 503 sesuai AC-3; (4) penanda aktif mendapat 429 sesuai AC-4; (5) selain itu penanda dipasang lalu query dimulai. Karena itu request tidak sah tetap mendapat 400 walau pemeriksaan lain sedang aktif, dan 400 pada backend yang diam tidak membuat request sah berikutnya mendapat 429. `GET /api/status` tetap menjawab `{"status":"ok"}` tanpa menyentuh database.
- **AC-2**: Dengan pool `Bun.SQL` yang dibuat `apps/backend/src/index.ts` dari `DATABASE_URL` milik role `foundation_backend` dan metadata yang dapat dibaca, route menjalankan satu transaksi pada pool itu: `SET LOCAL statement_timeout = '2s'`, lalu `SELECT count(*)::integer AS applied FROM common.schema_migrations`. HTTP 200 berisi JSON dengan tepat tiga field `{"status":"available","checkedAt":<string hasil Date.toISOString()>,"appliedMigrations":<integer >= 0>}`, dengan `appliedMigrations` sama dengan jumlah baris tabel saat query. Jumlah `0` (database sudah diprovision tetapi belum dimigrasi) tetap HTTP 200. Route tidak menulis database, tidak membaca file migration, dan tidak mengirim nama, checksum, maupun `applied_at`; kelengkapan migration tetap diperiksa `doctor` fitur 2.
- **AC-3**: Pool tidak ada (backend dijalankan tanpa `DATABASE_URL`), koneksi ditolak atau terputus, hak `SELECT` dicabut, `statement_timeout` terlampaui, atau batas 5.000 ms tercapai membuat route menjawab HTTP 503 dengan JSON tepat `{"status":"unavailable","checkedAt":<string hasil Date.toISOString()>}`. Backend mengirim jawaban paling lambat 5.000 ms sesudah handler menerima request. Body, header, stdout, dan stderr backend tidak memuat URL database, password, teks SQL, nama role, kode atau pesan error PostgreSQL, maupun stack, termasuk ketika query yang sudah melewati batas 5.000 ms kemudian gagal; kegagalan terlambat itu dibuang tanpa log, tidak menjadi unhandled rejection, dan tidak menghentikan proses backend. Selama database tidak siap, `GET /api/status` tetap 200 dan frontend tetap dilayani; setelah database pulih, request berikutnya mendapat 200 tanpa restart backend.
- **AC-4**: Setiap instance aplikasi dari `createApp` (satu per proses backend) memegang paling banyak satu pemeriksaan database aktif. Penanda aktif diperiksa lalu dipasang tanpa `await` di antaranya, sebelum query dimulai, dan baru dilepas ketika promise query selesai, berhasil maupun gagal, termasuk sesudah batas 5.000 ms sudah dijawab 503. Request yang datang ketika penanda terpasang langsung mendapat HTTP 429 dengan JSON tepat `{"status":"busy"}`, tanpa query baru dan tanpa antrean. Respons 200, 400, 404 dari handler, 429, dan 503 route ini memuat header `Cache-Control: no-store`. Backend tidak mencoba ulang query secara otomatis: satu request yang dijawab 503 menjalankan fungsi jumlah tepat satu kali.
- **AC-5**: Operasi diekspor ke `openapi.json` dengan `operationId` `getDevelopmentReadiness`, tag `development`, `security: []`, dan tepat response 200, 400, 429, 500, dan 503 sesuai tabel *Kontrak OpenAPI*. Model bernama `ReadinessAvailable`, `ReadinessBusy`, dan `ReadinessUnavailable` lulus aturan checker spec 0008 tanpa perubahan rule; satu satunya perubahan checker adalah entri baru `REQUIRED_OPERATIONS` sesuai tabel *Operasi wajib baru*. `Cache-Control` tidak dideklarasikan di OpenAPI. `bun run api:sync` menghasilkan `DevelopmentService.getDevelopmentReadiness()` serta ekspor tipe ketiga model di `apps/frontend/sdk/public-api.ts` tanpa edit manual, dan `bun run api:check` lulus dengan dua run identik. Checker menolak dokumen yang kehilangan operasi ini, atau yang komponen suksesnya tidak sesuai entri, dengan rule `required-operation`.
- **AC-6**: `apps/frontend/src/app/features/readiness/readiness-api.ts` berisi class `ReadinessApi` dengan `@Service()` yang mengikuti *Kontrak adapter fitur* spec 0009. Method `check()` mengembalikan `Observable<ReadinessResult>` dingin dari `DevelopmentService.getDevelopmentReadiness()`, tidak pernah error, dan memetakan hasil menurut tabel *Pemetaan adapter*. Request yang dikirim tepat satu `GET` ke URL relatif `/api/readiness`, tanpa query, body, header `Authorization`, atau `withCredentials`. Terhadap backend nyata harness spec 0009 (tanpa `DATABASE_URL`) hasilnya `{ status: 'unavailable', checkedAt }` dengan `checkedAt` string ISO, dan terhadap `sdkContractClosedUrl` hasilnya `{ status: 'network' }`. Body 200 tidak diteruskan apa adanya: adapter memeriksa setiap field lalu membuat object baru, sehingga body yang tidak sesuai model tidak pernah tampil sebagai hasil berhasil.
- **AC-7**: Pada build Angular konfigurasi `development` (dipakai `dev:frontend` dan `serve`), navigasi wrapper berisi tepat dua item dengan urutan dan bentuk `{ id: 'home', title: 'Beranda', link: '/', exactMatch: true }` lalu `{ id: 'readiness', title: 'Kesiapan', link: '/kesiapan', exactMatch: true }`, sehingga hanya item yang cocok yang ditandai sebagai halaman aktif. Atribut `aria-current` berasal dari navigasi library; aplikasi tidak menulis, menghapus, atau memperbaikinya. Sesudah sebuah item dipilih dari navigasi (sidebar pada 1280×812, drawer pada 375×812), item itu satu satunya yang mempunyai `aria-current="page"`. Pada pemuatan pertama sebuah URL (dibuka langsung atau dimuat ulang), item yang tidak cocok tidak pernah mempunyai `aria-current`, tetapi item yang cocok dapat tampil aktif tanpa `aria-current`. Celah ini cacat library yang diketahui pada `@ojiepermana/angular` 22.1.14 dan 22.2.0 (rationale, keputusan 47 sampai 50), dijaga canary READY-006, dan ditutup lewat Follow-up; ketika pin library pindah ke versi yang memuat perbaikan, kalimat pemuatan pertama ini kembali menjadi "pada setiap halaman, termasuk pemuatan pertama, hanya item yang cocok yang mempunyai `aria-current`". `/` tetap halaman pengantar statis spec 0007 tanpa request API. `/kesiapan` memuat komponen halaman secara lazy di dalam wrapper dengan judul `h1` `Kesiapan`. Halaman mengirim tepat satu pemeriksaan saat dibuka, lalu satu pemeriksaan setiap kali tombol `Periksa ulang` diaktifkan; tidak ada polling atau pemeriksaan ulang otomatis, termasuk untuk hasil `busy`. Teks setiap state mengikuti tabel *Teks dan state halaman*. Selama request berjalan, hasil lama tidak ditampilkan, tombol memakai `aria-disabled="true"`, dan aktivasi tombol diabaikan tanpa request kedua. Hasil gagal tidak menampilkan jumlah migration lama. `checkedAt` tampil dalam elemen `<time>` dengan atribut `datetime` berisi string dari server dan teks hasil `new Intl.DateTimeFormat(undefined, { dateStyle: 'medium', timeStyle: 'medium' }).format(new Date(checkedAt))`, sehingga mengikuti locale dan zona waktu browser. Jumlah migration tampil sebagai angka bulat tanpa pemisah ribuan, termasuk `0`. Meninggalkan halaman membatalkan request yang masih berjalan.
- **AC-8**: Halaman mengimpor dari `@ojiepermana/angular` 22.1.14 hanya class publik berikut, dan hanya dari tiga entry point ini: `CardComponent` (selector `Card`), `CardHeaderComponent` (`CardHeader`), `CardTitleComponent` (dipakai sebagai `<h2 CardTitle>`), `CardDescriptionComponent` (`<p CardDescription>`), `CardContentComponent` (`CardContent`), dan `CardFooterComponent` (`CardFooter`) dari `@ojiepermana/angular/component/card`; `ButtonComponent` (`<button Button>`, yang tidak mempunyai input `disabled`, sehingga state loading memakai atribut `aria-disabled`) dari `@ojiepermana/angular/component/button`; dan `SpinnerComponent` (`<Spinner decorative />`) dari `@ojiepermana/angular/component/spinner`. Tidak ada impor file internal library; style lokal hanya mengatur komposisi. Teks state berada dalam satu elemen `role="status"` dengan `aria-live="polite"` yang tetap ada dan dipakai ulang (node DOM yang sama) di setiap state, sehingga perubahan state diumumkan pembaca layar, dan status tidak disampaikan lewat warna saja. Tombol dapat dicapai dengan Tab dan diaktifkan dengan Enter maupun Space, indikator focus terlihat (`outline-style` atau `box-shadow` hasil komputasi bukan `none`, pola UI-001), dan focus tetap pada tombol setelah hasil tiba. Pada viewport 1280×812 dan 375×812, untuk state `available` dan `unavailable`, tidak ada overflow horizontal halaman, dan elemen status, setiap `dt` dan `dd`, `<time>`, serta tombol tidak terpotong: `scrollWidth <= clientWidth` dan kotak elemen berada di dalam viewport.
- **AC-9**: Pada build `production` (`bun run build:frontend`), navigasi hanya berisi `Beranda` ke `/`, route `kesiapan` tidak terdaftar sehingga `/kesiapan` diarahkan ke `/` oleh fallback spec 0007, dan membuka `/` maupun `/kesiapan` tidak mengirim request apa pun yang path nya memuat `/api/`. Chunk lazy halaman kesiapan boleh tetap ada di `dist` production, karena `isDevMode()` adalah pemeriksaan runtime dan spec ini tidak menambah gerbang build; buktinya perilaku, bukan ketiadaan file. `bun run check:frontend:bundle` tetap lulus, dan bundle production tidak memuat URL database atau credential.
- **AC-10**: Pada PostgreSQL 18 terisolasi dari image `foundation-postgres:18-pinned` yang diprovision dan dimigrasi dengan `database/provision.ts` dan `database/migrate.ts` memakai credential acak, test API dengan backend proses nyata membuktikan AC-2 sampai AC-4: jumlah `0` sebelum migration lalu sama dengan jumlah file `database/migrations/*.sql` sesudah migration, lock tabel termasuk lonjakan 50 request serentak, hak yang dicabut, container yang di pause, dihentikan, lalu dijalankan lagi, dengan proses backend tetap hidup dan stderr nya kosong sepanjang test. Playwright membuktikan alur browser melalui SDK, proxy `/api`, backend, dan database: hasil berhasil dengan jumlah tepat, periksa ulang, database dihentikan lalu hasil gagal tanpa jumlah lama, kemudian database dijalankan lagi dan periksa ulang berhasil tanpa restart frontend atau backend. Tidak ada mock database. Nilai credential acak tidak muncul di respons, output backend dan frontend, JUnit, maupun artefak Playwright; trace dan video Playwright dimatikan agar setiap artefak dapat dipindai sebagai byte, dan setiap proses anak menerima environment allow list eksplisit tanpa membaca file `.env`. Test nyata hanya menjalankan `docker pause`, `unpause`, `stop`, `start`, dan `rm -f` pada container yang lolos penjaga baris *Nama dan penjaga container*, sehingga container yang dibuat Compose, termasuk PostgreSQL Compose bersama, tidak pernah disentuh, sedangkan container harness dari image yang dibangun Compose (`foundation-postgres:18-pinned` membawa label project Compose dari suite spec 0002) tetap dapat dihentikan, dijalankan lagi, dan dihapus.

## Decision

**Chosen option**: Satu route baca metadata khusus development dan satu halaman development di `/kesiapan`, memakai pool backend, SDK, dan adapter yang sudah disiapkan fitur 5, 8, dan 9, sementara `/` tetap halaman pengantar statis.

Route ini memeriksa apakah backend dapat membaca database pada saat request. Ia tidak menggantikan `doctor`, yang memeriksa role dan checksum seluruh migration sebelum `serve`. Production tidak memasang route maupun halaman diagnostik. Spec ini merevisi target navigasi AC-2 spec 0007 (item Kesiapan kini menuju `/kesiapan`, dengan item Beranda baru menuju `/`), sesuai tindak lanjut spec 0007 yang meminta route `/` diratifikasi atau direvisi di sini.

**Implementation skills**: `angular-developer` (skill pengguna, `~/.claude/skills/angular-developer/`), terutama `references/resource.md` untuk `rxResource` dan `references/http-client.md` untuk `HttpErrorResponse` · `elysiajs` (skill pengguna, `~/.claude/skills/elysiajs/`) untuk komposisi route dan helper `status`. Aturan proyek untuk Angular, UI, database, keamanan, testing, dan OpenAPI/SDK tetap mengikat implementasi.

## Feature design

**Data model sketch**:

| Objek | Kolom yang dipakai | Relasi | Hak fitur ini |
| --- | --- | --- | --- |
| `common.schema_migrations` dari spec 0004 | `name text` primary key; `checksum text`; `applied_at timestamptz` (hanya jumlah baris yang dibaca) | Tidak ada FK | `SELECT` oleh `foundation_backend`, yang sudah diberikan spec 0004 |

Tidak ada entitas, migration, seed, grant, atau schema baru, sehingga pertanyaan schema `AGENTS.md` tidak berlaku: fitur hanya membaca metadata `common` sesuai baris Data scope fitur 10 dan spec 0004. Runner spec 0005 tetap satu satunya penulis riwayat.

**State transitions**:
- Halaman: dibuka → `loading` → salah satu dari `available`, `unavailable`, `busy`, `network`, atau `failed`. Tombol `Periksa ulang` dari state selain `loading` → `loading` (hasil lama disembunyikan). Tombol saat `loading` tidak berbuat apa apa. Meninggalkan halaman saat `loading` membatalkan request.
- Backend per instance aplikasi: `idle` → `checking` (penanda dipasang, query dimulai) → `idle` saat promise query selesai. Selama `checking`, request sah baru mendapat 429. Request dengan method atau path lain (404) dan request dengan input tambahan (400) dijawab sebelum state diperiksa, tanpa mengubahnya. Bila batas 5.000 ms tercapai, request pemicu dijawab 503 tetapi state tetap `checking` sampai query selesai; hasil query terlambat, berhasil maupun gagal, hanya melepas penanda lalu dibuang.

**API surface**:

| Endpoint | Method | Masukan | Hasil | Akses | Kesalahan penting |
| --- | --- | --- | --- | --- | --- |
| `/api/readiness` | GET | Tidak ada query, body, atau header khusus | 200 `ReadinessAvailable` | Tanpa login, `security: []`, hanya komposisi development pada loopback | 400 input tambahan; 429 pemeriksaan lain aktif; 503 database tidak siap atau melewati batas waktu; 500 kesalahan tak terduga lewat `onError`; 404 tidak dideklarasikan untuk `HEAD`, method lain, atau `/api/readiness/` di development, serta untuk path ini di production |

| Path | Method | `operationId` | Tag | Security operasi | Response sukses | Komponen |
| --- | --- | --- | --- | --- | --- | --- |

**Pemetaan adapter** (`ReadinessResult = ReadinessAvailable | ReadinessUnavailable | ReadinessBusy | { status: 'network' } | { status: 'failed' }`, dideklarasikan dan diekspor dari `readiness-api.ts`; tiga tipe pertama diekspor ulang dari `@sdk` dengan `export type`):

| Hasil operasi SDK | Syarat | `ReadinessResult` |
| --- | --- | --- |
| Sukses 200 | Body berupa object dengan `status === 'available'`, `appliedMigrations` yang lulus `Number.isSafeInteger` dan `>= 0`, serta `checkedAt` string yang `Date.parse` nya bukan `NaN` | Object baru `{ status: 'available', checkedAt, appliedMigrations }` |
| Sukses 200 | Selain itu, misalnya layanan lain menjawab 200 atau field hilang, negatif, pecahan, atau tanggal tidak sah | `{ status: 'failed' }` |
| `HttpErrorResponse` 503 | `error` berupa object dengan `status === 'unavailable'` dan `checkedAt` string yang `Date.parse` nya bukan `NaN` | Object baru `{ status: 'unavailable', checkedAt }` |
| `HttpErrorResponse` 429 | `error` berupa object dengan `status === 'busy'` | `{ status: 'busy' }` |
| `HttpErrorResponse` 0, 502, atau 504 | Body apa pun. Backend hanya menjawab 200, 400, 404, 429, 500, dan 503, sehingga 502 dan 504 berasal dari proxy development, misalnya backend tidak berjalan saat `dev:frontend` aktif (Vite 8.3.0 yang dipakai dev server Angular menjawab 502 `text/plain` kosong ketika target menolak koneksi) | `{ status: 'network' }` |
| Selain itu | Misalnya 400, 404, 500, 503 atau 429 dengan body lain, 503 dengan `checkedAt` yang ditolak `Date.parse`, atau error yang bukan `HttpErrorResponse` | `{ status: 'failed' }` |

**Value sourcing**:

| Aksi | Nilai yang dihasilkan atau ditampilkan | Sumber |
| --- | --- | --- |
| Backend 200 | `status: "available"` | Literal yang dikirim ketika query jumlah berhasil |
| Backend 200 | `appliedMigrations` | Kolom `applied` dari `SELECT count(*)::integer AS applied FROM common.schema_migrations`; cast `integer` membuat `Bun.SQL` mengembalikan `number` (probe: `typeof` bernilai `number`) |
| Backend 200 dan 503 | `checkedAt` | `new Date().toISOString()` jam server pada saat hasil, kegagalan, atau batas waktu diketahui; 400, 404, dan 429 tidak mempunyai waktu karena query tidak dijalankan |
| Backend 503 | `status: "unavailable"` | Literal untuk pool yang tidak ada, error apa pun dari transaksi, atau batas 5.000 ms |
| Backend 429 | `status: "busy"` | Penanda pemeriksaan aktif milik instance aplikasi |
| Backend 400 | `{"error":"Invalid request"}` | Body yang sama dengan pemetaan `VALIDATION` di `onError` `apps/backend/src/app.ts` |
| Backend 400 | Pemicu | `new URL(request.url, 'http://localhost').search !== ''`, `Content-Length` selain `0`, atau ada `Transfer-Encoding`. Probe: Bun 1.4.2 memberi `request.body` `null` untuk GET yang membawa body tetapi tetap menyampaikan kedua header itu, sehingga pemeriksaan memakai header |
| Backend 404 development | Pemicu dan bentuk | `request.method !== 'GET'` atau `new URL(request.url, 'http://localhost').pathname !== '/api/readiness'` (probe 2026-10-04: Elysia 1.4.30 meneruskan `HEAD` dan garis miring akhir ke handler GET, dengan `request.method` `HEAD` dan pathname `/api/readiness/`; bila `request.url` relatif, Elysia sendiri menjawab garis miring akhir dengan 404 lewat `onError`, keputusan 51). Dijawab dengan `Response` tetap berbody `{"error":"Not found"}`, `Content-Type: application/json`, dan `Cache-Control: no-store`, karena 404 tidak ada di peta response route; probe: bentuk ini lulus `tsc` dengan `apps/backend/tsconfig.json`, dan `HEAD` mendapat 404 tanpa body |

**Key invariants**:
1. `createApp` tidak pernah membuat pool. `index.ts` membuat paling banyak satu pool saat `DATABASE_URL` ada, meneruskannya ke `createApp(mode, { database })`, dan menutupnya saat shutdown sesuai spec 0004 dengan `pool.close({ timeout: 1 })`, sehingga pemeriksaan yang tertahan database beku tidak menahan shutdown melewati batas lima detik (keputusan 54). `createApp('development')` tanpa opsi tetap dapat diekspor tanpa listener maupun koneksi (APP-003, OPENAPI-001), dan route readiness pada komposisi itu menjawab 503.
2. Penanda pemeriksaan aktif dan batas waktu dimiliki instance yang dibuat factory route, tanpa state tingkat modul. Penanda diperiksa dan dipasang tanpa `await` di antaranya, sebelum query, dan dilepas hanya ketika promise transaksi selesai. Promise transaksi dibuat satu kali per pemeriksaan dan saat dibuat langsung diberi handler akhir untuk hasil berhasil maupun gagal; tidak ada promise turunan yang dibiarkan tanpa handler, dan timer batas waktu dibersihkan pada setiap jalur. Tidak ada antrean, tidak ada pembatasan waktu tahan penanda, dan tidak ada retry di backend. Batas statement berlaku lewat `SET LOCAL` di dalam transaksi, sehingga default pool untuk route lain tidak berubah.
3. Query bertuliskan tetap dengan nama schema eksplisit dan tanpa input dari client. Hanya jumlah baris yang keluar dari database.
4. Setiap kegagalan database dipetakan ke body 503 yang sama. Route tidak menulis log untuk kegagalan, dan kegagalan terlambat sesudah batas 5.000 ms dibuang tanpa log dan tanpa unhandled rejection, sehingga detail PostgreSQL tidak pernah sampai ke stdout, stderr, atau respons, dan proses backend tidak berhenti karenanya.
5. Halaman memakai SDK hanya melalui `ReadinessApi`. Adapter tidak menyimpan state; komponen memegang state lewat `rxResource`. Paling banyak satu request aktif per halaman, tanpa polling. Saat request baru dimulai, hasil lama tidak ditampilkan sebagai hasil saat ini, dan hasil gagal tidak pernah menampilkan jumlah lama.
6. Halaman `/` tetap statis dan tidak mengimpor adapter atau SDK, sehingga AC-5 dan AC-6 spec 0007 tetap berlaku. Route `kesiapan` dan item navigasinya hanya ada ketika `isDevMode()` bernilai `true`. Penanda halaman aktif sepenuhnya milik navigasi library; aplikasi tidak menambal DOM internal library untuk menutup celah `aria-current` pada pemuatan pertama.
7. Tidak ada dependency, variable environment aplikasi, secret, schema, migration, atau grant baru.

**Security model**: Pelakunya pengembang lokal dan proses lain di mesin yang sama yang dapat menjangkau `127.0.0.1:8888`. Route tidak memerlukan login karena hanya ada pada komposisi development yang mendengar pada loopback; production tidak memasangnya. Data yang keluar hanya status, waktu, dan jumlah migration, dibaca role `foundation_backend` yang hanya mempunyai `SELECT` pada metadata. Tidak ada akses `users` atau `auth`, DDL, atau hak tulis. Halaman lain di browser dapat mengirim GET lintas origin tetapi tidak dapat membaca respons karena tidak ada header CORS; serangan DNS rebinding dapat membaca jumlah dan waktu itu, risiko yang diterima untuk data serendah ini di development. Batas method, path, dan input, satu pemeriksaan aktif, batas statement dan respons, `no-store`, serta pemetaan respons eksplisit menahan konsumsi resource dan kebocoran detail. `HEAD` tidak menjalankan query karena dijawab 404. Konsumsi resource berlebihan dibuktikan lonjakan 50 request serentak pada READY-008 (paling banyak satu sesi `foundation_backend` menunggu lock dan `/api/status` tetap cepat); profil k6 dicatat `not_applicable` karena tidak ada target kapasitas yang disepakati. URL database dan error mentah tidak masuk browser, log, JUnit, maupun bundle.

**Configuration required**: Tidak ada variable environment aplikasi, secret, atau layanan baru. Backend memakai `DATABASE_URL` milik `foundation_backend` dari spec 0004; `serve` tetap mewajibkan preflight `doctor` fitur 2, sedangkan backend yang dijalankan langsung tanpa URL memberi 503 pada route ini. Jalankan `test:infrastructure` (INFRA-001 dan INFRA-005 harus lulus), `typecheck:contract`, `typecheck:e2e`, `test:integration`, `test:scenarios`, `test:database:real`, `test:readiness:real`, dan `test:ci`. Satisfies **AC-10** dan menjaga AC-6 spec 0002.

## Consequences

**Positive**:
- Alur nyata pertama Foundation terbukti dari browser sampai PostgreSQL dengan role runtime, termasuk database yang berhenti setelah aplikasi berjalan lalu pulih.
- Fitur 2 mendapat alur browser READY-009 yang dapat dijalankan ulang terhadap aplikasi yang dijalankan `serve` untuk menuntaskan AC-9 spec 0003.
- Adapter pertama menjadi contoh nyata kontrak adapter spec 0009, termasuk body error bermodel bernama untuk 429 dan 503.
- `/` tetap statis, sehingga AC-5 dan AC-6 spec 0007 serta UI-002 dan APP-002 tetap berlaku tanpa perubahan.

**Negative / tradeoffs**:
- Route menambah satu query, penanda concurrency, dan timer di backend. Bila koneksi database membeku tanpa memutus socket (container di pause atau jaringan terputus diam diam), penanda tertahan sampai socket selesai dan halaman menunjukkan `busy` selama itu; probe pause 8 detik selesai sendiri setelah unpause, tetapi bila socket tidak pernah selesai, backend perlu direstart.
- Batas 5.000 ms dan 429 membuat sebagian pemeriksaan pada database lambat perlu diulang manual.
- Target navigasi AC-2 spec 0007 berubah dan asersi navigasi UI-001 ikut berubah.
- Setiap entri `REQUIRED_OPERATIONS` baru memaksa fixture `valid.json`, `subset-full.json`, dan hitungan method OPENAPI-006 ikut diperbarui. Setiap operasi SDK baru juga mengubah daftar ekspor SDK-007, dan perubahan tanda tangan `createApp` mengubah anchor teks di `openapi-contract.test.ts`; daftar perubahan test yang diizinkan tercantum di langkah 1 Build plan.
- Bukti database nyata (READY-008 dan READY-009) membutuhkan Docker dan berjalan di luar `test:ci` sampai fitur 11 menambahkannya ke CI. Ada dua konfigurasi Playwright yang harus dirawat. Batas `run()` di `test:database:real` naik menjadi 300 detik, sehingga run yang macet baru dihentikan lebih lambat; saat itu seluruh grup proses dihentikan dan container READY-008 dihapus lewat penjaga.
- Kasus query yang gagal sesudah batas 5.000 ms dibuktikan pada unit READY-002 dengan fungsi jumlah pengganti, dan dalam proses pada READY-008 dengan error PostgreSQL asli: `deadlineMs` 500 dan lock dari koneksi admin membuat error `57014` tiba sekitar 2.000 ms, sesudah jawaban `unavailable` (keputusan 57). Lewat backend proses nyata, batas 5.000 ms lebih besar dari batas statement dua detik, sehingga urutan itu hanya deterministik dalam proses. READY-008 membuktikan proses tetap hidup dengan stderr kosong pada urutan pause dan stop yang dapat diulang.
- Kondisi backend mati saat `dev:frontend` berjalan (502 dari proxy) dibuktikan pada tingkat pemetaan adapter READY-004, bukan lewat browser, karena `webServer` backend `test:e2e` tidak dapat dihentikan di tengah test.
- READY-007 bergantung pada `dist` production dari checkout yang sama; `test:ci` menjamin urutannya, tetapi run lokal dengan `dist` lama dapat memberi hasil yang tidak mewakili kode saat ini.
- Serangan DNS rebinding dapat membaca jumlah migration dan waktu dari backend development; risiko ini diterima.
- Penjaga mengenali container buatan Compose dari tiga label yang diamati dipasang Compose 5.4.0, 5.5.0, dan 5.5.1 pada setiap container yang dibuatnya, bukan dari jaminan tertulis Compose. Bila versi Compose kelak berhenti memasang ketiganya, lapisan label hanya tersisa `foundation.test`; pola nama tetap menolak container Compose biasa (nama `<project>-<service>-<n>`), kecuali container Compose yang sengaja diberi `container_name` sesuai pola dan label `foundation.test=readiness`. Saat Docker Compose di host atau CI diperbarui, probe label 2026-10-04 sebaiknya diulang, dan fixture READY-010 disesuaikan bila hasilnya berubah.
- Pada pemuatan pertama sebuah URL, item navigasi halaman itu tampil aktif tanpa `aria-current`, sehingga pembaca layar tidak mengumumkan halaman saat ini sampai pengguna memilih item dari navigasi. Probe 2026-10-04: pada 1280×812 celah ini muncul di `/`, dan pada drawer 375×812 di `/` maupun `/kesiapan`. Celah yang sama ada di build production untuk `Beranda` (navigasi spec 0007). Fitur ini diterima dengan cacat library yang diketahui itu, dan perbaikannya bergantung pada rilis library oleh pemilik (Follow-up).
- SDK bertambah satu operasi dan tiga model, sehingga initial bundle sedikit bertambah karena barrel `@sdk` dimuat `app.config.ts`; halaman sendiri dimuat lazy.

**Neutral**:
- Tidak ada perubahan schema, migration, grant, atau variable environment aplikasi. Jumlah migration bukan bukti checksum atau kesiapan release; `doctor` dan runner tetap menangani itu.
- Batas statement berlaku lokal per transaksi; default pool untuk route lain tidak berubah.
- Frontend tidak menambah batas waktu request sendiri: respons route dibatasi 5.000 ms oleh backend, dan listener backend menutup koneksi diam setelah 10 detik.
- `ng serve --configuration production` juga menyembunyikan halaman karena gerbangnya `isDevMode()`, bukan mode backend.
- Chunk lazy halaman kesiapan dapat tetap ada di `dist` production karena gerbangnya pemeriksaan runtime; chunk itu tidak memuat credential dan tidak pernah dimuat karena route tidak terdaftar.
- Profil k6 tidak dijalankan untuk fitur ini (`not_applicable`); kapasitas dan pemulihan pada beban milik fitur 12.
- Orkestrasi test yang memanggil Docker berada di `tests/orchestration/`, sejalan dengan `tests/integration/tooling-real/doctor-smoke.ts`, sehingga `scripts/` tetap berisi tooling development, build, dan pemeriksaan repository tanpa Docker sesuai INFRA-001 spec 0002 (keputusan 58).
- Container harness tetap membawa `com.docker.compose.version` dan label OCI dari image. Label project dan service dikosongkan saat dibuat; Compose 5.5.1 sendiri tidak memasukkan container `docker run` ke `ps` maupun `down --remove-orphans` project yang labelnya diwarisi (probe 2026-10-04), sehingga pengosongan itu hanya menjaga filter label `docker ps` milik suite spec 0002. Image `foundation-postgres:18-pinned` dan cara suite spec 0002 membangunnya tidak berubah.
